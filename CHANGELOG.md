## [Unreleased]

### Changed

- **A closed day's digest is computed once per process instead of on every Overview tick** — `/api/summary/stream` and `/api/usage/stream` sit behind the *same* watch on the same log directory and rebuild on the same 600ms debounce, but only one of them was ever taught not to redo its past. `docs/features/usage-limit-meters.md` records the reasoning for the meters — `buildUsage` and `learnCeilings` are "cached rather than run per request" because "re-reading thousands of sidecar files per tick is not affordable", with each archived day memoised for the process lifetime in `usage-history.ts` — and the summary and trends path never got it. `buildSummary`'s baseline walk recomputed up to fourteen finished days on every tick, and `buildTrends` had a memo (`rawArchiveDigests`) covering only a *fully archived* day, so the live half of a split day and the whole baseline walk fell outside it. That store now lives in `server/src/day-digest-memo.ts`, deliberately shaped like the `usage-history.ts` it sits beside, and both callers read through it. **The key is the one that was already there** — day, backing, archive root, and the classifier hash-set *size* — because the parity harness computes both backings and a shared entry would hand the second run the first one's answer, and because the classifier store only grows, so a digest taken before a new revision was recorded would otherwise never be recomputed. **Today is never stored**, which is a fix and not only a precaution: the archiver rotates on the UTC day while a reporting day is a `REPORT_TZ` day, so the archive can already hold part of the day in progress, and the old memo would cache that half-day and serve it until restart. **Neither is a day still split across the live directory and the archive** — the memo has no key for "still moving" and needs none, because `baselineDigests` reads both halves of a day and keeps the result only when the live directory contributed nothing at all. Consulting the memo *before* reading is what makes it worth anything: a hit skips both halves of the day's read, not merely the digest arithmetic. `buildTrends`'s resolution loop, fourteen or thirty sequential awaits over days that do not depend on one another, is now a single `Promise.all` — the shape `readWindow` already uses for its archived halves. `baselineDigests` deliberately stays sequential: it stops at the first day that captured anything, normally the very first, and a day resolving to nothing is never memoised since its archive may simply not have run yet — so loading that run together would re-read the same idle days on every request forever, to save an await on a day the walk was never going to reach. **The honest limit, which the idea recorded and which is worth repeating**: a memo helps the second read and later, so a cold server still pays full price for the first Overview load. The store is unbounded, like the two beside it, and bounded in practice by the number of distinct closed days one process is asked for — one small object per day, growing at most a day per day of uptime.
- **One manifest in `packages/core` declares every API route, and both the server and the dashboard are built from it instead of restating it** — the same route was written down four times: once as a `case` in the 900-line `switch` in `server/src/server.ts`, a second time in that file's hand-written `WRITE_ROUTES` set and its five sibling path constants, a third time as a template string in an `apps/admin/src/api.ts` client function, and a fourth time in that function's `qs` call naming the query parameters. Nothing tied the four together, so a route could be served and unreachable, or reachable and unserved, and the only thing that noticed was a person. `packages/core/src/api-routes.ts` states each of the **72** routes once — path, methods, `kind` (`json` or `stream`), the query parameters it reads, the CORS posture it answers under, and for a stream the JSON route it mirrors — and everything else is derived from that. **Response types stay types, not runtime entries**, because a runtime type entry is a second statement of the shape the handler already returns; the manifest carries the path union and each consumer binds its own shapes to it. **The two derivations are load-bearing rather than decorative, which is the whole point of doing it this way.** The server's dispatch is now `Record<ApiRoutePath, RouteHandler>`, so it fails to compile in *both* directions — a handler for a path nobody declared, and a declared path nobody handles — and the request path reads `apiRoute(url.pathname)` for the 404, `isApiWriteRoute(route)` for the 405, and the route's own `cors` for the preflight, where before each of those was a separate hand-maintained list. The dashboard's `read`/`write` helpers are generic over `ApiJsonGetPath` / `ApiWritePath` and take their parameters as `Partial<Record<ApiRouteParam<P>, …>>`, so a typo'd query key is a type error rather than a parameter the server silently ignores, and the two response maps extend `Record<…, unknown>` so a declared path with no bound response fails the build. **`WRITE_ROUTES` folded in as a property rather than as a rule**: a write is `cors: 'origin'` **and** a declared `POST`, which reproduces the old set exactly and keeps `/api/chat/stream` where it belongs — origin-checked, because it carries chat content, and never on the write allowlist, because it is a GET. That pair is why CORS is declared per route instead of inferred from the method. What the types cannot say, `packages/core/test/api-routes.test.ts` says: paths are unique, every `streamOf` names a declared JSON route, and the write allowlist is the same fourteen paths in the same order it always was. **The honest remainder**: the SSE URLs hardcoded in `apps/admin/src/routes/*.tsx` still name their paths as template strings — those files belong to another change in flight, so only `chatStreamPath`, which lives in `apps/admin/src/api.ts`, is manifest-derived today, and the rest is a mechanical follow-up once that lane is clear.

### Fixed

- **The rail's first section label, `DASHBOARD`, sits clear of the wordmark's shadow instead of under it** — `.rail-head` casts `0 10px 16px -10px` downward and `.stations` began flush against that edge, so the shadow's roughly 8px of reach past the clip line landed directly on the first `.nav-group-label` and read as smudged rather than as a boundary. The space is a `padding-block-start` on `.stations`, deliberately **not** more `padding-bottom` on `.rail-head`: the shadow is drawn on the head's bottom edge, so growing the head moves the shadow down with the label and clears nothing. Putting it below the clip line moves only the content, and because `.stations` is the scroller that padding is scroll start rather than a fixed gap — the first label still passes under the head on scroll, which is what the shadow exists to show.

- **The real-archive parity replay is one case per archived day and one per undated route, instead of one case for the entire corpus, so the gate stops timing out as the archive grows** — `route parity over the real logs/archive > answers every wired route byte-identically for every archived day` replayed *every* wired route against *every* day of `logs/archive` inside a single `it`, so its cost was the sum over the whole corpus and grew by a day every day. At twenty archived days it hit the 600s budget and failed on every PR without ever asserting anything wrong. **It was structural, not a regression**: run alone on `main` with its fourteen siblings skipped, the case still dies at 600007ms after a 655s duration, which also means `main` never actually finished the replay — the number to beat was never 670s, it was unknown. Measured after the split, it is about 1020s. **Two splits, because the first one exposed that the obvious cause was the wrong half.** `ParityRoute` gained a `perDay` flag naming the routes that enumerate per archived day (`/api/summary`, `/api/tools`, `/api/trends`, `/api/prompt-mix`, `/api/usage`, `/api/skim`, `/api/context`) and `ParityContext` gained a `days` field scoping their enumeration, so the suite declares an `it.each` over the days — twenty-one cases at 9–31s each, about 347s in total. That left the *undated* routes, which turned out to be the real weight: replayed together they overran 600s on their own. Each is now its own case, which is where their cost stops growing, since `parity.ts` already caps their enumeration by transcript, by run and by prompt cohort. **The one enumeration that had no cap now has one.** `/api/sessions/suggestions/bucket` replayed a case per suggestion bucket, and buckets accrue every fifty sessions and never retire — at 240s it was the slowest case left by a factor of three, and climbing. `BUCKETS_PER_RUN` bounds it to the newest twenty, on the same footing as the existing `PER_THREAD_CASES`: `/api/sessions/suggestions` replays whole and carries every bucket with its suggestions, so what the cap bounds is the per-bucket drill-down alone. **Nothing about the comparison weakened**: every archived day and every route is still replayed, each answer still compared whole and byte-for-byte through `diffJson`, and `NORMALIZATIONS` is still empty. **The caches had to move with the split**, or it would have multiplied the cost it was meant to bound: `mismatches` dropped every memo on entry — right for the synthetic corpus that mutates between its tests, wrong for cases that would then re-read the archive once each. Replaying is now `replay(ctx, db, routes)` with the caches left to the caller, `mismatches` is that plus the reset it always did, and the real-archive suite resets once in `beforeAll` over its frozen snapshot. That is safe for the reason the memos were built that way: each keys on the backing that filled it *and* the directory it read, so a warm cache still cannot let one backing answer for the other. **The `replayed nothing, so it proved nothing` guard moved out of `replay` to its callers**, because once a route is its own case that assertion becomes wrong: `/api/concepts` and `/api/concepts/concept` enumerate nothing by design when the hosted store is configured, and the guard would have failed a correct route. It still holds where it means something — the whole-corpus replay, and each day's. The day listing is taken synchronously (`archivedDaysSync`) for the one reason a sync read is warranted: the cases have to be *named* while the suite is collected, which is before any `beforeAll` has run.

### Added

- **A test now names any handler or client function that reaches no route** — the route manifest made the two directions the compiler *can* see impossible (a handler for an undeclared path, a declared path with no handler), but neither direction reaches an export that sits outside the dispatch table entirely: a removed feature leaves a dead `build*` in a 3051-line `server/src/api.ts` and a dead client function in a 1026-line `apps/admin/src/api.ts`, and manual review was the only thing looking. `server/test/orphan-surface.test.ts` derives both lists from `API_ROUTES` and **fails by naming every unmatched export**, never by a count — `server/src/api.ts: buildX` is the message, so the failure is already the fix list. It is a **static parse rather than a runtime import**, for two reasons that are not stylistic: `apps/admin/src/api.ts` reads `import.meta.env`, which only Vite defines, and `apps/admin` has no test suite of its own, so a server-side test reading its source is the only route to it; and a handler's link to its route exists only as a textual reference inside the `HANDLERS` map, whose values are closures that say nothing about themselves once constructed. What anchors the parse is the file's first assertion — that `HANDLERS`' keys are exactly the manifest's 72 paths — which is what lets the rest treat `server/src/server.ts` as *the* routed surface. **It never deletes**, and a deliberately-unrouted export is exempted in `UNROUTED_BY_DESIGN` with a reason and the entry point that does reach it, both re-checked: a stale exemption whose export was deleted, whose export became routed, or whose named entry point stopped calling it fails as loudly as an orphan. The four standing exemptions are `buildSuggestionBuckets` and `buildRuleDefects` (reached by `server/src/suggestions-cli.ts`, never over HTTP) and the dashboard's `API_BASE` and `PERMISSION_MODES` (configuration and a value list, not calls). The reverse drift is caught too — a client naming a path the manifest does not declare.
- **The ideas dashboard can say SHIPPED, and Release has stopped being a one-way door** — a claimed idea offered exactly one control, `Release`, so the only move available when its PR merged was the one that threw the claim away: the ledger's own `applyIdeaMarks` rebuilds an entry without its claim on every mark but `shipped`, which means the holder *and* the PR url on that claim are gone, and there was no second control to get them back with. `IdeaDecisionControls` in `apps/admin/src/components/IdeaCard.tsx` — shared by the list card and the permalink, so both move together — now reveals a form for each of the three decisions that need a value, one at a time, on the same reveal-require-submit shape `Reject` already used. **Ship collects the PR url as the note**, prefilled from `idea.claim.pr` when the claim carries one and re-filled if a claim arrives from the CLI while the card is mounted, because the server refuses a note-less `shipped` mark and the note *is* the url. **Re-claim collects a holder and optionally the url again** — typed rather than restored, since the release genuinely destroyed both, and a `packages/core` test now pins that fact so the UI is not guessing at it. The two decisions the controls need are predicates in the domain rather than conditions in the component: `canShipIdea` says `accepted` and `claimed` and nothing else — never the terminal `shipped`, never an idea nobody signed off — and `isIdeaTakeable` is the claimability rule extracted out of `applyIdeaClaims`, which now calls it, so the button and the write cannot disagree about what is takeable. **Claiming is its own route, `POST /api/ideas/claim`, not a status a mark may set**: a mark carries no holder, so `claimed` stays absent from `BROWSER_IDEA_STATUSES` while `shipped` joins it, and refusals — somebody else holds it — come back as data to render rather than as a thrown error, exactly as `applyIdeaClaims` returns them. `applyIdeaStatus` enforces the same two rules server-side that the buttons enforce in the browser, so a hand-rolled request cannot un-ship terminal work or ship an idea that was never accepted.
- **Every idea now states the `/task` prompt that builds it, in one place both a human and an orchestrator read** — the ledger already held everything a run needs to start work (the title, the rationale in its fixed bullet order, the human's `comment` as build criteria, every citation with its quote, and the `claim` protocol that stops two runs building the same idea), and nothing assembled it: a person accepting an idea then retyped it as a task, and `/improve` handing accepted ideas to subagents had to re-derive the same brief per subagent, which is exactly where two runs' briefs drift apart. `ideaTaskPrompt` in `packages/core/src/ideas.ts` composes it — pure, no I/O — and both surfaces call it, so the dashboard's copy button and `pnpm --filter server ideas prompt --slug <slug>` emit the same bytes rather than two paraphrases. **It is derived and deliberately never stored.** There is no `prompt` field on `IdeaEntry`, because a stored copy goes stale the moment somebody re-files the idea or rewrites its comment, and the ledger would then carry two disagreeing statements of one task with nothing to say which is current; the entry stays the single source and the prompt is a reading of it, which is what the "follows the entry rather than a stored copy" test pins. **The claim lines are on every prompt, including an already-claimed one**, since a prompt is copied once and pasted into a run that starts later — what was free at render time may not be by then, and `ideas claim`'s non-zero exit is a better refusal than a status snapshot taken minutes earlier. On `/ideas/$slug` the prompt sits in a **Preview | Edit** pair that opens on Preview: the text is generated and usually correct, so opening on a textarea would present a composed artifact as a blank to fill in. Edit is for the one-off caveat that belongs in *this* copy, and **that edit is local to the clipboard on purpose** — the durable instruction already has a field, `comment`, which the generated prompt quotes, so writing there changes what everyone generates next while editing here changes only what you paste now; the card says so beside the Reset button. The page is live over SSE, so the draft follows the regenerated prompt when the entry changes **unless it has been edited**, discarding a reader's own words being the worse surprise. The copy button reports the one failure it actually has — `navigator.clipboard` is absent outside a secure context, which is precisely the case when the dashboard is opened over plain HTTP from another machine — rather than appearing to succeed.

### Fixed

- **The skills a concept surfaced wrap inside their card instead of running off the side of it** — `BadgeCard` on `/concepts/$ord` laid its badges out as a plain `<div>` of inline spans held apart by an inline `marginRight: 4`, and that spacing is the only thing the row had: `.badge` is `white-space: nowrap`, and adjacent JSX siblings emit **no whitespace text node** between them, so the badges formed one unbroken inline run with nowhere the browser was permitted to break. A concept with more than a few entries therefore painted straight past the card's right edge rather than moving to a second line — margin is not a break opportunity, which is why the row looked spaced correctly right up until it was too wide. The container now carries a `.badge-row` class — `display: flex`, `flex-wrap: wrap`, `gap: var(--space-3)` — so wrapping is the row's job rather than something the badge is expected to volunteer, and the inline style is gone since the gap states the same 4px as a step of the space scale. It lands in `styles/components/badge.css` beside the badge it spaces, so both `BadgeCard` callers on the page — **Skills applied** and the optional **Skills surfaced** — are fixed by the one rule rather than by a style repeated at each call site.
- **An idea's rationale renders as a real bullet list on its permalink, instead of folding its bullets into one line** — `/ideate` writes the rationale as literal `- ` lines separated by newlines and may close with a paragraph of evidence, and both the card and the permalink read that text through `ideaRationaleBullets`, which was **all-or-nothing**: *every* non-empty line had to be a bullet, so the moment a rationale carried its closing paragraph the helper returned `[]`, the whole thing fell back to a single `<p>`, and HTML folded every one of those newlines into a space. The bullets were in the stored string the entire time — the two newest rows on the ledger carry them — which is why this read as a formatting bug with no bad data behind it. **The permalink now renders the rationale through the existing `Markdown` component** rather than through the card's reading of it, so the `- ` lines become a real `<ul>`, a `**Label**` lead-in becomes bold, inline code stays code, and the closing paragraph keeps its own block instead of running on from the last bullet. That component already backs the memory, command, concept and job-file views, so this is one more consumer of a renderer the dashboard ships rather than a second markdown path. **The card keeps its own reading, because it cannot use that one**: its three-bullet preview clamps by bullet rather than by height, since `-webkit-line-clamp` needs `display: -webkit-box`, which stops a `<ul>` rendering as a list at all. So `ideaRationaleBullets` moved from all-or-nothing to the **leading run** — every line up to the first that is not a bullet — which is what makes the same mixed rationale preview as three bullets on the list page too. The guard that mattered survives intact: the *first* non-empty line must still be a bullet, so a paragraph that merely contains a dash stays prose rather than becoming a list with an orphan, and every existing case for that rule passes unchanged. The trailing prose is deliberately outside the preview and only outside the preview — the permalink carries it, so nothing is dropped anywhere a reader can reach for it. `ideas list` had the same defect in its own medium and got the same fix: it interpolated the rationale after a fixed six-space indent, which indents the first line only, so a bulleted rationale printed one indented bullet and left the rest hanging at column zero.
- **The Concepts page reads the store `/teach` actually writes to, and says which store answered** — `/teach` has been posting to the hosted Worker since step 2 of [ADR 0005](docs/adrs/0005-host-the-concept-store.md), while `/api/concepts` went on reading `logs/concepts.jsonl`. A concept saved from any device was therefore invisible in the dashboard, and **the page looked correct while it was wrong**: an empty list from the local file is indistinguishable from an empty corpus, which is how a saved concept came to look lost rather than misfiled. With `CONCEPTS_URL` and `CONCEPTS_TOKEN` both set — read from `process.env` on every call, never logged, never in a response body, never written to a file — both routes read the Worker; with either unset the local file answers exactly as before, so a checkout with no credentials still renders the page. **The ambiguity is the other half of the fix.** `meta.storePath` was already printed by the page, so it now carries the Worker's read URL when the hosted store answered and the local path *plus the reason* (`CONCEPTS_URL/CONCEPTS_TOKEN unset, hosted store not read`) when it did not; `meta.store` says the same thing as a value. Nothing under `apps/admin/src/routes/` changed — the label the page already rendered was the right place to put it. **A configured store that will not answer is a 502, not a fallback**, on the two SSE routes as well as the two request routes: serving the local corpus after a failed remote read would reproduce the exact wrong-store-looks-fine page this change exists to remove. Those SSE routes also stop watching `logs/` once the hosted store is configured — `logs/` takes a write per proxied request and none of them say anything about the Worker, so the watch would refetch the whole corpus every debounce tick, per connected client, and discard each answer as unchanged; a remote-backed page takes its snapshot and refreshes on the next load. The read goes to `GET /api/concepts/export` rather than the compact listing route, because the export carries the optional detail fields the detail page renders and every version of a term — the local file's own reading of itself, where a term taught twice appears twice — so one request answers both routes in the format the existing parser already takes. **`ord` keeps meaning what it always meant**, and that is what keeps every `/concepts/<n>` permalink resolving: a Worker row is keyed by a ULID, but the export is ordered `saved_at ASC, id ASC`, which is the order the file was appended in and the order the database was seeded from, so line *n* of the file is row *n* of the export; the reasoning is recorded in `server/src/concepts-remote.ts` beside the code that depends on it. The local file, its ingest and its schema are all untouched — retiring them is the next step, once remote reads are proven in use — and the request path's shadow check is skipped on a remote answer, since it compares the two local backings and a remote answer came from neither — the parity harness skips its two concepts suites for the same reason, rather than replaying one remote answer against another at a full-corpus fetch per case per side. Tests stub `fetch` and never touch the live Worker, covering the remote read, the fallback on each half-set credential, a non-2xx, and a refused connection; a setup file clears both variables before the suite so a developer who exports them for `/teach` does not turn the existing concepts tests into live network calls.

### Changed

- **The side rail's two fixed ends are lit now, so the stations read as passing under them rather than stopping short — and the status dot says its state in colour instead of in motion** — the rail pinned the wordmark to its top and the log count to its foot and gave the stations between them their own scroller, which means there are two edges where content is clipped and neither said so: a station cut off mid-row at either end looked like a station that had been drawn badly, not like a list continuing past a boundary. Both ends now carry a soft `box-shadow` and sit above the scroller on `z-index`, since `.stations` is positioned and would otherwise paint over an unpositioned sibling. **The gap between the head and the stations moved from the stations' margin to the head's own `padding-bottom`**, which is the whole reason the shadow lands where it should: at 20px of margin the head's border box ended 20px above the line content actually vanishes at, so a shadow drawn on it floated in open rail rather than falling on the clip. The spacing a reader sees is identical — the same step, on the other side of the same gap — and the drawer's `.stations { margin-top: 0 }` went with it, having existed only to cancel the margin that is no longer there. The foot needed no such move: its border-top already sat flush against the stations' bottom edge, so it gained the shadow alone, mirrored upward. **The pulse came off the live dot at the same time, and taking it off exposed why it had been carrying the whole signal.** `.dot.ok` looped `signal-pulse` — an expanding teal ring, forever, on a dot that is reporting a stream is *fine* — which is an interface asking to be looked at in order to say nothing has happened; the two places it showed, the `LiveIndicator` in the shared day-window controls and the health badge in the rail's foot, are both ambient status, and ambient status is what colour is for.

### Fixed

- **The status dot has been rendering grey since the stylesheet was layered, so the pulse ring was the only thing on screen that knew the stream was up** — `styles.css` declares `@layer tokens, base, layout, components` once for the whole sheet, and a layer beats specificity outright: `shell.css` is `layout`, so its `.dot.ok`, `.dot.bad` and `.dot.warn` — two class selectors each — lost to a bare `.dot` in `suggestion.css`, which is `components` and set `background: var(--line)`. Every health and live dot in the dashboard therefore drew in the line grey, at the suggestion list's 7px rather than the shell's 8px, and had done so for as long as the layer order has existed. It went unnoticed for the one reason it could: the pulse's ring is drawn as a `box-shadow` in teal and `suggestion.css` declares no `animation` or `box-shadow` to override it, so the ring kept firing over the grey dot and read as the status — which is also why removing the pulse could not be done without finding this, since it would have left a grey dot reporting `live`, `connecting` and `offline` identically. The fix is to scope the offending rule to the list it bullets, `.bucket-suggestions .dot`, rather than to reorder layers or raise specificity: the file is the suggestion component's, its dots are only ever emitted inside that `<ul>`, and a component rule that names a bare `.dot` is claiming every dot in the sheet by accident. `ok`, `warn` and `bad` now resolve to `--signal`, `--amber` and `--coral` as they were always written to.

### Changed

- **The `AdviceProvider` interface is gone, and the heuristic advice is simply the advice** — `packages/core/src/advice.ts` declared a one-method interface, gave it exactly one implementation, and no caller ever typed against it: `server/src/api.ts` imports the concrete `heuristicAdvice` singleton by name. The interface's own doc comment carried the reason it existed — an `agents/`-backed LLM provider could "drop in without touching callers" — and the repo had already written down that the case never arrived, in the design spec's Out-of-scope list and in the feature doc's open questions, both of which are corrected here rather than left describing a seam that is not there. **Deleting it changes no behaviour, and that is the argument**: every caller compiles unchanged, which is the test speculative generality has to fail. The return type collapsed with it — `advise` returned `Advice[] | Promise<Advice[]>`, a union that existed only so a hypothetical network-backed provider could be async, so the sole call site's `await` was awaiting a value that was never a promise and is now gone. `Advice`, `Severity` and `ADVICE_THRESHOLDS` are untouched: the first two are the wire shape the dashboard and the daily job both read, and the third is configuration for rules that really run, so none of them is the seam. The counter-argument is recorded rather than dismissed — if an LLM provider is genuinely next, the interface was a week early rather than wrong — and the answer is that it costs one line to reintroduce in the commit that adds a second implementation, justified by a caller instead of by a principle. The test now exercises the exported singleton the callers use rather than constructing an instance of its own.

### Added

- **The pull request an idea is claimed against now moves the idea's status, so `shipped` stops being something a person has to remember** — the ledger already recorded the PR url on `IdeaClaim`, and nothing ever read it. So the last step of building an accepted idea was a human noticing a merge and asking an agent for `ideas mark -s shipped`, and the two failures either side of that were worse than the chore: a merged idea sat `claimed` until somebody looked, and a claim whose PR was closed or whose branch went away held the idea **forever**, because `isIdeaClaimStale` deliberately never expires a claim carrying a `pr` — the six-hour TTL is safe precisely because a recorded PR means review is in progress, which is the same property that makes an abandoned one permanent. `planIdeaPrTransitions` in `packages/core/src/ideas.ts` is the whole decision and it is pure: store plus `{ pr, outcome }[]` in, and out come the transitions, the `IdeaMark[]` that performs them, and — named rather than implied — what was deliberately left alone. `claimed` + merged becomes `shipped` with the PR url as the note, **byte for byte the row the manual mark writes**, so the automatic path and the hand path do not diverge and the claim survives as the record of who built the thing; `claimed` + closed or detached becomes `accepted`, which is the release the docs already describe, human sign-off intact and the idea back on offer; `claimed` + open is nothing, because the claim is doing its job. **`shipped` is terminal**: its PR is read like any other and no outcome moves it, since re-opening a merged PR or deleting its branch must not un-ship work that landed, and it comes back under `unchanged` so a reader can see it was checked rather than quietly skipped. `server/src/ideas-pr.ts` does the two impure halves, and the inference in it is the part that needed care — `detached` is not a PR state but an **open** PR whose `headRefName` is absent from `git ls-remote --heads origin`, and the failure direction is asymmetric, so an unreadable remote is read as *every branch alive* rather than *every branch deleted*: the other reading would release every live claim on the ledger the first time the scheduled job ran without network. The same refusal to guess governs coverage — the `gh` listing reads one repo and is capped at 200 while this ledger is device-wide, so a linked PR the listing does not cover is reported under `unobserved` and left untouched, never read as closed. It reaches the user two ways: `ideas sync` (with `--dry-run`, like every other maintenance step here) for a run that wants to reconcile now, and the scheduled `maintain --apply` job beside `reconcileRuns`, which is the one that actually removes the manual step — never fatal there, since no `gh`, no auth and no origin all mean "learned nothing this run" and are logged as distinct from a successful run with an empty plan. The dashboard's claim line turns the url into a real link in both `IdeaCard.tsx` and the detail route, since it is now the thing the status follows.
- **Every legacy-compatibility fallback now carries the date it became legacy, and a test fails once no retained capture can still reach it** — three separate feature docs asked the same question about the same class of code and none of them could be answered: `session-transcripts.md` on whether `isAuditSidecar` should require the `session` block "once those age out", `session-suggestions.md` on `node.argsHash ?? node.tool` as "the legacy path, kept deliberately", `live-session-graph.md` on the `Agent`/`Task` allow-list and the start-time heuristic that "stay". Each is speculative generality **on a timer** — a branch serving a case that was real when written and stops being a case on a date nobody recorded, after which deleting it cannot change behaviour and it is pure carried weight. `packages/core/src/fallbacks.ts` records that date: nine entries, each with the day the *superseding* field began being written (established from `git log -S<field> -- proxy`, never guessed), the `file:line` of the branch, and the text that line must contain. **On its own the table buys nothing** — a list of dates is a comment — so the other half is `server/test/fallback-retirement.test.ts`, which reads the oldest capture the install *actually retains* and fails for any entry dated before that floor, naming the file, the line and what to delete. It reuses what is already there rather than reimplementing the walk: `listArchiveDays` from `server/src/retention.ts` and the all-time floor resolver `fileSource.oldestDay` in `server/src/db/source.ts`. **It never deletes** — removing a compatibility branch is a change somebody reviews. Three details separate a live gate from a decorative one. The floor is a **listing, not a corpus walk** — two `readdir`s, no capture opened, 16 ms — because the one other test that reads the real `logs/archive` takes minutes and a second of those would be worse than nothing. An entry may be **undated** where the history genuinely cannot establish a day (two are: the archived digest's `cacheHitRatio`, and the request-filename guard's tolerance of `:`), and the undated set is pinned in the test, so an undated fallback is reported rather than passing silently — a compatibility branch nobody dated is the state this exists to end. And the `file:line` anchors are **checked against the code**, since a line number is the whole anchor and line numbers move; a registry that drifted off its own code would retire the wrong branch, which is worse than retiring none. The comparison is strict: a field introduced *on* the floor day is not retirable, because a capture from earlier that same day sits in the floor's own directory. **The first run retires nothing, and that is a real answer rather than a null one** — the floor resolves to 2026-07-12, which is the repo's own first commit, so every field ever added is younger than the retained corpus and all seven dated fallbacks are load-bearing today. The nearest is the skim block at 2026-07-18: roughly six days of the archive rolling forward, at which point the suite goes red on its own and names it. The three docs pages now point at their entry instead of asking the question.

- **What the dashboard reads out of a body is extracted before eviction removes it, so an old day loses the blob and not the answer** — retention is documented as lossless for metrics, and it is, for everything read out of an `.audit.json`. It was never true of a value read out of the **body**. `/api/skim` renders each request's last user turn, and both read backings got that by opening the `.request.txt` *at query time*: past the retention edge the file is gone, so the route counted a `bodiesEvicted` and handed back nothing. The skim views therefore degraded silently exactly where the usage views did not, against a claim `docs/features/retention-lifecycle.md` made in two places — a documentation defect as much as a code one, and both are corrected here. **This is a compaction pass, not a retention change**: eviction deletes the same files on the same schedule, and nothing about the plan, the cutoff or the `--apply` path moves. What changed is *when* the value is computed. Ingest now reads the body for it while the body is still there, into two columns beside the `md_path` / `request_path` / `blob_evicted` trio [ADR 0004](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md) added for precisely this shape of question: `skim_text`, and `body_derived` — which is a flag rather than `skim_text IS NOT NULL`, because a body carrying no user turn derives a **real null** and so does an unparseable one, and without the distinction every later pass would re-read the same file forever. A body that vanished before any pass saw it is left *underived* rather than marked as looked-at, which keeps "never observed" apart from "observed, nothing there". The extraction is also the **dedupe**: `latestUserText` existed twice, once in `server/src/logs.ts` and once in `server/src/db/source.ts`, which is a parity break waiting to happen for a value two backings must agree on byte for byte — it now lives once, in `server/src/derive.ts`, and the file scan, the SQL read and ingest all call it. The read path prefers the column and **stops opening the blob at all** when the row is derived, falling back to an existence check, because `meta.bodiesEvicted` has to stay a *live disk observation* on both backings: a row's `blob_evicted` is only as fresh as the last ingest, and an archived day whose audit listing has not changed is skipped wholesale by its watermark. So the count still rises at the edge while the text stops disappearing with it. Ordering is a **guarantee rather than a hope the watcher was running**: `maintain --apply` runs an ingest pass of its own before the evict phase, the same before-the-destructive-step constraint it already enforces for command-run reconciliation. One derivative was considered and deliberately left out — the system-prompt section text `buildPromptSection` recovers from up to eight bodies is *unbounded*, and extracting it would be the content-addressed blob store the ADR rejected; these are bounded strings, `logs/` stays the sole source of truth, and `rm logs/claude-proxy.db && pnpm --filter server ingest` still reconstructs everything on disk, which a test asserts rather than the prose claiming it. **The honest limit, stated rather than glossed: it is forward-only.** A day whose bodies are already gone has nothing left to derive from and a re-ingest cannot invent it, so every row already on the ledger as evicted stays exactly as it is. This improves every day from the day it ships and no day before it.

- **"All" is a window like any other now, because the reader was given a floor instead of being left to answer an unbounded span with roughly today** — `readWindow` in `server/src/db/source.ts` is the single place a multi-day span composes the archived and live halves, and it excluded exactly one span: with no `date`, `since` or `sinceDays` it read the live root alone and returned an empty `days`. That is not an error, it is a wrong answer that looks like an answer, and it is why the pickers stopped at 30d and every route clamped `?days=` into 1–365 — the widest question the dashboard could ask was a month. One option, `all: true`, is the whole seam: the backing is asked for its own oldest day, that day is resolved into an ordinary `since` **once per request**, and everything below the resolution composes a bounded span exactly as it did before, so no existing builder's code path changes. **The floor is looked up, never guessed**, and per backing: the file side lists `logs/archive/`'s day directories through the same `listArchiveDays` that `collectRetentionCorpus` uses — split out of it rather than reimplemented, and without the per-file `stat`s pricing a plan needs — plus the live root's dated filenames; the substrate takes `MIN(id)` over `request` and `request_skipped` and `MIN(source_dir)`, all indexed, so it is a seek. Both then step one day back, because a reporting day lags the UTC day a filename is stamped with and the earliest archived directory can hold the tail of the day before it. **The substrate does not walk at all.** `readDir` was already filtering by an `id` range over the primary key and by `source_dir`, so dropping the range leaves a query that selects the whole archive at once; `readWholeArchive` issues it once and buckets the rows into reporting days by the walk's own rule — a day is `archive/<day>` plus `archive/<day+1>`, archived-directory-first, stem-sorted — which turns 90-odd paired per-day reads into one. The file backing keeps the walk, since a directory listing has nothing cheaper to offer. `readDir` split into `entriesFrom` and `materialize` so both paths build sidecars, tool and rate-limit joins, skim bodies and eviction counts through the identical code, which is the only basis on which parity can be claimed — and it is asserted, by a test requiring the two backings to produce deep-equal window shapes, the same floor, and the same resolved day count over a corpus spanning three months. `DAY_WINDOWS` gained an **All** entry, `?days=0` is the wire spelling (a count of days cannot say "all", and `0` needed no dashboard fetch change), `parseDays` resolves it server-side off the backing's floor, and the route clamp passes it through untouched: 365 still bounds a number a caller asked for, and no longer decides how far back the corpus may be read.

- **Retention gained an explicit `never`, and every maintenance run now prices what it is choosing to keep** — eviction is a cost decision [ADR 0004](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md) made and measured, but the other side of it was never built: `resolveRetentionDays` took `RETENTION_DAYS` as any non-negative integer with no way to say off, so "keep everything" was spelled as a large magic number — a setting no reader could tell from a typo, and one nothing tested. **The value that read like off was the worst one available.** `RETENTION_DAYS=0` puts `cutoff` on today, which expires every archived day at once and hands the very next `--apply` the entire body corpus; it is now **rejected** and falls back to 30, because nobody has ever meant "evict everything captured before this morning". `never` — with `off` accepted for it — is the supported way to say it, and it turns off **exactly one phase**: archiving and eviction were already separate in `planRetention`, so day directories, sidecars and the archive layout are what they would otherwise have been and the plan simply evicts nothing. That is asserted rather than asserted-about, by requiring the `never` plan's whole `archive` section to equal the 30-day plan's over the same corpus. The window is a type rather than a number now (`RetentionWindow = number | 'never'`) and `cutoff` is `string | null`, so "no day expires" is unrepresentable as a date instead of encoded as an unreachable one. **The second half is what makes `never` defensible rather than a footgun in the opposite direction.** The planner already walked the whole corpus with byte sizes and the run already printed counts, days and reclaimable bytes, so it now prints the keep side out of the same walk: bytes surviving the plan, split into bodies and everything else; the body rate observed over the retained window; and the growth that follows at 30, 90 and 365 days. The rate's denominator is the **calendar span** the retained bodies cover rather than the count of days that happen to hold a file — a quiet day still spent a day of the window — and under a finite window the projection is clamped at the steady state that window implies, since each new day displaces an expiring one. Under `never` nothing clamps it, and the number printed is the bill for keeping everything. It is arithmetic over a listing already in hand rather than a second pass over the disk, and it prints under `--apply` as well as on a dry run, which is the point: the scheduled 21:00 job's log becomes a growth record and not only a reclamation record.

- **An idea's rationale renders as the list it now is, and the permalink gained the decision itself** — `/ideate` writes a rationale as plain-English bullets in a fixed order (what it is, the problem, how it works, what it replaces, size, and an optional `Depends on <slug>`), so the dashboard renders it as a list rather than as one run-on line, and two proposals become comparable line for line instead of paragraph for paragraph. **Both shapes are on the ledger at once and stay that way**: nothing rewrites a row it did not write, so every idea recorded before the bulleted shape exists as a paragraph and still renders as one. `ideaRationaleBullets` in `packages/core` decides which is which by reading the text rather than by a stored flag, and its test is deliberately all-or-nothing — *every* non-empty line must open with a bullet marker — so a paragraph containing a dash renders as the paragraph it is, and a half-converted rationale never renders as a list with prose floating beside it. A leading `**Label**` is split from its claim so the labels hang and the fixed order can be scanned down its left edge. The card shows the **first three** bullets and the permalink shows all of them; the cut is by bullet rather than by height because `-webkit-line-clamp` needs `display: -webkit-box`, which stops a `<ul>` rendering as a list at all, and because the fixed order already puts the three a scanning reader wants at the top. A legacy paragraph keeps the three-line clamp it had. **The decision controls moved onto `/ideas/$slug`** at the same time, as one shared `IdeaDecisionControls` rather than a second copy: Accept, Reject-with-required-reason, Release and Undo were card-only, which meant a reader who followed the permalink to read the one thing the card clamps had to go back to the list to act on what they had just read — and one component means the two surfaces cannot disagree about what a status may become.

### Changed

- **The concepts Worker's MCP endpoint speaks the `2026-07-28` revision and only that one, so a connection costs nothing to establish** — `services/concepts/src/mcp.ts` had `PROTOCOL_VERSION = '2025-06-18'` hardcoded and answered an `initialize` handshake, which is session ceremony over a server that has never held a session: it answers every request from a single JSON body and keeps nothing between them. The drift went unnoticed because **the test asserted the version's shape rather than its value** — `toMatch(/^\d{4}-\d{2}-\d{2}$/)` passes for any date ever written there — so the suite now asserts `2026-07-28` exactly, which is the only form of that assertion that can fail when a revision moves. The new revision replaces the handshake with a version declared on **every** request, in `params._meta` under `io.modelcontextprotocol/protocolVersion` and mirrored into the `MCP-Protocol-Version` header; the two must agree, and each request is accepted or rejected on its own. `Mcp-Method` and, on a `tools/call`, `Mcp-Name` are likewise required and checked against the body — a header disagreeing with the body it names is the vulnerability the mirroring creates, so it is `400` with `-32020` rather than a reconciliation. The mandatory `server/discover` returns the supported versions, the capabilities including the `extensions` map the revision specifies (empty: this server advertises none), and the identity under `_meta`. **Legacy support was dropped rather than kept alongside**, because a dual-era server needs sessions for the legacy half and would reintroduce per-connection state on the one always-on component in the system to serve clients no agent here runs. An `initialize` therefore gets `-32022` with `data.supported` naming `2026-07-28` — *not* a bare "method not found", since a legacy client has no fall-forward mechanism and that message is the only diagnostic it can ever surface. The three tools, their schemas, their descriptions and the `isError`-inside-the-result convention are untouched, as are the single `application/json` body and the absent GET stream. ADR 0005 records the era decision and the reversal path.

- **The token layer gained a space, type and radius scale, and a lint rule now refuses a bare px, so a component picks a step instead of inventing a number** — the cascade split named `@layer tokens` and put exactly one motion token in it, and the layer otherwise held ink, surfaces, a signal palette and three font families: nothing at all about size or space. So every component that needed room invented a number, and the drift is measurable rather than theoretical. **27 distinct spacing values** across padding, gap and margin, including 3, 5, 7, 9, 11, 15, 18, 22, 26 and 34px — a value differing from its neighbour by one pixel was not a decision anybody made. **17 font sizes, five of them half-pixels** — 9.5, 10.5, 11.5, 12.5 and 13.5 sitting alongside 9, 10, 11, 12 and 13, which is the tell: a component that wanted "slightly smaller than the one beside it" got a new size rather than a step. And **13 corner radii between 2px and 16px** where the dashboard draws three shapes. This is the mechanism `--rail-inset` bought for one variable, at the scale of the whole sheet. **The ramp is derived from the sheet rather than imposed on it**: a strict 4px base was rejected because 6px, 10px and 14px are used 48, 63 and 38 times — more than 4px and 16px are — so they are load-bearing, not drift. `--space-1..12` therefore runs on a 2px rhythm to 16px and 4px above it, `--space-1` is the hairline 1px an inline chip's vertical padding actually wants, and three **named** page-shell tokens (`--space-page`, `--space-page-lg`, `--space-page-xl`) carry the one-off frame sizes rather than growing the ramp a coarse tail one rule reaches for. `--text-1..10` removes the half-pixel entirely — every one of them rounds **up half a pixel**, which is sub-pixel and cannot be seen. **Where a value did not sit on a step it went to its nearer neighbour, and where it sat exactly between two it went to whichever the sheet already used more**, so the migration does not systematically grow or shrink the interface; eleven values moved by more than that, none by more than 4px, and each was checked on the page rather than in the diff. **The enforcement is a real Biome rule, not a bolt-on script**: Biome 2.5 ships nothing for this, but its GritQL plugins do run against CSS, so `apps/admin/lint/no-bare-size.grit` rides along with the `biome check .` that already gates the repo. It fires on padding, margin, gap, font-size and border-radius, and lets through a `var()`, a bare `0` and the `0px` floor of a `clamp()` — a zero has no size to snap. One limitation is stated rather than papered over: the rule is meant to scope to `@layer components`, and a `within` clause over an at-rule compiles and then matches nothing, so it scopes by file — which here is the same statement, since the dashboard sheet is the only CSS in the repo and `tokens.css` declares only custom properties. No markup changed.
- **The sessions rail's preview line is derived from the opening prompt instead of quoting it, so a slash-command row stops rendering its own XML envelope** — the rail took its preview from `subtitle ?? firstTask`, the untouched first prompt, and a slash command's first prompt opens with `<command-message>`. `packages/core/src/sessions.ts` already stripped `<command-name>` and `<command-args>` for the *name*, so every command session showed a clean `/task` over the literal string `<command-message>task</command-message>`, wrapped mid-tag by the two-line clamp and ellipsised inside a tag name — which is what made those rows read as broken rather than merely long. **The fix is deliberately not a titling request.** The open question at `docs/features/dashboard-chat-sessions.md` had already established that only the `cli` transport carries Claude Code's out-of-band titling call, so a fix routed through it would have been missing in exactly the sessions that need one; `deriveSessionPreview` derives the line from the prompt that is already there, beside the two patterns that were already stripping it, so the dashboard is not the only place that knows about the tag. A command's **arguments** are the preview — they are the one part of its prompt the name does not already carry, and the definition inlined after the envelope is identical on every run — and a command with no arguments gets no preview at all rather than a repeat of its name. **A compaction preamble is answered rather than quoted**: 129 of the 565 transcripts in the store open with "This session is being continued from a previous conversation…" followed by the *previous* conversation's whole summary, which is the longest shape in the store and the least useful two lines in it, so those rows say they were continued and stop there. Truncation moved to a **word boundary**, with a floor below which a boundary is not worth honouring — a path, url or hash has its only space near the front, and cutting back to it would throw the line away rather than shorten it. The existing `-webkit-line-clamp: 2` on `.session-row-preview` is now the *second* cut rather than the only one. Checked against every transcript in the store: no derived preview carries a leftover tag.
- **`CHANGELOG.md` can no longer conflict, because the repo now has a `.gitattributes` that tells git to keep both sides** — 93 of the commits since July touched this file and every one of them *prepended*, so any two branches in flight edited the same first lines and the three-way merge conflicted every single time, in the identical place, over no disagreement at all: both sides were adding, neither was changing what the other wrote. The previous answer to that was prose telling sessions how to resolve it, which cannot work — prose does not stop two branches from editing the same line, and the pattern recurred in windows recorded entirely after it landed. `CHANGELOG.md merge=union` removes the affordance instead: git takes both sides' added lines and the merge completes with nothing to resolve. It is safe **because of what this file's format already is** — one bullet per entry on its own line, `### Added` / `### Changed` / `### Fixed` headings that already repeat down the file, and a single `## [Unreleased]` release heading, so there is no per-release ordering for an interleave to get wrong. Proven rather than assumed: two throwaway branches each prepending an entry conflict without the attribute and merge clean with both entries present under it. The line is **scoped to this one file** — "keep both sides" is a silent wrong answer in code — and both `.gitattributes` and the repository map in `AGENTS.md` say why it is there, so a later reader does not tidy it away.

- **The dashboard's stylesheet became a governed cascade of per-component files, and its size rules now ask the box around a component rather than the window** — `apps/admin/src/styles.css` was 4,735 lines in one file, which made two things true at once: a rule won because of the line it sat on, so the file could not be split without changing what rendered, and every width decision in it was a `@media` query about the viewport. The viewport is the wrong question here. The dashboard puts a rail beside its content that is 244px wide, or 64px collapsed, or a drawer at zero, so the same window width gives the content column three different sizes — and a card inside a `.grid.two` halves it again. **CHANGELOG 29 and 95 record what that costs**: the same bug, a table held open past the card around it, fixed twice months apart and both times per page, because a viewport query cannot tell the Context table at ~1,100px of card from the same table at ~420px in half a grid. **A `@layer tokens, base, layout, components` order declared once** fixes precedence independently of source order, and the order was chosen to match the file's existing shape so every rule that already won still wins — which is the property that made the split safe, and the split was verified rule-for-rule against the original before anything else changed. The sheet is now an entry file of `@import`s over 26 partials. **Two size containers are named** — `workspace` on the content column, `card` on the card — and components ask those. The cramped-table rule consequently lives once, in the table's own file, where the next page inherits it instead of rediscovering it; tightening its gutters there is load-bearing rather than cosmetic, since cell padding is part of a column's intrinsic minimum and 10px to 6px takes roughly 8px off every column. Thresholds were **re-derived, not renamed**: a container is narrower than the window by the rail plus padding, so 861px of window is about 600px of column. Two breakpoints were **deleted outright** rather than converted, `auto-fit` with a `minmax` floor working the column count out from the space the grid was given. `.content--full` opts out with `container-type: normal` because the live graph pans its own canvas, and the **app shell's own 860px boundary deliberately stays a viewport query** — whether there is room for a rail beside the content genuinely is a question about the window. Separately, **six `prefers-reduced-motion` blocks collapse to one**. Four were redundant against a blanket `* { animation: none !important }` that outranked everything; removing that blanket was only safe because every one of the 34 motion sites now reads `--motion-duration`, with the slow and looping rates as `calc()` multiples of it so they all zero from the single base. The two blocks that were **not** duration concerns keep their own tokens: `--motion-scroll`, since `scroll-behavior: smooth` is motion the reader did not ask for, and `--skeleton-fill`, since the shimmer is a moving background and a stopped clock would freeze its sweep mid-stroke rather than flatten it.

### Added

- **The bare `button`, `select` and `input` are styled once in the base layer, so a control used somewhere new inherits the dashboard instead of arriving as browser chrome** — the sheet styled the controls it had named, `.segmented button` and `select.chat-permission` among them, and left every other one at the platform default: `base.css` reached a bare button for `focus-visible` alone, with no background, border, radius, type or disabled treatment behind it. The consequence was visible on the running dashboard rather than theoretical — the idea detail page's Area picker was a native white select and its comment box a white-bordered textarea sitting inside a designed card, and the ledger's `Release` button was a grey platform bevel in the platform's own font. A control's appearance was settled where it was *used*, so every new one started from zero. The reset therefore lives in **`@layer base`**, and that placement is the whole safety argument: a base rule loses to every rule in `@layer components` by **layer order rather than specificity**, so a component that already declares a property keeps rendering exactly as it did, no matter how weak its selector. Above the floor sit **three named classes for the three jobs the dashboard actually has** — `.btn-primary` for an action, `.btn-quiet` for a disclosure or a secondary, and `.select-field` for a select — in one new partial, `styles/components/control.css`, imported first among the components so a component file that names the same control still wins. `.select-field` is a **wrapper**, not a class on the `<select>`, and that is the point of it: `appearance: none` removes the platform's disclosure arrow, an arrowless select reads as a text field, and the arrow can only be drawn back as a background image on something that is not the control itself. Checkboxes and radios are excluded outright — a surface is not a substitute for the native box, and giving them one leaves nothing that reads as checked. Every size in the new CSS is a step of the scale rather than a number, which the `no-bare-size` GritQL rule enforces on the way through `biome check`.

- **The safety claim was measured rather than asserted, and the two places where it does not hold were fixed rather than argued away** — layer order only protects a property a component **actually declares**, and a differential of `getComputedStyle` over every `button`, `select`, `input` and `textarea` on six pages, captured before and after, is what turned that caveat into a list. It found two leaks. `line-height` was dropped from the reset outright: almost no component declares one, so setting it retimed the height of every existing control by a pixel or two — the browser's own `normal` is what they are all sized against today, so that is what they keep. And `.segmented button` never named a `border-radius`, so it inherited the floor's; the segment is square by design, the group above it draws the radius and clips to it, and that rule now says `border-radius: 0` out loud. With both in place all **14 `.segmented` instances across Overview and Trends are identical** on every property measured, and the only differences left anywhere are `font-family` on controls that never named a face — which is the defect being fixed, not a regression. **The composer stopped colliding with its own hint** on the way past: `.prompt-input-options` carried `min-width: 0`, so it shrank past its own contents and the permission select overlapped the "Enter to send" line instead of moving it; the toolbar wraps now and the options row will not shrink below `min-content`, so the hint drops beneath the control rather than under it.

- **The chat reply and the tools the turn runs stream into the page as one interleaved account, and the finished reply is still the record** — a dashboard chat turn showed a three-dot wait and nothing else until it completed, which for an agent turn is minutes or hours of a page that cannot say whether anything is happening. Both transports were *already* decoding a stream that interleaves the reply's text with the turn's `tool_use` and `tool_result` blocks and then throwing the ordering away at the end, so the fix is to re-emit that same interleaving rather than to invent a second one: `CliLiveReader` reads the headless child's `stream-json` stdout as it lands (a `StringDecoder` and a held partial line, because chunk boundaries fall mid-character and mid-line), `readStreamedBody` reads `/v1/messages` SSE the same way, and both feed one per-session bus that goes out over the dashboard's existing `serveSse` plumbing on `GET /api/chat/stream?sessionId=`. **`serveSse` grew a second kind of source to carry it** — it had only ever tailed a file path, and this one is pushed — so the stream descriptor is now a watch-source or a push-source and there is no second SSE writer to drift. The bubble appends text as it arrives and appends a chip per tool **in the order the turn actually ran them**, which is what turns the chips from a post-hoc summary into a live account; the composer's summary row hides while a turn is in flight, since it holds the *previous* turn's chips and two rows at once read as one list.
- **That stream is an accessory, and the design says so at every point it could have become load-bearing** — `ChatSendResult` is still decoded from the whole stream whether or not anyone watched, and the browser replaces the live bubble with it when the POST resolves, so **a dropped stream re-reads the finished reply rather than leaving a half-written one on screen**. That is what buys the absence of a retry policy: there is nothing beyond `EventSource`'s own reconnect, which is answered with a snapshot of the live buffer, and a stream that never connects at all is indistinguishable from the wait it replaced. Buffers are keyed by session id in a map **independent of the session map**, because the dashboard names its session id before turn one and opens the stream in the same tick as the POST — a reader routinely asks for a session the server has not heard of yet, and answering that with a 404 would have made the race a bug instead of a non-event. A turn that outruns the 4,000-event replay keeps streaming and only the replay is trimmed, with `truncated` on the frame, since a reader silently shown a reply with a hole in it is worse than one told there is one. The route is **origin-checked like the write routes rather than open like the other reads** — every other read route serves `access-control-allow-origin: *`, and this one carries chat content.
- **The `role='status'` region moves onto the streaming bubble instead of being deleted with the wait span it replaces** — that span was the turn's only announcement, so removing it would have traded a silent page for a silent screen reader. It carries a short, low-churn sentence ("Reply arriving — 3 tools run so far"), and the streamed prose and chips are `aria-hidden`: a live region over streaming markdown re-announces a half-written document on every append, which is noise rather than access, and the finished bubble underneath is the artifact worth reading. A chip whose `tool_result` has not come back pulses, new chips fade in, and a caret trails the text while it is arriving — all three dropped under `prefers-reduced-motion`, the same opt-out the existing wait animation carries.

- **The Overview's live badge and day picker are one component, the Trends page renders that same one, and the two plots below it can leave the page's window without leaving the page** — the pair had been assembled twice: the Overview built `.pagehead-controls` around a `LiveIndicator` and a `Segmented`, and the Trends page built the switcher again on its own, so the two heads could drift and only one of them ever said whether the stream was up. `DayWindowControls` is now the single definition and both pages call it; `live` is optional so a page with no stream behind it still gets the picker. Under it, **Cost per token** and **Tokens per request** each carry their own `Page | 7d | 14d | 30d` switcher. **`Page` is the default and is a real state, not the label on 7d** — a card that has not been touched follows whatever the head is set to, and `Page` is how it goes back to following after it has been pinned, which a plain window list could not express. Each card fetches under **`['trends', days]`, the key the page head's own query already uses**, so a following card costs no extra request and a card pinned to the window the page happens to be on shares its cache entry too — the cards stopped taking a `digests` prop and read their own window instead, which is what lets one plot sit at 30d while the other stays at the page's 7d. The Trends page picked up the same live splice on the way: it subscribes to `/api/summary/stream` like the Overview, so today's partial day moves in the blend as it is captured, and its new **Live** badge reports a stream that is genuinely feeding the page rather than decorating it.
- **The Pull requests page can move `main` across the commits merged PRs landed, and nothing is ever destroyed doing it** — a merged PR's landing commit (`gh`'s `mergeCommit`, a squash commit here and a true merge commit in the early history) is now a **position**, and clicking any trunk node offers **Set main here**, forwards or back, which force-pushes `refs/heads/main` to it. The entire safety property is **one rule enforced at slide time**: before `main` leaves a commit, that commit must be reachable from some `refs/main-history/*` ref, and if it is not it is **pinned first** and that push confirmed before `main` moves. That is sufficient rather than merely careful — GitHub's own merges only ever *append* to `main`, so a slide from this page is the only thing in the system that can strand a commit — and it is why there is **no journal and no bookkeeping**: the invariant is checked against the refs themselves at the one moment it can be violated. It is checked against the refs **`origin` actually has**, read with `git ls-remote` rather than out of the local ref store, because a sync leaves local-only refs behind that would otherwise vouch for a commit `origin` reaches from nothing. Pins are **content-addressed**, `refs/main-history/<short-sha>`, so two devices pinning the same commit write the same ref with the same value and pinning is idempotent and race-free, and the namespace keeps them out of GitHub's branch and tag lists entirely. **All shared state is refs on `origin`, never SQLite** — the database is per-device and the several machines this runs on would each hold a different, equally confident account of where `main` has been. **Pins are never deleted**, because deleting the last ref to a line is exactly what would let GitHub collect those commits; a line is *hidden* instead, by a separate `refs/main-history/hidden/<short-sha>` marker, which being a ref means hiding reaches every device rather than one browser. The marker is named for the line's **pin**, not for the row that was clicked, so hiding from a landing commit partway up a line — which is what sliding back more than one position leaves — hides that line instead of writing a marker no pin matches. Authorization is the device's own `gh` identity — `gh api user` over **REST, because `gh`'s GraphQL-backed calls resolve to an account that is not a collaborator on these repos**, checked against `MAIN_HISTORY_ALLOWED_LOGINS` — with the limitation stated rather than papered over: a local process sharing this device's token passes. The move itself is `--force-with-lease=refs/heads/main:<the sha the page displayed>`, so a page that went stale between render and click is rejected by GitHub atomically instead of by a check here that could race. Reads ride the existing 60s `gh` cache and touch the **ref store only** — never the index, never a worktree.
- **A rail that is drawn from real ancestry, and a local checkout that can actually follow `main` backwards** — lane layout is computed **server-side**, because only the ref store knows the commit graph, and shipped with the rows; `packages/core/src/main-history.ts` stays a pure function of a graph, a set of positions and a set of refs, unit-tested on its own. `main` is a straight vertical rail running off the top of the frame with a persistent **main →** marker on its position, and each pinned line **kinks off at its divergence point exactly once** and then runs vertically in its own lane — the git-graph idiom, constant width, no diagonal spaghetti. On this side of the wire, a plain `git pull` **will not** follow `main` backwards: the older commit is an ancestor of the local branch, so pull says "Already up to date" and quietly keeps the newer one, which is the failure mode that makes a sync button necessary rather than convenient. The page detects the divergence and computes **every refusal before drawing the button**, rather than discovering it on the press — hard-refusing on an in-progress merge/rebase/cherry-pick/revert/bisect, on `main` being checked out in another worktree (named in the refusal), and on unpushed local commits that no pin reaches, the last of which offers an explicit **preserve and proceed** that saves them to `refs/main-history/local-orphan/<ts>` first. The pre-reset position is **always** recorded as a ref, and that ref is **local** — a way back on this device, said so in the response and on the page, rather than a pin `origin` knows about — and when `main` is the checked-out branch the work in progress is stashed (`--include-untracked`, deliberately not `--all`) with the **stash commit sha surfaced in the response and in the UI**, so a fumbled `stash drop` is recoverable. The git plumbing is integration-tested against a temporary bare repo and clones in a tmpdir — no network and no credentials — asserting that orphaned commits stay fetchable from a fresh clone after a slide, that `--force-with-lease` rejects a stale expected sha, and that each preflight refusal fires.
- **Saving the device system prompt shows you the write first, and refuses one aimed at a file it has not seen** — `/system-prompt` is the dashboard's one write over authored text a human cannot reconstruct, and until now `Save` was blind: it replaced `~/.claude/CLAUDE.md` and left you to work out afterwards, from a one-deep `.bak`, what had gone. `Save` no longer writes. It **re-reads the file** and swaps the editor for a **line diff of the draft against the bytes on disk at that moment** — not the bytes the page loaded with, which on a tab left open for an afternoon is the wrong comparison and the one that hides the problem. The diff renders through the dashboard's existing **`CodeBlock`**, so it inherits the shared code styling and the repo takes on **no diff dependency**; `CodeBlock` gains one optional `lineClass` hook so a caller can tint whole lines, and `diffSystemPromptText` in `packages/core` supplies `@@` hunk headers, three lines of context either side of each change, and add/remove counts. It trims the matching head and tail before aligning anything — a long instruction file usually changes in one place — and past a cell ceiling stops aligning and calls the change a whole-file replacement, which at that size is what it is. **The concurrent-edit check is that same read, not a second feature**: the confirm-time mtime either still matches the one editing began from or it does not, and when it does not the step says the file changed underneath *and the diff already on screen is against the new contents*, so "what would I have lost" is answered where it is asked rather than in a terminal. A bare refusal would have sent the reader looking. The refusal is real and not only cosmetic: `POST /api/system-prompt` takes an optional **`expectedModified`** and answers **409** when the file no longer carries it, checked before `writeSystemPromptFile` is reached, so a change arriving *while the diff is on screen* is still caught; omitting the field writes regardless, and `null` means "there was no file". No new route, and **no rotating-backup history directory** — the `.bak` was one deep because the save was blind, and a save you read before committing to needs it far less.
- **The wordmark is the way home to Overview, and it is on the narrow top bar too** — `claude·proxy` sat in the rail's head as two inert `<span>`s, so the one mark every page carries was the only piece of chrome that went nowhere, and the convention every other dashboard trains a reader in — click the logo, land on the front page — quietly failed here. It is now a `Link` to `/`, and clicking it **while already on Overview** scrolls back to the top and closes the drawer rather than re-navigating, which is exactly what a lit station already does, so the mark and the station it duplicates behave the same. The narrow breakpoint is where this mattered most and had nothing at all: below 860px the rail becomes an off-canvas drawer and `.rail-head` is hidden outright, so the wordmark disappeared and the top bar carried a hamburger against empty space. A second copy now sits at the **far right of that top bar**, opposite the drawer toggle (`margin-left: auto`), which is the one place it cannot be mistaken for the toggle and cannot be reached by a thumb aiming for it. Both copies are the same component rather than two markups that could drift, and both are one link with an `aria-label` naming the destination, so the node and the wordmark are a single target rather than two adjacent ones.

### Added

- **The concept corpus became a hosted service that agents can query, because a file on one laptop was reachable by nobody else and by nothing at all** — `/teach` wrote to `logs/concepts.jsonl` in whichever checkout the machine had, so concepts taught at work were invisible at home, and on a machine where `CLAUDE_PROXY_STORE` was unset the command still produced its sentence and silently saved nothing. Meanwhile the corpus was the one body of knowledge here that no agent could read: `okq` gives agents ranked search over `docs/`, and the thing the user has actually been teaching themselves had no equivalent. `services/concepts` is a fifth workspace package — a Cloudflare Worker over **D1**, serving the same data as REST and as **MCP** at `POST /mcp` with three tools (`concepts_list` returns the whole glossary compactly, `concepts_get` and `concepts_search` return the prose, and every one of them accepts the `field`/`skill`/`since`/`hasNotes` filters plus facet counts so an agent can discover what those filters accept). D1 was chosen **because it is SQLite**: FTS5 supplies the same `bm25()` ranking `okq` gets from Tantivy, and it lets the tests drive the production SQL — the same `migrations/0001_init.sql`, the same virtual table, the same ranking function — through `node:sqlite` in memory, so all 44 of them run with no Cloudflare account and no network. Nothing is mocked, and there is no second implementation of the schema to drift. `@claude-proxy/core` is imported rather than duplicated, which works only because it has zero runtime dependencies and so runs on workerd unchanged.
- **The store is append-only and its ids are derived rather than random, which is what makes both a replayed write and a full restore free** — re-teaching a term inserts a *version* instead of overwriting one, and reads resolve newest-per-term (case- and whitespace-insensitively, so `Carousel` supersedes `carousel`) unless a caller asks for `includeSuperseded`; how an understanding changed is data, not noise. A row id is a ULID whose timestamp half comes from `savedAt` and whose remaining 80 bits are a hash of the record itself, so ids sort chronologically, `POST`ing the same concept twice is idempotent with no dedupe pass, and an export followed by an import reproduces every id exactly — which is the property that turns the nightly backup into a real restore. The full record is also stored verbatim in a `document` column, because the columns beside it cannot express "never recorded" as against "recorded empty" and the detail view depends on the difference. **[ADR 0005](docs/adrs/0005-host-the-concept-store.md) records what this costs**: ADR 0004 says files are truth and the database is disposable, and for concepts that is deliberately broken, paid for by a cron trigger that commits the whole corpus as JSONL to a private repo daily — comparing git blob shas so an unchanged day makes no commit — in the same format the toolchain already reads. Worst case is one day. The ADR also records the single `CONCEPTS_TOKEN` (a read-only second token became fiction the moment orbs needed to write, and two tokens with identical reach is bookkeeping wearing the costume of a boundary), and why MCP is hand-rolled rather than taking the SDK into the request path of the only always-on component in the system. The repo's **first GitHub Actions workflow** deploys it on merge, running migrations before the deploy and smoke-checking `/health` — the one unauthenticated route, which is what lets CI verify a deploy without being handed the corpus token. **This ships additively**: `/teach` still writes the local file, and retiring it is a later, deliberately sequenced step, because deleting it before every device has the updated command would silently drop concepts.
- **Every idea is filed under an area, and the ledger is read one area at a time** — the ledger was one flat list, so a UI polish item and an infrastructure change sat side by side awaiting the same sign-off, and "is this worth building" does not read the same for both. `IdeaEntry` now carries an **`area`**: kebab-case, shape-validated exactly as the slug is, and otherwise free text. It is **required by `parseIdeaAdds`** — refused precisely as an entry citing no evidence is refused — and **tolerated absent by `parseIdeasStore`**, which is the load-bearing half of the migration: rows written before areas existed keep loading, because dropping them would lose their **rejection reasons**, and those reasons are what stop a rejected idea being re-proposed. Legacy rows read as **Unfiled** and are classified with the new `ideas file` verb. `SEED_IDEA_AREAS` names `ui-ux`, `infrastructure`, `code-quality`, `services` and `commands` with display labels, and is **advisory only** — it orders and labels the tabs and appears in the CLI's help and in the refusal an unparseable area produces, while nothing anywhere enforces membership, because an agent with a genuinely new area must be able to open one. Fragmentation is handled the way near-duplicate slugs already were, by **surfacing rather than refusing**: `similarAreas` matches shared tokens *and* prefixes — the fragmentations worth catching are abbreviations (`infra` for `infrastructure`), which share no whole token with what they abbreviate — and `ideas add` reports the hits while still landing the entry.
- **`commands` is the one area the pure core knows the meaning of, because of a fifth evidence source that carries no locator** — `command-gap` is the citation for a command that was never written, and there is no file to point at, which is the entire condition it describes. Two containment rules are enforced at the parse boundary: a `command-gap` citation may appear **only** on an idea whose area is `commands`, and it is the **only** source that may stand alone. Re-filing is checked too, since it is the only other way to reach the state the parse forbids — `applyIdeaFilings` refuses over the **whole batch before writing anything**, rather than half-applying and then throwing. The trade-off is stated rather than hidden: a locator-less `command-gap` is the one citation a reader cannot go and check, and confining it to `commands` is the price of admitting it at all. Beside it, `comment` is a new field that is deliberately **not** `note` — `note` keeps its exact meaning (the rejection reason, or the shipped PR url) while `comment` is a person's own words, the build criteria whoever implements the idea should read, replaced on each save rather than appended and cleared by an empty one.
- **Filing is its own verb, because a status change must not move an idea between tabs as a side effect** — `ideas file --slug --area` is deliberately not folded into `mark`, and `ideas note --slug --text` writes the comment; both leave everything else on the entry exactly where it was, so re-filing a rejected idea keeps the rejection and its reason. `ideas list` gains `--area`, and `--help` lists the seed areas. Cards stay fully actionable — nothing was moved off them. `/ideas/$slug` carries the full rationale, every citation with its quote, the claim holder and how long it has been held, the `by` provenance, the re-file picker and the comment editor; **the area is absent from the permalink on purpose**, since re-filing is normal and a link that breaks when somebody corrects a misfile is worse than a less descriptive url. The drawer also lists **the sessions that touched that PR**: nothing records that link, so it is recovered from the transcripts — a session that built a PR names its branch throughout (including the slash-flattened `feat-x` spelling a worktree directory uses), and one that reviewed or merged it names the number as `#14` or a `/pull/14` url. Each match says which of the two signals it came from, so a coincidental `#14` reads as the weak evidence it is, and the drawer states plainly that transcripts hold roughly today only — an empty list means no transcript on record, not that nobody worked on it. Parsing is defensive throughout (`gh` gains fields between versions), a row with no number is dropped, and the page polls every 30s so a PR merged elsewhere appears on its own.
- **The station for the page already on screen rides back to the top instead of doing nothing** — clicking the lit station in the side rail was a no-op: the router resolves a navigation to the location it is already on and neither moves nor scrolls, so the one control a reader reaches for after scrolling to the bottom of a long page did nothing at all. It now smooth-scrolls the document to the top. Three deliberate limits. The check is **exact pathname equality, not the station's lit state** — `/trends` stays lit under `/trends/$metric` and must still navigate *there*, so keying on the active styling would have broken backing out of every drill-down. A **modified click is left alone** (`meta`/`ctrl`/`shift`/`alt`), because that click is opening a tab rather than navigating here, and swallowing it would be the more annoying regression. And it **closes the nav drawer** on a narrow viewport, since the drawer covers the page it just scrolled and the reader would otherwise watch nothing happen — the one place this feature is invisible without it. Motion honours `prefers-reduced-motion`, jumping rather than animating.
- **The Context size table is searchable by what was actually asked for, which is the one thing a request's own record never held** — the "Requests" table could be sorted six ways and none of them answered "which run was this?", because an audit sidecar records *who* sent a request (`sessionId`, `threadId`) and never *what for*. The prompt text does exist, but the two obvious sources are both wrong: the request body's first message is the whole wire payload — system prompt, `<system-reminder>` blocks carrying `AGENTS.md`/`CLAUDE.md`/memory, and for a slash command the entire inlined definition — so searching it matches every `/task` run on boilerplate none of them typed, and the transcript's `- subtitle:` is `gist(root, 200)`, truncated at exactly the length where a criteria line gets interesting. So the search reads the **untruncated** opening prompt — `logs/sessions/<threadId>.state.json`'s `root` on the file backing, `session.root_prompt` on the SQLite one — and reduces it with `userPromptText` in `packages/core`: reminders stripped (including one a truncated prompt left unclosed), and for an envelope **the command name plus its `<command-args>` and nothing after**, so `/task Add full-text search to the Context Size page` is the searchable text and the four hundred lines of pipeline definition behind it are not. Matching is case-insensitive, every whitespace-separated term must appear in any order, and `"a phrase"` in double quotes matches whole; a matching row shows an excerpt windowed on the first term rather than the prompt's opening words, which for a `/task` are the same on every run.
- **The lookup keys on thread id and is bounded to the window, both of which are the seam's constraints rather than conveniences** — `readRootPrompts(logDir, threadIds)` joins `SidecarSource` ([ADR 0004](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md)) as a method that **names the threads it wants**, because a window holds a handful while the corpus is megabytes of prompt text, and the SQL side chunks its `IN (…)` at 500 binds so a wide window cannot hit SQLite's parameter ceiling. It keys on **thread id, never session id**: a session id spans an agent together with its subagents, so keying on it would caption a subagent's 190k-token request with whatever its parent was asked — precisely the misattribution the sidecar's `threadId` was added to fix. Filtering itself stays **client-side** over entries the page already has, so typing narrows instantly and never refetches, and `/api/context` gains one nullable `prompt` field that both backings fill identically. A thread that recorded no opening prompt is `null` and **never matches**, including on an empty query's pass-through — the caption says how many prompts are searchable so a short list reads as missing data rather than as no results.
- **A spawned branch says whether it is still running, so a lost dispatch is not read as a dead one** — when a `/task` dispatch's tool result came back as a harness error, nothing in the repo could say whether that agent was gone or simply mid-step. It was fine, and still working twenty-six minutes later; the parent reported the outcome as unknown and stalled rather than risk a duplicate worktree and a duplicate PR. Ground truth was already on disk — the branch's transcript was still being appended to — so this turns it into a verdict. Every branch now carries a **`liveness`** of `running`, `quiet`, `finished` or `unknown`, derived from when its transcript was last written and whether it ended on an outcome. The verdict is **derived, never reported**, which is the whole point: an agent that crashed cannot self-report, and one whose result the harness ate never got the chance, so nothing here asks the branch anything. **`quiet` deliberately does not mean dead** — a branch sitting on a full `verify` or a cold install appends nothing for minutes and looks identical to one that died, so the threshold (`QUIET_AFTER_MS`, ten minutes, sized to one long tool call) is **reported in every payload** rather than assumed, and the state's own wording says "busy or stalled, not known to be dead". It shows up in three places: `/api/sessions/graph` carries it per branch and the graph rail draws it beside the existing **in flight** marker — the two together are what distinguish an eaten result (in flight *and* running) from a real death; the **Jobs** page joins each job's session to the transcripts it wrote and shows the family rolled up, where **one live branch makes the job live** and a job matching no transcript reads `unknown` rather than `finished`, next to a new **Live** tile that is deliberately distinct from **Running** (a job that died mid-write claims `working` forever, because `state.json` is the job's own claim and freezes when it stops); and a new **`GET /api/sessions/liveness`** answers the same question without the node streams, so a stalled dispatcher can ask from a terminal — `curl -s localhost:8787/api/sessions/liveness | jq '.threads[] | select(.liveness.state != "finished")'`. **Resuming or killing anything is explicitly out of scope** — this is a read and stays one. The verdict is a **pure function with `now` passed in**, and every builder threads a single `now` into both backings, so the file- and SQLite-backed sources stay byte-identical and a clock tick cannot masquerade as a parity mismatch. Verified by `packages/core/test/liveness.test.ts` and `server/test/sessions-liveness.test.ts`, plus the existing parity suite over the real archive.

- **An idea is claimed at the start of work, because `accepted` and `shipped` were eleven minutes apart and two runs walked into the gap** — the ledger's status machine had nothing between "a human signed this off" and "the work landed", and the implementing run stamped `shipped` at *PR-open* time. So from the moment a run picked an idea up to the moment its PR existed, the entry still read `accepted` — which is the one status an implementing run looks for, and therefore still on offer. That is not hypothetical: PRs #139 and #140 both implemented `archive-aware-window-reader` against the same accepted entry, opened eleven minutes apart, and one of them was closed unmerged. **`claimed` is stamped first, before any code is written**, which compresses the window from the length of an implementation to the width of one read-modify-write, and `shipped` goes back to meaning the work actually landed. The claim carries a holder — `{ by, at, pr? }`, where `by` is a branch, a run id or a person, whatever a second run can read and recognise as not itself — because "taken" with no name attached tells the second run nothing about whether to wait or move on. Only `accepted` may be claimed, or a `claimed` entry that is stale or already yours; **`proposed` is refused**, so claiming cannot route around the human sign-off that is the entire point of `accepted`. Refusals are returned rather than thrown, so a batch claiming three ideas still takes the two that were free, and `ideas claim` exits non-zero on a refusal so a scripted run walks away instead of reading a zero exit as permission.
- **A dead run's claim expires on a clock nobody has to run, and a claim with a PR never expires at all** — the stale-claim question has two plausible answers and only one of them survives the failure it has to handle. An **explicit release** is cleaner to reason about and fails exactly when it matters: a run that dies cannot release its own claim, so the idea is locked forever by a process that no longer exists, and nobody would ever go and unstick it by hand — a worse outcome than the duplicate work the claim was added to prevent. So the rule is an **age-based expiry**, six hours, and it is computed at read time from the `at` already on the entry: no heartbeat, no liveness protocol, no background sweeper, and no write at all when a claim lapses. **The escape hatch is what makes a TTL that short safe: a claim carrying a `pr` is never stale, however old.** An open PR is live evidence the work exists, and expiring one would invite precisely the duplicate implementation this state exists to stop — which matters because the long part of an idea's life is PR *review*, not writing. An unparseable `at` reads as stale, since the alternative is a malformed row locking an idea permanently, and a claim with no readable holder is dropped at the parse boundary while the idea itself survives — losing the entry to a bad holder field would be the larger loss. Beside the expiry there is still an explicit release: **`ideas mark -s accepted` frees an idea immediately** for a run that gives up early. Every mark but `shipped` drops the claim; `shipped` keeps it, because there the claim is the record of who built the thing.
- **`ideas list --available` exists because "signed off" and "available" stopped being the same question** — a run listing `-s accepted` alone never recovers an idea abandoned by a run that died, since the entry sits at `claimed` forever, invisible to the only query that looks for work; a run listing `-s accepted,claimed` happily takes one out from under a live holder. `--available` is `accepted` plus any `claimed` entry whose claim has expired, with staleness read at query time, and the test pins both wrong answers alongside the right one so neither shortcut comes back. In the dashboard `claimed` is a fifth badge and the card names its holder and start time — that is the answer to "why has nothing happened to this one" — but **`claimed` is not settable from a browser**, and for a different reason than `shipped` is not: it is not a decision a person makes, it is a machine registering that it has started building, and a button would park an idea for the whole expiry under a holder nobody can find. **Releasing** one from there *is* allowed and is `accepted`, so a human can free an idea from a run that hung without waiting the six hours out. **One thing this does not finish, stated plainly: `/ideate` and `/improve` are user-level command files on the device, not files in this repo.** The mechanism is complete and usable, but an implementing run only stops colliding once its command file claims as its first step and reads `--available` in place of `-s accepted` — a change that has to be made where those files actually live.
- **A verdict now records who judged the window and how much of it they actually opened** — a verdict is an agent's product and nothing checked that the agent did the work. `--amnesty` existed precisely to make a no-notes verdict *explicit*, yet an ordinary `judge` call was trusted identically, and the ideas ledger had the same hole from the other side: nothing recorded who accepted an idea. `packages/core/src/provenance.ts` is the envelope **both** write paths now attach — `WriteProvenance {thread, window?, opened?}` on `SuggestionJudgement` and on `IdeaEntry` alike, so "which agent decided this" is one shape across two stores rather than two near-misses. The *who* is a claim the caller makes: `suggestions judge --thread <id>` and `ideas mark --thread <id>`, no new instrumentation beyond a run passing its own thread id through. The *how much* is **not asked for** — a judging run is itself a session the proxy transcribes, so `transcriptsOpened` reads that thread's own tool calls back off `logs/sessions/<threadId>.md` and matches them against the window's thread ids, preferring the untruncated `.nodes.jsonl` sidecar text so a long path clipped at capture still counts. **Any tool naming a transcript counts, not only `Read`**: the question is whether the judge looked at the evidence, and a `Bash` grep opened it just as a `Read` did. A judge is never credited for its own transcript being in its own window, and an agent that names a thread it did not run gets an honest zero.
- **A thin-pass marker on the Advice page and in `suggestions buckets`, advisory in both** — under **30%** of a window's transcripts opened, the bucket's verdict is badged `Thin pass 2/10` beside the existing judgement badge and printed as `THIN` by the CLI. Two design calls the idea left open, stated rather than made silently: the threshold is set **low on purpose** — it catches the pass that read *almost nothing* instead of prescribing how much reading a careful verdict takes, since a sound verdict can come off three transcripts when the rule only fired in three — and the marker surfaces in **both** surfaces rather than the dashboard alone, because the judging agent is a CLI caller and a marker it cannot see cannot correct it. It never refuses, hides, or downgrades a write. **Everything is additive and every field optional**: an existing verdict or idea row with no envelope loads exactly as before, an unparseable envelope is dropped while the row underneath survives, and `isThinPass` is false for absent or unmeasurable provenance — an *unattributed* verdict is a different thing from a careless one, and inferring carelessness from a legacy row would indict every verdict written before this existed. Closes an open question in each of `docs/features/session-suggestions.md` and `docs/features/ideas-ledger.md`.
- **The proxy writes down the three join keys it already knew at capture time, instead of leaving every consumer to re-infer them wrongly** — the proxy computes `threadIdFor(sessionId, messages)` to *name* the transcript it is writing, watches the `tool_use` block that starts a child thread go past, and holds each tool call's whole argument object in memory. It then wrote none of that down, so three separate consumers guessed at it and three separate open questions recorded the guesses failing. Each payload is a **replacement** for an inference, not an addition beside it. **(a)** The audit sidecar's `session` block carries `threadId`, and `sessionContextPeak`/`sessionContextEntries` take an exact thread match over the session-wide one — a session id covers the main agent, its subagents and one-shot helpers, so a thread's "Peak context" tile could previously be showing a subagent's request. **(b)** A `tool_use` carrying a non-empty `prompt` is a spawn, and the child transcript gets `- parent:` / `- spawn:` / `- agent:` header lines naming the spawning thread, the node index of the call, and the agent type. Detection keys on the **argument, not the tool's name**, so the old `Agent`/`Task` allow-list no longer bounds what counts as a spawn, and the agent type comes off the call's full input rather than the one truncated argument the display line kept. **(c)** `argsHash` — `sha256(name + "\n" + key-sorted JSON of the input)`, first 16 hex — rides in the `.nodes.jsonl` row beside the truncated display signature.
- **`redundantReads` keys on the hash, which is what stops it firing on sessions that never re-read anything** — a judge verdict on bucket 42 confirmed the rule was reporting duplicates that did not exist: every `Read` under a `.claude/worktrees/<long-branch>/…` path truncates to the same 60 rendered characters, so a session reading a dozen distinct files under one worktree collapsed into a single key and tripped the threshold. The rule now reads `node.argsHash ?? node.tool`, and the fallback is the whole legacy story — a transcript written before the field has no hashes and behaves exactly as it did.
- **Spawn pairing is bidirectional and the leftovers are labelled as guesses** — a blocking spawn's `tool_use` block only reaches the wire in the parent's *next* request, after the child has already run, so the child usually exists before the spawn is observed; a backgrounded one arrives the other way round. The registry mirrors the mechanism already used for out-of-band titles: `recordSpawn` links an unparented thread whose root matches (most recently seen wins) and appends the header lines to a transcript already flushed, otherwise it parks the record for `claimSpawn` to drain at the child's first sighting. `linkAgentSessions` applies every recorded pairing first — validating that the named parent exists, is not the child itself, and is not one of its own descendants — then runs the old per-family start-time pass over what is left, and flags every link that pass makes `inferred: true`. That field answers the graph's standing open question directly: nothing in the payload used to mark a pairing as uncertain, and a parallel fan-out is exactly where the positional guess goes wrong. Children are ordered by spawn index rather than by start time, so the recorded order is the one the canvas draws.
- **Legacy transcripts keep working, and that is the tested path rather than the assumed one** — the migration is the usual one: sidecars and transcripts written before these fields lack them and take the inferred route, exactly as `isAuditSidecar` already tolerates a missing `session` block. `threadId` is **omitted rather than nulled** when there is no root to hash, on both the file side and the SQLite rebuild, so the two sources still serialize byte-identically — the parity suite covers a request that carries the key and one that does not, and a session family with one recorded child beside one inferred one. Substrate slice 12 adds `request.thread_id` (indexed), `session_node.args_hash`, and `session.parent_thread_id` / `spawn_index` / `spawn_agent_type`, and resets the ingest watermark so existing rows self-heal on the next pass instead of keeping their nulls.
- **A point on a trend chart can be pinned, so the tooltip compares days instead of reporting one** — hovering `/trends/$metric` showed a single day, which made comparing two of them a matter of memorising a figure and hovering again; the chart plotted the comparison and then refused to state it. Clicking a point now pins it into the tooltip as a list. **The hovered point always heads that list**, with pinned days beneath it in click order, each carrying its delta against the hovered one — so the baseline is whatever the pointer is on and moving the pointer re-reads every pin against the new one. Hovering a day that is already pinned **promotes it to the head rather than listing it twice**, and a pin whose day falls out of the window when the range switches is simply absent rather than rendered empty. The delta is **deliberately uncoloured**: the chart is not told whether up is a win for the metric it is plotting, and a green or red here would be asserting one. A pinned point is drawn on the line as a **hollow ring in the series' own colour**, which is load-bearing rather than decorative — the tooltip listing the pins only exists while something is hovered, so without a cue on the line itself the pinned set is invisible the moment the pointer leaves. The card is a flex column **sized to its rows and capped at the plot height**, and only the pin list scrolls, so the hovered figure never leaves the top however many days are pinned. Pinning is **opt-in through a `pinnable` prop and enabled on the detail chart alone**: `SeriesLineChart` has five call sites, and the carousel's panels are each wrapped in a `Link` whose click already navigates, so pinning there would take a click that is spoken for. **Two recharts behaviours had to be worked around, and neither shows up in a typecheck** — `activeDot` renders over the point it marks and swallowed every click, which is *every* click since a point is always hovered before it is clicked (fixed with `pointer-events: none` on the marker), and hovering re-renders the dots, so the node a press landed on is gone before the release and the browser never dispatches a `click` at all (hence `onMouseDown`). The hit target is a transparent 9px disc rather than the 2px visible dot, and carries `role='switch'` with `aria-checked` and Enter/Space handling, so a pin is reachable from the keyboard and reads back its state.
- **`--help` is now a switch the CLIs structurally cannot re-break** — `suggestions judge --help` exited 1 with `[suggestions] missing value for --help`, because each CLI carried its own `parseArgs` in which any `--name` outside a local boolean list consumed the next argv entry; at the end of argv there is nothing to consume, so the one flag every caller tries first was the one flag that could not work. The fix is not another note telling agents to avoid it — that had already been written twice and the failure recurred — but the removal of the affordance: `parseCliArgs` in `packages/core/src/cli-args.ts` is the single parser both `suggestions-cli.ts` and `ideas-cli.ts` now use, and it folds `help` into the boolean set and pins `-h` to it **after** the caller's spec is applied, so a call site cannot alias `h` elsewhere or drop `help` from the standalone set. Help is answered before subcommand dispatch, so `judge --help` answers the same as `--help`. **The `missing value for --X` error is untouched for flags that genuinely take values** — `suggestions list --range` still exits 1 with it, and a test pins that alongside the 20 that drive every subcommand of both CLIs over a real process boundary. Sibling CLIs were audited and needed no change: `chat-cli.ts`, `maintain-cli.ts`, `ingest-cli.ts`, `daily-summary.ts` and `prompt-backfill-cli.ts` read bare positionals or `argv.includes(...)` and never had the shape.
- **One archive-aware window reader sits behind every multi-day builder** — a reporting day near the present is half-archived and half-live, because `REPORT_TZ` and the archiver's UTC rotation do not line up, and each builder composed those two halves by hand or not at all. Eight of them read only `logDir` and so lost a day the moment `pnpm --filter server maintain` moved it: `buildContext`, `buildSkimTrend`, `resolveSessionRequests`, `buildWithheld`, `buildToolSchema`, `buildSessionSuggestionBucket`, `buildSessionGraphNodes`, and `filesForPromptHash`, which carried a fifth open-coded copy of the per-day archive loop. `readWindow(logDir, {sinceDays, archiveDir})` in `server/src/db/source.ts` is now the one composition — archived days oldest-first then the live root, with `byDay`, `archivedDays` and `days` alongside the usual `LoadResult` — and `readSidecars` stays the single-root primitive it always was. An **unbounded span reads the live root only and returns an empty `days`**, rather than guessing a floor. Two deliberate limits: `buildTrends` keeps its existing path, because its `rawArchivedDigest` memo is a *digest*-level cache that `readWindow`'s signature does not cover and routing it through would re-read the whole window on every call; and `archiveDir` stays an explicit option rather than defaulting to `resolveArchiveDir()`, since `<logDir>/archive/` is where `maintain` actually writes and auto-resolving the relocated root would change behaviour for builders that never had it.
- **The command detail page renders the installed command file itself, byte for byte, rather than a reconstruction of it** — the page could say how a command performed and which of its `## Step N` steps a run reached, while the document those steps come from was readable nowhere in the dashboard. Rebuilding a readable version out of the parsed step catalogue was rejected: the catalogue keeps headings and step bodies, so every flag list, every `<!-- include -->` directive and all of the prose between steps would have been silently dropped, and a viewer that quietly omits half the file is worse than none when the file is what you came to read. So `listInstalledCommands` now **keeps the text it was already hashing** — `contentHash(content)` had the bytes in hand and threw them away — and it travels through `buildCommand` to a new `source` field on `CommandResponse`, which is `null` once a command is uninstalled, since at that point only the run store remembers it existed. The card offers the same **Pretty / Raw** pair the memory and file views use: Pretty renders the frontmatter as the existing `.fm` grid above the rendered body, Raw is the exact source in a `<pre>`. A command file runs long, so the card scrolls **internally** rather than pushing the charts below it off the page, and the skeleton reserves its height so nothing jumps when the fetch lands.
- **The shared markdown renderer grew the three things command files actually use, and the frontmatter parser stopped being a copy** — pointing the existing `Markdown` component at a command file exposed exactly what the memory files never exercised. **Nested lists** were rendered flat, which collapses a command's flag lists and sub-bullets into one undifferentiated run: parsing is now two passes, `nest` building a tree off relative indentation (so a two-space file and a four-space file both read) and `renderList` recursing, with a wrapped continuation line folded into the bullet above it rather than becoming a bullet of its own. **HTML comments** are stripped everywhere except inside a fence — in these files they are `<!-- include -->` directives, not prose, and a multi-line one is skipped whole — while fence detection deliberately reads the **raw** line so a comment inside a code block still renders. And **emphasis now re-enters the tokeniser**, because these files put code spans inside bold runs and the old single-pass tokeniser left the backticks literal mid-sentence; that one was invisible to typecheck and to every test, and was found by looking at the rendered page. `splitFrontmatter`/`Frontmatter` moved out of `memory-detail.tsx` into `components/Frontmatter.tsx` so the two pages share one parser instead of drifting.
- **The ideas ledger is adjudicated in the browser, which is the entire reason `/ideate` had to stop mid-run and ask** — the ledger has been complete since it landed, and completely unreachable: no HTTP route, no dashboard surface, and `pnpm --filter server ideas mark` as the only way to sign an idea off. Since the sign-off is a *human* decision and `accepted` is the one status `/improve` may act on, requiring it at a terminal meant the proposing run could not end without a person in-session. The Advice page carries the ledger now, so the run records its proposals and exits. `GET /api/ideas` lists the rows with per-status counts, narrowed by `?status=` and `?repo=` — and a **checkout path is refused there exactly as on a write**, since this ledger is device-wide and a path names a different thing on the next machine — while `meta.total` always counts the whole ledger so a filtered view still says how much it hid. `/api/ideas/stream` shadows it over SSE watching the log directory, so an idea written from a terminal appears without a reload. `POST /api/ideas/status` goes through the same `parseIdeaMarks`/`applyIdeaMarks` the CLI uses and is on the **write allowlist**, under the origin-checked CORS the chat routes use rather than the reads' open `*`: a POST here writes a store shared across every repo on the device that another command then acts on, so it must not answer anyone who asks.
- **The browser may set three of the four statuses, and the two refusals live in `applyIdeaStatus` rather than in the route** — `accepted`, `rejected` and `proposed` (the undo, which un-signs an idea without erasing the entry or its note) are reachable; **`shipped` stays CLI-only** because it carries a PR url and is a claim made by whoever landed the change, not a button beside Accept. And a **`rejected` mark with no note is refused with 400**: the reason is the ledger's dedupe record — the thing that stops a rejected idea being re-proposed next run — and an empty one is *worse* than none, because it looks like a decision while carrying nothing a later reader can use. Keeping both checks in the builder rather than the handler is what stops the HTTP contract and the CLI's from drifting apart. Every card renders **what the idea cites** (paths, and `bucket/id` for a judge note), because the evidence is what makes an idea approvable and a card without it is just a title asking to be trusted; the repo's remote slug is on the card too, which is the answer to the question a route was originally held back over — how a device-wide store renders on a page about one proxy's logs. `accepted` rows stay visible in a settled state so it is clear what `/improve` picks up next, and `rejected` rows **collapse behind a toggle rather than disappearing**, because they are never deleted.
- **The always-on heuristic cards are demoted by a day-over-day check, not by raising their thresholds** — `large-system-prompt` and `high-cost` trip on essentially every day of this install and restate the same sentence each time, so they permanently occupied the top of the page above anything actionable. Raising `ADVICE_THRESHOLDS` would have hidden a real finding, and deleting the rules would have lost it outright; the honest observation is that the finding has not *changed*. `adviceMovement` in `packages/core` reads each rule's declared `metric` back off both digests and reports the relative move, and the page folds every card under `ADVICE_STEADY_PCT` (10%) into one **"unchanged since &lt;date&gt;" line that expands to the full cards** — advice is demoted, never silently dropped. The comparison needs no new storage: `baselineDigests` already resolves prior days across the live directory and `logs/archive/<date>/`, and the busy day it stopped its backward walk on is the one compared against. **Absent evidence never makes a card steady**: an unreadable metric, a rule declaring none (`healthy`), and a missing prior day all render in full, so being unable to measure a finding is not grounds for demoting it. Ideas render above all of it, since they are the only part of the page waiting on a person.
- **The proxy puts back the message-level `cache_control` breakpoint Claude Code intermittently drops, which is the difference between a $0.28 turn and a $2.03 one** — a healthy `/v1/messages` request carries three `{"type":"ephemeral","ttl":"1h"}` breakpoints: two on `system` and one on the final content block of the last message. Intermittently (observed on 2.1.221 and 2.1.222, roughly every eighth turn in the worst session, sporadic elsewhere and not time-correlated) a turn ships the two system ones and **none on any message**. The API can then read only the ~48k system+tools prefix, `cache_creation_input_tokens` comes back 0, and the whole transcript bills as fresh `input_tokens` — up to 194,761 on one observed call. The next turn resumes reading the same prefix it always could, so **the omission forfeits both the read and the write and buys nothing**. On 2026-08-05, 32 of 1,526 work calls (2.1%) produced 97.7% of the day's fresh input: 2.66M tokens, roughly $40. Ruled out first, because each would have meant a different fix: not a retry, not a subagent, not prefix mutation, not the four-breakpoint API cap (healthy calls use three, cold ones two), and not the proxy, whose other `cache_control` sites are read-only — a cold request and its neighbours are **byte-identical once `cache_control` is stripped**, same tools, same system blocks, same sampling fields, same session, every message hash matching position-for-position.
- **The injector is gated on six conditions, and the first one is what retires it** — it acts only when there is **no `cache_control` anywhere in `messages`**, so the day the CLI starts always shipping the breakpoint the branch becomes unreachable and the code is a no-op *by construction*. That is deliberately not a version check, a version comparison, or a date-based expiry: each of those needs maintaining and each goes stale silently. The rest refuse to invent caching or to lose money doing it. **At least one `system` block must carry `cache_control`** — proof the client wants caching on this request — and the TTL is **copied off that block rather than hardcoded to `1h`**, so a client-side change carries through, along with any field this proxy has never seen. A **write bills at 1.25–2x fresh input**, so a shallow prompt is left alone (≥100 KB of serialized messages, or ≥40 turns). And critically, **a warm prefix must already exist for the session**: without a read to recover the write, injecting converts full-price fresh input into a 2x write and *loses* money, so the ledger only counts a session warm once a reply has read past that request's own estimated system+tools size — which is the only available evidence that the *message* prefix is cached rather than just the system blocks. It bails at the four-breakpoint cap, honours `PROXY_CACHE_BREAKPOINT=off`, and **fails open throughout**: an optimization must never break or drop a request. The breakpoint lands on the last content block of the last message, where healthy turns put it; a last message whose content is a bare string has no block to carry one and is skipped rather than rewritten.
- **The code reports its own obsolescence, so nobody has to track Claude Code releases** — `cacheBreakpointInjected` is recorded on **every** request in the audit sidecar, becomes a **nullable** `cache_breakpoint_injected` column in substrate slice 9, and surfaces as `UsageDigest.cacheBreakpointInjections`. The column is nullable rather than `NOT NULL DEFAULT 0` for a reason that is the whole point: a sidecar predating the injector must stay distinguishable from one that recorded "did not inject", because the retirement trigger is *a week of zeroes*, and that only means something if zero is a real observation rather than the absence of one. Once the count stays at zero after a CLI upgrade, `proxy/cache-breakpoint.ts` and its three call sites can simply be deleted. **One consequence is accepted rather than fixed**: injecting changes the bytes `skim.keyFor(forwardBody)` hashes, so an affected request keys differently than before and takes a one-time skim miss — cheaper than the cold call it replaces, and the skim is an exact-repeat cache that is off by default.
- **Invented proposals get a ledger of their own, because they cannot borrow a suggestion's evidence** — the rules in `suggestions.ts` measure how work was *done*, so they structurally cannot see a capability that is missing: nothing counts a command that was never written. `/improve` covers the first and is forbidden from inventing anything, on a rule that is load-bearing rather than fussy — padding a run with the agent's own ideas breaks the trace from every change back to the sessions that justified it. So invention gets a **different store with a different evidence standard** instead of a relaxed rule, and the two never merge: `suggestions list` returns no idea, `ideas list` no suggestion, separate files and separate namespaces sharing no code. `<logDir>/ideas.json` holds one entry per idea, and `pnpm --filter server ideas list|add|mark` reads the log directory directly so **no server is required**. What substitutes for source sessions is two things, both required: **cited evidence a person authored** — an `## Open questions` entry, a judge's enrichment note, a CHANGELOG entry, or an explicit deferral, each with a path (or `bucket`/`id` for a judge note, which lives in the other store rather than in a file) — and **a recorded human sign-off**, which is what `accepted` is and why it is the only status `/improve` may act on. An entry citing nothing is refused at the **parse boundary** rather than linted, since "I noticed the code could use X" is precisely the output the requirement exists to suppress.
- **The ledger's default status is persisted, which is the opposite of how a suggestion flag works, and the inversion is the point** — a `pending` suggestion is dropped on read and deleted on write, so that file holds only decisions and an empty one means "nothing done yet". Here a `proposed` idea is **kept**, because the ledger's whole job is to record *what was already considered*: an idea proposed and rejected must never be proposed again, and the rejection reason is the most valuable row in the file. A store keeping only the liked ideas would re-propose the rejected ones every run. The **slug is the dedupe key** and adding one already present in **any** status, `rejected` included, is refused rather than overwritten — reported, not thrown, so a batch of three with one collision still records the other two. Because a near-duplicate under a different slug defeats that key and only a reader can tell a rename from a genuine sibling, `similarIdeaSlugs` scores shared slug tokens and `add` reports the hits under `similar` **without refusing anything** — an overlap is a prompt to look, not a verdict. The **repo is a git remote slug, never a checkout path**, since the store is device-wide and shared across every repo on the machine and a path names a different thing on the next one; that is enforced, not documented. A mark on an unknown slug **writes nothing**, again the opposite of a suggestion flag — there an unknown id is still written because the rules are recomputed and it may come back, while an idea exists only in this file, so inventing a titleless evidence-free entry to hold the flag would write exactly the row the parser drops. `rejected` and `shipped` each require their note: the reason, and the PR url.
- **A corrupt ledger throws where a corrupt flag file reads as empty** — `readSuggestionStatusStore` treating a broken file as empty is right *there*, because the suggestions underneath are recomputed from the transcripts on every load, so the flags are the only loss and refusing to render the dashboard would be worse. An idea exists **nowhere else**: reading a broken ledger as empty would let a caller conclude the ledger is fresh, re-propose everything already rejected in it, and then overwrite the file with that conclusion. A *missing* file still reads as empty, since that is the honest starting state. The distinction is load-bearing for a caller resolving the store through a waterfall of tiers — a missing store is *absent* and it may fall through, a broken one is a **stop**, and falling through past a broken tier 1 forks one ledger into two that each look complete. **One defect here typechecked and passed every unit test and was only found by driving the CLI**: `--help` exited 1 with `missing value for --help`, because a leading flag leaves the command defaulted to `list` and the help check ran against that resolved command rather than argv, so `--help` reached the parser as a flag wanting a value.

- **Session suggestions can now be adjudicated before `/improve` acts on them** — the rules in `suggestions.ts` are deterministic pattern matches with high recall and **no judgment**, so some of what they report is simply wrong: `serial-discovery` fires on reads that were genuinely dependent, `redundant-reads` collapses two long paths sharing a truncated prefix. Nothing could record that a finding was *wrong*, and `skipped` is a different claim — *the finding was right, we passed over it* — so a misfiring rule cost attention in every `/improve` run forever. A fourth flag **`dismissed`** records it, and because `SUGGESTION_STATUSES` is the single source everything derives from, the CLI's validation message and the dashboard's control both pick it up for free. **Only `done` is a dated claim, so neither `skipped` nor `dismissed` produces a recurrence state** — reading a regression off a dismissal would be reading a fix off a finding that never existed — and the `historical`/`regressed`/`mixed` model is untouched, pinned by a test asserting a dismissed entry yields no recurrence claim. **Enrichment for a *confirmed* suggestion goes at bucket level, in a new top-level `judged` map, never on the suggestion's entry**, and that is structural rather than tidy: a confirmed suggestion is still `pending`, and a pending entry cannot persist at all (dropped on read, deleted on write — which is exactly what makes `Pending` the undo), while the entry's single `note` is overwritten by whoever later marks it `done -n "<PR url>"`. Bucket-level storage keeps `note` single-purpose and the judge's context unclobberable. The store bumps to **version 2**, and a v1 file migrates by defaulting `judged` to `{}` — the whole of that upgrade, since every bucket in such a file reads as unjudged, which is true.
- **Buckets are `not-ready` / `dirty` / `clean`, and cleanliness is held per bucket precisely to break a loop** — only a complete window may be judged or improved upon, since a partial one will gain sessions and re-fire its rules over a wider window, so `complete` is now on the bucket type. **Cleanliness is deliberately not derived from the suggestion entries**: if it were, un-dismissing a suggestion — the existing `Pending` undo, which *deletes* the entry — would re-dirty the bucket, the judge would run again, and it would re-dismiss exactly what a human had just un-dismissed. Keeping the flag at bucket level means a human override survives, because the judge never revisits a clean bucket; tests pin it on both sides of the file boundary. Judging is also **refused outright when any session carries a null `started`**, naming the session at fault — membership is ordered by `(a.started ?? '').localeCompare(b.started ?? '')`, so a null sorts ahead of every real timestamp, lands at the front of bucket 1, and shifts every boundary after it by one, silently re-pointing every stored verdict at sessions it never examined. 0 of the corpus is affected today; the guard exists to keep it that way. Indexes are otherwise stable because **transcripts are never archived or evicted** — `retention.ts` only moves files whose *name* carries a date prefix — so a full bucket's membership is immutable.
- **Repeated dismissals now indict the rule rather than being re-litigated every ten sessions** — `ruleDefects` reports a rule dismissed in **3+ buckets** *and* in **50%+ of the buckets it fired in**, returning the count, the ratio and each bucket with its dismissal reason, with both numbers in an exported `SUGGESTION_DEFECT_THRESHOLDS`. **Both conditions are load-bearing**: the count alone would indict a rule that fired forty times and was wrong three, the ratio alone one that fired once and was dismissed once. Only complete buckets count on either side, since a partial window can never contribute a dismissal and would only dilute every ratio. Four CLI commands carry it, all reading the log directory directly so **no server is required** and all with `--json`: `suggestions buckets [--dirty]`, `suggestions judge -r <n> [--confirm <id>[:<note>]] [--dismiss <id>:<reason>]` — which writes the dismissed statuses and the `judged` record in **one atomic temp-file-plus-rename**, because two writes could leave a bucket recorded as judged with its dismissals missing — `suggestions judge --amnesty` for drawing a line under a backlog, and `suggestions defects`. Over HTTP, status rows carry `bucketState`/`judgedAt`/`enrichment`, `meta.bucketStates` counts dirty/clean/not-ready over **every** bucket rather than the rows returned (how much of the corpus is unadjudicated is a fact about the corpus, not the slice asked for), and a `POST` carrying `judged` or `amnesty` takes the guarded path through the existing origin-checked write CORS. In the dashboard `dismissed` takes the faintest of the four tones — the row is a record, not a finding — dimmed further than a merely resolved one with its reason still legible and **not counted as open**; every bucket is badged **Judged / Unjudged / Not yet full** on both the Advice list and the bucket detail, and a confirmed suggestion shows the judge's note under its control. **Two defects here typechecked and passed unit tests, and were only found by driving the CLI against the real corpus**: comma-splitting a `--dismiss` value turned one reason into a second entry naming a rule nobody mentioned (a fragment carrying a colon would have been written as a real dismissal), so a value containing a colon now splits only at a comma that introduces a new `<id>:`, with the parser moved into core under test; and `--amnesty` re-recorded *every* complete bucket with no notes, **deleting enrichment a judge had actually written**, so it now covers only still-dirty buckets and leaves judged ones and their notes alone.
- **Command detail now trends how much work a run does and how long it takes, not just what it costs** — the page could say what a `/task` spent and which step it spent it on, but nothing answered the two questions cost cannot: how long a run takes end to end, and how many steps it takes to get there. Two per-run charts, oldest left, at the same grain as the scatter above them — a command runs a handful of times a week, so daily buckets would mostly be empty. **"Steps per run" plots three series precisely because they are not the same number**: agent steps (transcript nodes — every decision, tool call and outcome the run and its subagents produced), the tool calls among them, and declared `## Step N` steps reached. The divergence is the finding, and conflating them hides the shape worth catching: a run that did plenty of work and still never reached the last step. **Declared steps are counted against the run's own snapshot rather than the current catalogue** — a step the command file grew afterwards was never available to reach, and counting it would read as a regression the run had no way to cause. They are two charts rather than two axes because a step count lives in the low tens while a duration is milliseconds in the millions, and a shared axis flattens the counts onto it; they share one x, so reading a spike in one against the other is a matter of looking up or down. `commandRunShapes` is pure and in `packages/core` under test, built from stored records alone.
- **A run records an end-to-end wall clock, distinct from the span between its requests** — `totals.durationMs` measures first captured request to last, which **stops at the last request rather than at the answer to it, and reports 0 for a run that only ever sent one**. The new `totals.wallMs` is the honest end-to-end reading: a top-level run *is* its session, so its transcript's start and last write bracket the whole thing. A **nested** run deliberately does not widen — it is a slice of its host's session and owns no bracket of its own, so widening would charge a `/clean` with time its parent spent before and after it; it keeps the request span, which is pinned by a test asserting the two are equal for a child. Both fields read 0 as *unknown* rather than *instant*. There is **no backfill** — this is computed at capture time, so records written before it keep 0 — and rather than silently mixing the two measurements, `meta.wallMeasuredRuns` counts the points on the wider bracket and the card names the shortfall. The run detail page's tile becomes **End to end** and reports how much of that span was spent sending requests. Schema bumps to 3, and substrate slice 8 adds `totals_wall_ms` beside `totals_duration_ms` so both are queryable; the store watermark is dropped so the column fills on the next pass.

- **`/trends` is back, as end-of-day snapshots blended into one rate per metric** — the page that folded into the Overview was a by-day table beside two bar charts, and it went because every one of its answers already had a better home. This is a different page answering a different question: the Overview says how *today* is going, and nothing said what the rate has actually **settled at**. Two ideas carry it, both pure and both in `packages/core` under test rather than in a component. `endOfDaySnapshots` drops the still-open current day — a day being written to is a part-day figure standing next to whole ones, so leaving it in plots it short and drags every mean on the page down; on real captured data the 30-day window is 15 closed days, `2026-07-13 → 2026-08-02`, with today excluded. And `blendRate` is **`Σ numerator / Σ denominator` across the window, never the mean of each day's own rate** — that distinction is the entire feature, because averaging daily rates lets a day with four requests count as much as one with four hundred. The test that pins it is 100 requests at $1 against 1 at $10: blended $1.09, not the $5.50 a per-day mean returns. Every metric now declares its own `MetricBlend` — a numerator, a denominator and the **unit the value is read with** (`per day`, `per work request`, `per M tokens moved`, `per session id`, `of prompt tokens`) — and the field is **required on `StatMetric`**, so a new metric cannot be registered without stating what its rate is per; a per-request mean recovers its numerator by multiplying back through `perCall.work.requests` rather than being re-derived. Idle days are skipped rather than counted as zero, and the table's **Days** column reports days that carried a denominator, not days in the window.
- **The graphs are a carousel of full-size stat cards, and picking one opens its trend over time** — a slide is the Overview's card grown up: same label, same value, same footer with its delta chip, with the sparkline become a real 240px plot and the metric's description under it. The whole slide is the link to `/trends/$metric`, which is a **sibling route, not a child**, so choosing a graph is a navigation rather than an outlet inside the carousel. Thirteen chips name every metric so one is picked by name instead of by counting anonymous dots, arrows step through and disable at both ends, and a hand-driven swipe re-syncs the chips from the track's own scroll position rather than from the last button pressed. Two defects here typechecked cleanly and were only found by driving it: `.trend-track` was **unpositioned**, so a slide's `offsetLeft` was measured from a page-level ancestor and every scroll target — and the nearest-slide sync reading them back — was off by that constant; and `show` used an animated `scrollTo`, which leaves the track exactly where it was wherever the animation does not run while the chips claim it moved, so it assigns `scrollLeft` outright. Verified against real data: chip 5 → `scrollLeft` 2284 with `Cost per call` leftmost, next → 2855, prev → 2284, and the slide's own click landing on `/trends/cost-per-call`. `/trends/$metric`'s breadcrumb now says **Trends** rather than Overview, which is what the URL always claimed.

- **Four per-call metrics, so the dashboard can answer whether a turn is actually getting cheaper** — every existing Overview statistic is a daily total or a blended rate, which means a quiet day looks like an improvement and a busy one like a regression. `Cost per call`, `Fixed prefix`, `Fresh input per call` and `Calls per session` divide by requests instead, splitting the bill into the two things you can move independently: what a call costs, and how many calls a piece of work takes. They ride on `UsageDigest.perCall`, so `/api/summary` and `/api/trends` carry them with no new endpoint, and `overview.tsx` picks them up from `METRICS.map` with no edit. **The headline deliberately excludes auto-mode permission-classifier traffic** — Claude Code sends a separate ~110 KB prompt per agent tool call to score it, and counting those would make each mean track the ratio of classifier to work traffic rather than either one; on real captured data they are over half the day's requests. A call is classifier traffic when its `request.system.hash` resolves to a stored outline carrying **both** a `HARD BLOCK` and a `SOFT BLOCK` heading. **Matching on headings rather than on size is the load-bearing choice**: the classifier prompt moves by a kilobyte or two between revisions and a byte threshold would silently reclassify prompts as they drift across it. Every row of that table is now a link to `/trends/avg-system-prompt/$hash/section/$index`, a page carrying the section's size, share and depth as stat tiles above its verbatim text. **Reusing `/context/$file/message/$index` was investigated first and rejected**: `RequestBreakdown` models the system prompt as a single `systemBytes` number with no per-section array, so there is nothing in that route for a section index to address, and pointing it at one would have meant inventing a fake message. - **Cache-hit ratio and Tool overhead now carry a delta chip and a baseline line like every other Overview card** — the two of them were the only percentage cards on the page, and they were also the only two with no `trendField`, so `OverviewBody` looked them up in the trend map, found nothing, and rendered a bare headline. The arithmetic was `p > 0 ? ((t - p) / p) * 100 : 0` in three places, so a day following one with no traffic reported **0%** — no movement — even where it had doubled the last real figure; on `/trends/$metric` the line read "nothing recorded on `<yesterday>` to compare against" while the day it should have been compared to sat a couple of rows further up the same table. - **The usage meters were metering cache reads at the price of a cache read, and those are two different numbers** — `CACHE_READ_WEIGHT = 0.1` is the *billing* ratio (Opus reads at $1.50/MTok against $15/MTok fresh input). Anthropic's rate-limit accounting discounts cache reads several times harder than its billing does, and `usageUnits` — the whole unit `learnCeilings` and `buildUsageLimits` count in — was using the billing figure for both. The metering path now has its own **`CACHE_READ_METERING_WEIGHT = 0.02`**, and the billing ratio is deliberately *not* restated as a second constant beside it: money is computed from `pricing.ts`'s `MODEL_PRICES` and nowhere else, so the two cannot drift apart or be confused for one another. The new weight is **measured rather than assumed**, and `scripts/derive-metering-weight.mjs` re-derives it — and prints the checked-in test fixture verbatim — from the retained sidecars, so the numbers below can be reproduced rather than trusted. Sidecars have carried `anthropic-ratelimit-unified-5h-utilization` since 2026-08-04, giving four completed 5-hour windows — every one on record — that each pair a weighted count with Anthropic's own utilization reading and therefore each imply an allowance. One allowance produced all four, so the right weight is the one that makes them agree: at 0.1 they imply **54.7M / 47.1M / 44.2M / 50.6M** units, an 11.3% spread, and at 0.02 **20.0M / 17.7M / 18.7M / 18.9M**, a 6.1% one. **What that does and does not establish is stated in the docs rather than glossed**: the four windows are near-collinear — their cache-read share of units spans just 1.2pp — so weights within a tenth of the best fit (0.019) span 0.011–0.023, and ~6% of the disagreement is residual no weight removes. A far larger-sample check regressing every per-request reading against cumulative units bottoms out near 0.016 and roughly halves the residual against 0.1. The out-of-sample check is the one that survives its own weakness: on 2026-07-28, a header-less day the account demonstrably capped out on, the *unaligned maximum* 5-hour window — an upper bound on any real window — reaches only **79%** of the ceiling 0.1 implies, so at that weight the day could not have capped out, and it did. So the order of magnitude is solid and 0.1 is ruled out; the second digit is not pinned, and the JSDoc and feature doc now say so. **The reason this was invisible for so long is the reason it needed fixing**: usage and the learned ceiling are counted in the same units, so a wrong weight divides out of the ratio and both meters look fine — for exactly as long as the cache-hit ratio holds steady. It surfaces only when the token mix moves, and then it moves the estimated and learned meters together, silently and in the same direction. **A configured ceiling is not so forgiving, so `server/.env.example` was rescaled with the weight** — `USAGE_LIMIT_5H` and `USAGE_LIMIT_WEEK` are absolute counts in this unit, and the shipped examples were five times too high against the new one. Anyone who set those variables by hand must divide by about five: a ceiling left too high makes the meter read usage too *low*, which is the direction that hides a problem rather than surfacing it. The four windows are checked in as fixtures whose assertions are derived from the fixtures themselves — the shipped weight has to fit within a tenth of the best fit *they* admit, and the billing ratio has to fit measurably worse — rather than from literals restating the constant, so a future edit answers to the measurements instead of to the price sheet.
- **`serial-discovery` now counts serial round-trips instead of counting calls, so a well-batched turn is no longer the thing it flags hardest** — the rule's whole premise is that a read-only call which waited for the one before it cost a round-trip that need not have been paid, but it could not see a round-trip: `distillEntries` collected an assistant message's `tool_use` blocks into a local array and flattened them with `entries.push(...tools)`, so the turn boundary was destroyed before anything downstream could read it, and the rule then walked `session.nodes` flat and pushed every consecutive discovery node onto one run. Ten `Read`s issued **together in one turn** — one round-trip, and the exact behaviour `AGENTS.md` prescribes — were therefore indistinguishable from ten `Read`s across ten turns, and produced a longer run than the genuinely serial case ever does. The turn boundary is now carried rather than reconstructed: the proxy marks the **first** call of each assistant message with `▸` (`- ▸ Read(file_path=…)`), continuations stay unmarked, and `parseSessionNodes` opens a new turn on a marked line and joins the open one otherwise, filling a new `turn: number | null` on `SessionNode`. **Marking the first call rather than the continuations is what makes old transcripts safe**: every transcript written by the new proxy carries at least one marker per message with calls, and every transcript written before it carries none, so a legacy transcript reads back as `turn: null` throughout and the rule — which requires a known turn — yields nothing for it, rather than reading it as all-separate-turns and flagging every session ever recorded. A transcript that straddles the change is handled by the same rule: the calls before its first marker keep `turn: null`. `deriveSessionNodes` numbers turns off the request's `messages[]` the same way, and `mergeSessionNodes` always takes the **transcript's** turn even when the derived node wins on text, because the two streams number from different starting points and mixing them would merge unrelated turns. The rule itself now groups nodes into turns and counts a run of consecutive turns that each spent their entire round-trip on **exactly one** discovery call; a turn that issued four reads at once is not a run at all, at any length. **`serialRunLength` stays at 4** — a qualifying turn is by definition one call, so four turns is still four calls and the numeric weight is unchanged; only the population it counts is. One deliberate semantic change rides along: a `decision` node no longer breaks a run, because it is the turn's own reasoning and breaking on it would have narrowed the rule to silent turns; `task`, `done`, and `error` nodes still break it, since those are results a later turn had to wait for. Substrate slice 11 adds the nullable `session_node.turn` column — nullable because null is a real reading, not a gap — and blanks `session.bytes` so every transcript re-parses rather than being skipped on a matching `stat`. Pinned from both ends: `session-node-texts.test.ts` reads the proxy's own marker back as one shared turn, and the rule's tests cover the four cases that matter — four single-read turns flag, ten reads in one turn do not, four turns of two reads each do not, and an unmarked legacy transcript says nothing.
- **The cache-breakpoint injector's retirement signal now distinguishes "the CLI fixed it" from "a gate declined", which is the difference between deleting the module safely and deleting it while the defect is still live** — `ensureMessageBreakpoint` reported only `injected: boolean`, and the retirement trigger was documented as *a week of zeroes*. But the later gates decline most occurrences, so a zero is equally consistent with the client no longer dropping the breakpoint and with it still dropping one that gate 4 or 5 refused to act on. Measured over the first ~18 minutes live, the observed zero was **entirely** the second case: 152 requests recorded the flag, **0 injections, and the defect occurred twice** — so the trigger as built would have said "safe to retire" about a defect that had just happened. Injection behaviour, the gate thresholds, the `PROXY_CACHE_BREAKPOINT` kill switch and the fail-open `try`/`catch` are all untouched — a throw reports **no** observation rather than guessing which side of gate 3 it happened on.
- **Gate 5's prefix estimate was ~45% low, so it was answering "has this session ever had a cache hit" rather than "is the message prefix warm"** — the warm-prefix ledger was handed `estTokens(systemBytes + toolsBytes)`, where `estTokens` is `bytes / 4`, and gate 5 then treats a cache read above that figure as proof the *message* prefix is cached upstream. Measured across 29 cold-start requests in the log window where the ratio is directly observable (`cacheRead` 0 and `input` < 50, so `totalBytes / cacheCreation` **is** the ratio): a whole request runs **2.75 bytes per token, p10 2.68, p90 2.81** — dense JSON tool schemas tokenize far worse than four bytes a token, and the prefix is the densest part of the request. - **`unfinished-tasks` no longer counts every subagent thread against a terminal condition it structurally cannot meet** — the rule required each task to carry a `- done:` line, which is written only from a turn carrying text and zero tool calls. - **`AGENTS.md` now names the command shapes the classifier refuses, and the two discovery loops that keep regressing** — a follow-on to #105 over 39 buckets of recorded sessions, and both halves are written into sections that already existed rather than beside them. **The refusals were never about permission.** Five refused tool results across two sessions all had the same property: the agent had already decided to take the step, so the refusal cost a turn and a retry and prevented no work — and each one succeeded when reissued as the smallest bare command. So `Classifier-sensitive Git calls` is now `Classifier-sensitive calls`, since none of the three recorded shapes is git-specific: a read-only probe captured into a command substitution (`BASE=$(git merge-base origin/main HEAD)`, `d=$(ls logs/archive | sort | tail -1)` — run it bare and read the value off the output), an inspection glued to a mutation in one call (`ls -la logs/claude-proxy.db*; mv …` — two calls, which is the branch-lifecycle rule generalized), and a long process launched with a trailing `&` plus `sleep` (the Bash tool's own `run_in_background` and a bounded wait on the log is the supported form, and re-sending fails again because a foreground `sleep` is separately blocked). **The discovery rules were not restated, because restating them is what did not work**: `serial-discovery` and `redundant-reads` were resolved by #105 and tripped again across thirteen and twelve buckets respectively, so the trip-wire and the no-re-read rule are instead sharpened against the two shapes actually observed violating them. - **Reads now come from SQLite, and the way back is one flag** — slice 5 of the [SQLite migration](docs/wayfinder/map-sqlite-substrate.md) graduates the substrate from a shadow to the thing actually answering. Slices 1–4 built the tables and proved, route by route, that the database returns byte-identical JSON to the directory scan; this slice flips the default. Every API route now reads through `readSource()` in `server/src/db/runtime.ts`, which hands back the substrate unless `DB_READS=0` is set, in which case every route goes back to the file scan it used through slice 4. That is the entire rollback: no migration to undo, no data to move back, because the log files were never touched and the scan still answers everything. The resolver is also the only place that chooses, so no endpoint can quietly end up on a different backing than the one beside it, and it falls back on its own if the database could not be opened at all — a failure to open is a slow read, not an outage. The startup banner says which side is serving. **The invariants are unchanged**: `logs/` is still the sole source of truth and the database is still a disposable materialized view, still rebuilt from scratch by `rm logs/claude-proxy.db && pnpm --filter server ingest`; authored state (`logs/suggestion-status.json`, device settings) is still a JSON file and still read as one from both sides; `logs/sessions/*.md` are still written exactly as before, which is what keeps `/revive` working off disk with no API and no database; nothing under `proxy/` was modified; and there is still **no new dependency** — `node:sqlite`, raw SQL, `PRAGMA user_version`, schema still at version 3.
- **Shadow mode is now whichever side did *not* serve** — it was built to check the substrate against the files while the files answered, which after the flip would have been checking the answer against itself. `shadowSource()` returns the opposite of whatever `readSource()` picked: the files verify the substrate by default, the substrate verifies the files under `DB_READS=0`, and neither happens when the substrate never opened, because then there is no second opinion to be had. `shadowCheck` takes which side served so a reported difference still labels the file answer `files` and the database's `db` whichever way round it ran. It is still off unless `SHADOW_DB` is set, still runs in a `queueMicrotask` after the response is out, and still cannot affect what was served.
- **`/api/sessions/session` re-reads the transcript when the row is behind it** — this was a known blocker, recorded by slice 2 and deliberately left for the slice that flipped reads. `dbSource.readSession` returned the row's `meta`, `bytes` and `modified` alongside a freshly-read `content`, so a transcript appended to since the last ingest produced an object that disagreed with itself: `bytes` counting a shorter transcript than `content` held, `meta` describing a header the content had moved past. File-backed reads made it harmless, and the parity harness could not catch it by construction — it snapshots the corpus precisely to freeze the appends that cause it. It now reads the content and `stat`s the file in the same breath and lets the file's own size and mtime be the authority, using the row's metadata only when its watermark matches exactly, which is the same equality `ingest` uses to decide a transcript is unchanged. When the row is behind — or missing entirely, for a transcript the substrate has not reached yet — it re-parses the content, which is exactly what the file reader would have answered. The trade-off is named rather than hidden: this route stops being a detector of a transcript the substrate missed, so `/api/sessions` — replayed whole, and length-sensitive — is what catches that now, with shadow mode as the second net. There is a test that does the append the harness exists to prevent.
- **`/api/commands` reads back the store it just reconciled** — the same staleness the transcript fix settled, in the one place the server writes before it reads. `withCommandReconcile` appends to `logs/commands/runs.jsonl` and then answers from the substrate, which only picks the append up after the ingest watcher's 500ms debounce; a just-detected run, or a just-retired one, would have been missing from the very response the reconcile ran to produce. `dbSource.readCommandRuns` now `stat`s the store and compares it against the `file_watermark` row `ingestCommandRuns` keeps — the same `bytes`/`modified` equality used everywhere else — and re-reads the file whenever the mark is missing or does not match exactly. The rows answer only when they are provably current. The parity harness could not catch this either: it reconciles once and ingests before replaying, so its rows are never behind. There is a test that appends to the store between two ingests.
- **The suggestion-status write goes through the seam too** — slice 4's review flagged that `applySuggestionStatus` had grown a source parameter with no caller that ever passed anything but the default. Rather than delete it or leave it unexercised, the POST handler now passes `readSource()`. The flags themselves are authored state and stay in `logs/suggestion-status.json`; what goes through the seam is the derived half the response echoes back — the bucket/suggestion join — so the POST cannot describe a different corpus than the GET beside it. It stays out of the parity harness on purpose, because it is a write and replaying it against the real-corpus snapshot would write through a hardlinked status file; it is covered instead by a both-backings agreement test on the synthetic corpus. The CLI keeps the file default, since it runs with no substrate open.

The obvious fix — parse the envelope on every user turn — cannot work, and the sidecars say why: the CLI expands a nested command **client-side**, injecting the command file's body as an ordinary user turn with `$ARGUMENTS` already substituted and the envelope tags stripped, so there is no envelope on a nested turn to find. The run detail links a child back to the run that invoked it, and the run list shows `nested in /task` where a child has no prompt of its own to show — `/clean` and `/pr` declare no `## Step N` headings, so their records have a single unattributed bucket, but the duration, token cost, tool calls and outcome are real and their own.

- **The command runs are indexed, and the three routes over them are proved byte-identical from SQL** — slice 3 of the [SQLite migration](docs/wayfinder/map-sqlite-substrate.md) extends the substrate from transcripts to `logs/commands/runs.jsonl`, the append-only store `reconcileCommandRuns` distils out of the sessions and the captured requests before they age out. Six tables land: `command_run` (one row per record, carrying the envelope, the model and the run window, the outcome / interruption / `reachedEnd` triple, and the nine `runTotals` figures flattened into columns), `command_run_flag` and `command_run_thread` (the leading `--flags` and the run's whole agent family, the latter joining back to slice 2's `session` rows), `command_run_turn` (the per-turn context series), `command_run_step` (the per-step tokens, cost and the five waste counters), and `command_run_pattern`. Everything slices 1 and 2 settled still holds and is not revisited: `logs/` remains the sole source of truth with the database a **disposable view** — `rm logs/claude-proxy.db && pnpm --filter server ingest` still rebuilds all of it — nothing authored goes in, `proxy/` is untouched, reads are still file-backed, and the whole thing is still `node:sqlite` with raw prepared statements and **no new dependency**. Two things about command runs forced departures from the previous slices' shape, and both are why runs are their own slice. First, **a run is stored, not re-derived**: unlike a sidecar or a transcript, nothing re-reads a run's source on every read, and `readCommandRuns` deliberately hands back records it does not fully understand — `isCommandRun` checks three identity fields, so a record written by a newer or older writer is kept and rendered from whatever it has, which is also why half the record's fields are optional (`retired?`, `CommandStep.artifacts?`, and every field `runTotals` and `toListItem` default). Rebuilding such a record from columns cannot reproduce "this key was absent" versus "this key held the default", and it would silently drop a future writer's fields the moment slice 5 flips reads to DB-backed. So `command_run` carries a `document` column holding the record itself: **the tables exist to be queried, the document is what is served**, and the DB-backed `readCommandRuns` re-parses documents and re-applies the store reader's own sort and `retired` filter rather than reassembling anything. Second, **the store is a single mutable file**, so it gets a third watermark shape — a `file_watermark` row keyed on the path, holding `bytes` + `modified` — and a store whose `stat` still matches is never opened; when it has moved, the whole file is re-parsed and every row replaced inside one transaction, which is bounded because the table holds one row per run rather than one per appended line. `logs/commands/` also gets its own `fs.watch`, since the watch on `logs/` is not recursive. The parity harness gains `/api/commands`, `/api/commands/command` (including one flag facet per command, so the filter is exercised and not just the aggregate) and `/api/commands/run`, all enumerated from the **file** side so the substrate is asked about every command and every run the store knows rather than only the ones it managed to index; the `/stream` variants are absent because SSE re-serves the same builder. The installed catalogue under `~/.claude/commands` is deliberately **not** indexed — it lives outside `logs/`, so it is not the substrate's to mirror and both backings read it identically — but the harness pins it on `ParityContext.commandsDir` so a `/sync` landing mid-run cannot move it between the two replays, and the real-corpus test **copies** both it and `runs.jsonl` into its snapshot, because a hardlink freezes which files exist and not their contents. Shadow mode covers the three new routes behind `SHADOW_DB`, computing the DB answer after the response is already written and never affecting it. `NORMALIZATIONS` is still empty.

- **The session transcripts are indexed too, and the ten routes over them are proved byte-identical from SQL** — slice 2 of the [SQLite migration](docs/wayfinder/map-sqlite-substrate.md) extends the substrate from audit sidecars to `logs/sessions/`: `session` (one row per transcript, carrying the header metadata `parseSessionTranscript` derives, the listing's `bytes` / `modified`, and the untruncated opening prompt off the `.state.json` sidecar), `session_node` (the appended step stream in transcript line order), and `session_node_text` (the `.nodes.jsonl` sidecar). Everything slice 1 settled still holds and is not revisited: `logs/` remains the sole source of truth with the database a **disposable view** — `rm logs/claude-proxy.db && pnpm --filter server ingest` rebuilds all of it — nothing authored goes in, `proxy/` is untouched, and the whole thing is still `node:sqlite` with raw prepared statements and **no new dependency**. The transcript **body** stays on disk exactly as before: `md_path` is a pointer, `readSession` still reads the file for its `content`, and the DB backing never stops those files being written, because [`/revive`](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md) reads them straight off disk with no API and no database. Two things about transcripts forced departures from slice 1's shape, and both are the point of doing sessions as their own slice. First, **a transcript is mutable** — the proxy appends to it for the life of a run — so "seen this filename stem already" is not a sufficient watermark the way it is for an immutable audit sidecar. The session watermark is therefore **per file** (`bytes` + `modified`): an append always moves the size, so one `stat` per transcript detects change without re-reading it, and ingest stays idempotent — a second pass over an unchanged directory parses nothing. The same mutability meant the `fs.watch` had to be widened, since the proxy appends inside `logs/sessions/` without touching `logs/` itself, and a non-recursive watcher on the parent would have let the tables trail the files for a whole run. Second, **`session_node_text` is deliberately not a column on `session_node`** and carries no foreign key to it: the sidecar is sparse, it outlives edits, and it can name a node index the transcript no longer has — the file reader hands such an entry back rather than dropping it, so the substrate has to be able to as well. Eviction, by contrast, is *not* a state here: unlike a `request` row, whose `.md` body can be retained away underneath it, a transcript **is** its row's source, so a body that disappears takes the row with it (and its nodes, by cascade) on the next pass. Ten more routes register with the **parity harness** — `/api/sessions`, `/api/sessions/graph`, `/api/sessions/session`, `/api/sessions/node-text`, `/api/sessions/breakdown`, `/api/sessions/errors`, `/api/sessions/graph/nodes`, `/api/sessions/suggestions`, `/api/sessions/suggestions/bucket` and `/api/context` — replayed both ways with the **full JSON** compared, key order included, and the `NORMALIZATIONS` list still **empty**: the agent tree is rebuilt on the DB side by the same `linkAgentSessions` the file reader uses, which sorts each family internally and so does not care what order SQL hands rows over in, and the listing sort is reproduced rather than compensated for. `/api/context/detail`, `/api/context/message` and `/api/context/tool` are the named exceptions and stay unregistered: they read a `.request.txt` body straight off disk and touch no indexed column, so there is no DB path for them to disagree on. Per-thread cases replay the newest twenty transcripts rather than all of them — not a weakened comparison, since `/api/sessions` and `/api/sessions/graph` are replayed whole and carry *every* transcript's metadata and node stream, so a row the substrate got wrong fails there regardless; the cap only bounds the routes that re-read request bodies per thread. The real-corpus test's snapshot was widened to take `sessions/` too — the transcripts being the most volatile thing in the log directory, they are precisely the race that snapshot exists to close — and it **copies** them rather than hardlinking, unlike the write-once audit sidecars: a hardlink shares the inode, so it freezes which files exist but not their contents, and the proxy's appends to a live transcript would otherwise land inside the snapshot mid-replay and read as a substrate mismatch. The session suffix list is kept separate from the sidecar one because `.md` means two different things in this tree and taking the request bodies would have changed which requests read as blob-evicted. **Shadow mode** covers all ten new routes on the same terms as before: served from the files, computed from SQL alongside, mismatch logged, off unless `SHADOW_DB` is set, and strictly unable to affect the response. **Nothing flips to DB-backed reads** — that is slice 5.

- **A SQLite query substrate over the logs, built as a disposable view and proved byte-identical before anything depends on it** — `logs/` is doc-shaped, so every read path in the server is a full `readdir` + `readFile` scan rebuilt per request; the questions the dashboard now asks ("which tools burn the most tokens across every session", "how does this move across thirty archived days") are joins and aggregations, and a directory listing cannot serve them without re-reading everything each time. So the audit sidecars are now indexed into **`logs/claude-proxy.db`** — SQLite in WAL mode via **`node:sqlite`**, which is built into Node and therefore adds **no dependency**, leaving the project's zero-dependency stance intact; the one real platform change is the engines floor moving from `>=18` to `>=22`, Node 18 having gone EOL in April 2025 and Node 20 in April 2026. Raw SQL with prepared statements, schema version in `PRAGMA user_version`, no ORM and no query builder. What the database is allowed to *be* is the load-bearing decision: it is a **disposable materialized view**, `logs/` stays the sole source of truth, every table is reconstructible by re-ingesting, and the supported total-recovery path is therefore just `rm logs/claude-proxy.db && pnpm --filter server ingest`. That invariant decides the rest. Nothing **authored** goes in — `logs/suggestion-status.json` and device settings stay JSON files, because a view that can be deleted may not hold the only copy of something no re-ingest could rebuild. The `.md` and `.request.txt` bodies (~1.2 GB/day, ~99% of the bytes) stay on disk untouched, with the DB holding nullable pointers plus an explicit `blob_evicted` flag, so "retention deleted the body, we kept the metrics" is a queryable fact rather than a dangling path. And **`proxy/` is not touched at all**: the proxy is load-bearing — if it breaks, Claude Code itself stops working — so the server does all ingest, which is a blast-radius decision rather than a dependency-purity one. Ingest runs on server start plus an `fs.watch` on the log directory, keyed on the sidecar filename stem, so running twice or dying halfway are both harmless; it reconciles each directory against its live listing, so a day the summary job archives moves its rows rather than duplicating them and a file retention deletes takes its rows with it. The schema is audit rows only in this slice — `request`, a normalized `request_tool` (the headline unlock: "which tools burn the most tokens" becomes a `GROUP BY`), `request_rate_limit`, and `ingest_watermark` — plus two tables the spec did not ask for and losslessness did: `request_skipped`, because the file readers count an unparseable file under `parseErrors` and a structurally invalid one under the digest's `skipped`, and a view that quietly dropped them could not reproduce those numbers; and explicit `*_present` flags, because a legacy sidecar with no `session` object and a current one whose every session field is null are different facts on disk. **Nothing reads from the database yet**, and the reason is the artifact this slice really exists to build. The file-backed and DB-backed readers sit behind one `SidecarSource` interface, and a **parity harness** replays every wired route (`/api/summary`, `/api/tools`, `/api/trends`, `/api/usage`) against the whole of `logs/archive` **both ways**, asserting the **full JSON is identical** — including object key order, which `JSON.stringify` preserves and the digest's model map inherits from read order — never a row count and never a summary. Legitimate diffs are permitted only as **named** normalizations that state the mechanism making them benign, and the list is **empty**: rather than sorting differently and compensating, the DB reader reproduces the file reader's filename-stem iteration order exactly, which is what makes tie-breaking in the tool table and the busiest-hour scan land the same way on both sides. A harness that cannot fail proves nothing, so one test corrupts a row on purpose and asserts the harness catches it. Against a hardlinked snapshot of this machine's real archive — 14 days, ~14,800 requests, ~506,000 tool rows — all four routes are byte-identical on every day with zero normalizations; the snapshot is what makes that reproducible, since replaying against the live directory races the proxy still writing to it. Alongside it, **shadow mode** (`SHADOW_DB=1`, off by default) serves from the files exactly as today and computes the DB answer in parallel, logging any disagreement; it is a strict observer, running after the response has gone out and swallowing every failure inside it, because a broken substrate must not be able to break a page. Routes flip per route, only once parity is green, and the log files keep being written throughout — recorded in [ADR 0004](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md) together with the hard constraint that `/revive` reads `logs/sessions/*.md` straight off disk with no API and no database, so a later stage must not stop writing those files until `/revive` has been taught the DB, on pain of the migration disabling its own recovery mechanism. The remaining five slices, and a resume runbook written for a cold agent, are in the [migration map](docs/wayfinder/map-sqlite-substrate.md).

- **A suggestion's `done` is read as a dated claim, so a fix that held stops looking like one that didn't.**
  - Buckets are frozen windows, so a rule that tripped on old sessions trips on them forever — "still tripping" was never evidence a fix failed.
  - Each flag's `updated` is compared against the window's session span, giving every row a `recurrence`: `historical` (the window predates the claim), `regressed` (the window was recorded entirely after it and tripped anyway), `mixed`, `none`.
  - The claim is rule-wide rather than per bucket: one `done` carries to every later window instead of needing one mark per bucket. Only `done` counts — `skipped` and undated flags never produce a regression.
  - `suggestions list` hides `historical` by default and prints the hidden count, so the suppression is visible rather than silent; `--recurrence <states>` and `?recurrence=` narrow explicitly.
  - The dashboard badges recurrence, counts `N regressed` in both headers, keeps regressed rows undimmed with a coral border, and folds `historical` into "hide resolved".

- **A Commands page that measures what each slash command costs to run** — a new **Commands** station studies the efficiency of the commands installed in `~/.claude/commands`: how many tokens each declared `## Step N` burns, what prompt drove the run, and where runs die. Capture is **passive** — every real invocation whose prompt envelope carries a `<command-name>` is a run, so there is nothing to tag and no harness to start — and a run is the top-level session rolled up with its whole subagent tree via the existing `linkAgentSessions`, with a nested command counting both as a segment of its parent and toward its own command's numbers. The feature exists in three levels: `/commands` lists installed commands with invocations, a cost sparkline, completion rate and last run; `/commands/:command` leads with a **run scatter over time** (x = when, y = total tokens, colour = outcome, size = turns) carrying vertical markers where the command file itself changed, above a stacked tokens-by-step bar that swaps to a single run on hover, a pattern-frequency table and the run list; `/commands/:command/:threadId` draws a **token-weighted step tree** with the declared steps as the spine, every turn, tool call and subagent hanging off its attributed step at a width proportional to its tokens, and a per-turn delta inspector that reuses `/api/context/message` to show the actual bytes a turn sent. Flags are a **facet** rather than a variant — `/task --sub` and `/task` are the same command, filtered — because splitting them would fragment a small sample into a smaller one. What makes any of this possible is a store: transcripts and captured request bodies live for roughly a day and only sidecars are archived, so an append-only, schema-versioned `logs/commands/runs.jsonl` distils each run while its raw material is still on disk, and the page reads only from there. One idempotent reconcile pass keyed by thread id upserts records, fired debounced on log-directory change so the page moves mid-run and again from the daily-summary job as a backstop — the same code path both times, safe to re-run. Because the store is the only source, **data accrues only going forward**: there is no backfill, and a fresh checkout shows installed commands with no runs, which is the honest state rather than an error. The design's real constraint is that **step attribution is a heuristic** — turns are placed by the agent's own narration and by nested sub-command boundaries, not by any marker the model emits — and the feature refuses to pretend otherwise. Each placement carries a confidence, the run detail states plainly how much is guessed ("53 of 64 transcript nodes were placed against a step, 3 of them anchored on something the run actually did"), and turns nothing could place go into a dashed, clearly-labelled **unattributed** gutter that the UI shows rather than hides. The attribution rules are isolated and unit-tested precisely so an explicit `STEP n/N` marker can replace them later without touching anything else. Nothing is normalised — no dividing by files touched or diff lines — because a size proxy would launder the raw distributions this page exists to show. The pattern catalogue is a small deterministic rule set firing on specific graph nodes and badged there, joined across runs for frequency ("seen in 13 of 18 `/task` runs"), not sequence mining; waste and rework are step-attributable counters in the run record (errored tool calls, duplicate reads, cache misses, no-op turns), and the existing per-session suggestions engine is **linked** on the run detail rather than rebuilt. Degradation is stated wherever it happens: a run whose transcripts have aged out says so instead of rendering zeros as fact, a command with no `## Step N` headings reads "none declared", a step never reached is labelled as such, and a schema bump leaves older records readable rather than crashing the page.

- **Usage meters that read Anthropic's own numbers** — the meters were live but wrong: the Overview showed a weekly window at ~142% while Claude Code's own `/usage` panel said 7%. Two independent causes, both fixed here. The first is the denominator. Anthropic returns `anthropic-ratelimit-*` headers on API-key traffic but not on subscription OAuth traffic — measured on this device, **0 of 12,929** captured sidecars carried a `rateLimit` field — so the "authoritative" header path never once fired, and every window fell through to a ceiling *learned* from history, which is only a lower bound on the allowance. Dividing by a floor reads far too high. So the proxy now polls `GET https://api.anthropic.com/api/oauth/usage`, the same endpoint that panel reads, and a window sourced from it is exact: Anthropic's percentage, Anthropic's reset instant, no ceiling guessed at and no coverage caveat. That call needs the user's OAuth token, which decided where it lives — **in the proxy**, where the token is already in memory to be forwarded, so only the resulting numbers ever reach disk and the credential is never written, logged, or put in a sidecar; `x-api-key` requests are ignored outright, the endpoint being OAuth-only. It polls on a fixed 60-second timer rather than per request or per SSE tick, because a busy session would otherwise hammer it hundreds of times a minute, and it writes `logs/usage-live.json`, which wakes the existing log-directory watcher so the Overview stays live over SSE with no new plumbing. Every failure mode degrades rather than breaks: a failed poll leaves the last good file alone, a reading older than five minutes stops being used as a percentage, an unrecognised `kind` is skipped rather than guessed onto the wrong meter, and with no token seen yet — a freshly-started proxy, before its first request — the whole thing simply falls back to the estimate. The second cause is the *numerator*, and it would have survived the first fix. Anthropic's weekly allowance is a **fixed** window resetting at a published instant, not a trailing seven days, so estimating over a trailing week sweeps up everything since last Friday and charges it to an allowance that reset on Saturday: on this device, 83.0M weighted units counted where 14.9M actually belonged, a **5.6× overcount**. The estimate now anchors to the real reset instant, and the anchor deliberately **outlives the reading it came with** — allowances reset on a fixed cadence, so an instant that has already passed is rolled forward by whole windows and a week-old poll still marks where the current window opened. Coverage for an anchored window is measured against the part that has *elapsed* rather than the nominal span, since a weekly window seven hours old with all seven hours on disk is completely covered, and judging it against 168 hours would read 4% and stamp `partial` on a complete count. With no anchor ever seen the window still falls back to trailing — wrong in a known direction rather than unknowably.

- **Deleting a job from the Jobs page, for real** — each row on **Jobs** gains a `Delete` that removes that job's whole directory from `~/.claude/jobs`: its state, its timeline and everything under its `tmp/`. Listing husks without a way to clear them was half a feature — they accumulate, nothing else reaps them, and the page that knows about them is the obvious place to act. It is an actual `rm -r` with no trash behind it, so the control is awkward in proportion: the first click *arms* the row (`Delete 4.2 MB?` / `Yes, delete` / `cancel`), only one row is armed at a time, and what was removed is stated afterwards — name, file count, bytes freed, path — above the table it just changed. A **running** job is refused: its daemon is still writing there, so the button is disabled up front rather than failing after the click, and the API answers 409 if something asks anyway. Backed by `POST /api/jobs/delete`, the one destructive route in the API and the one on the jobs surface that isn't a GET: it goes through the origin-checked write CORS the chat routes use rather than the read routes' `*`, since a wildcard origin on a delete would let any page open in the browser wipe the device's job history. Before removing anything it re-establishes the target from scratch — the same id validation and direct-child test, an `lstat` that refuses a symlinked job directory outright (removing the link would leave the target, following it would delete outside the root), and a realpath check that the directory is still a direct child of the realpath'd jobs root. The reply carries the refreshed listing as well as the removal, so the page never re-renders a row that is already gone.

- **Usage meters that configure themselves** — the meters previously needed `USAGE_LIMIT_5H` / `USAGE_LIMIT_WEEK` set per device, so a checkout without them showed only the note telling you to set them. They now fall back to a ceiling **learned from history**: the busiest *completed* window on record. The distinction matters twice over. Only completed windows count, because the one in progress is still filling and would peg every meter at 100%; and only windows the retained logs fully span count, because a window starting before the oldest retained request is a fragment, and admitting it would drag the peak down to whatever survived rotation. That history has to come from `logs/archive/<date>/`, which keeps full per-request sidecar triples — the live `logs/` directory holds roughly a day and cannot span even one completed week. The new `server/src/usage-history.ts` reads 28 days of live plus archived sidecars (four weeks leaves room for three completed weekly windows) and memoises the result for an hour, since thousands of sidecars is too much to re-read per request and the answer can only change when a window completes. What the feature refuses to do is the interesting half. A learned ceiling is a **lower bound on the allowance, never the allowance** — Anthropic never stated the limit, so the most that can be said is "at least this much was possible" — and the error runs in one direction only: dividing by a ceiling that is too low makes utilization read too *high*, so the meter overstates how close the account is and cannot invent headroom. The UI carries that rather than burying it: the window is marked `inferred` with the reasoning on hover, the status chip drops limit language for record language (`Below record`, `Near record`, `New record`), and the blurb calls passing the bar *new territory* instead of exhaustion — only the header path ever claims requests will be refused. A configured ceiling still wins outright, being a statement about the allowance where the learned figure is a guess at its floor, and `USAGE_LIMIT_ENV_SUFFIX` in core is now the single source of truth for those variable names so a blurb cannot suggest one the server doesn't read. Nothing is invented where nothing is known: a window with under one completed window of history is omitted as before, and a window kind with no traffic at all learns nothing rather than a ceiling of zero, which is how the Fable meter stays absent on plans that never touch it. Two documentation errors went with it — the archive keeps raw sidecars, not per-day digests as the feature doc claimed, and a proxy restart does **not** always produce `rateLimit` headers: Anthropic returns `anthropic-ratelimit-*` on API-key traffic but not on subscription OAuth traffic, so on such an account the header path never fires at all, which is exactly the gap the learned ceiling fills.

- **The Overview tracks the usage limits, live** — a meter per metered allowance (rolling **5-hour**, **weekly**, and **weekly Fable** where it applies), each with a sentence saying whether the current rate is comfortable, close to the ceiling, or on track to run out early. The bar's colour tracks the **pace**, not the fill level: a nearly-full bar late in a window is fine while a modest one early on may not be, so the tone comes from where the rate is heading, and a faint extension of the bar marks the utilization the rate projects to by reset. The projection is `utilization / elapsed` — the sustainable rate being to spend the whole allowance over the whole window — with `elapsed` derived from the reset instant, so a window resetting in 1h of 5h is 80% gone. Two sources feed it, in order. First, **Anthropic's own accounting**: the proxy already had `up.headers` in hand and now records every `anthropic-ratelimit-*` / `x-ratelimit-*` response header into the sidecar's new `rateLimit` field, which carries the real allowance and the real reset and so needs no configuration. Names are matched by *shape* rather than against a fixed list — one segment names the span (`5h`, `7d`/`week`), an optional one narrows it to a model family, the last names the field — so a renamed or newly-added window reaches the dashboard without a proxy change; resets are accepted as an ISO instant, epoch seconds, epoch milliseconds, or seconds-from-now; and only the newest request's headers are read, since an older reading understates everything since. Second, an **estimate** from logged tokens in weighted units (`input + output + cacheCreation + cacheRead × 0.1` — cache reads bill at about a tenth of fresh input, and `realInput` is avoided because it already sums the other three), measured against a ceiling from `USAGE_LIMIT_5H` / `USAGE_LIMIT_WEEK` / `USAGE_LIMIT_WEEK_FABLE` (`_`/`,` separators and `k`/`m` suffixes accepted). There is deliberately **no default ceiling**: Anthropic doesn't publish quotas as token counts, so a window with neither headers nor a configured limit is omitted rather than drawn against an invented denominator — and setting the Fable ceiling is what opts that meter in, which is how "optional based on plan" is expressed. The honesty of the estimate is the subtle part. `logs/` retains roughly the current day and the archive keeps per-day *digests* rather than raw sidecars, so an estimated **weekly** window routinely cannot see its own span — measured at 15% coverage on this device. Each estimated window therefore reports `coverage`, and below 0.95 the meter is labelled `partial` in amber with the blurb stating the real figure is higher, so a reassuring number never stands unqualified on incomplete data. Two more states refuse to read as reassuring zeroes: no requests captured at all emits no estimated window (0% would say "well within limits" when the truth is "nothing was observed"), and a trailing estimate gets its own vocabulary throughout — exceeding a ceiling the operator chose says so, and only the header path claims requests will be refused. The pace logic is pure and takes an injected `now`, so every threshold is covered by tests.

### Fixed

- **The parity harness's staleness test queried a column that no longer exists** — the assertion that `/api/commands` re-reads a store the rows are behind looked the run up by `thread_id`, but `command_run` has been keyed on `run_id` since nested runs became records of their own (a nested run *shares* its host's thread, so the thread id was never a key). The test failed with `no such column: thread_id` rather than on the behaviour it guards. It now looks the row up by `runKey(run)`, which is what the table stores.

- **`/clear` is no longer a command run, and no longer charged for the work that followed it** — the Commands index listed `clear` with eleven invocations, one of them at **$17.05 over 60 turns**, for a command that executes entirely in the CLI and never reaches the model. Nothing was miscounted: a run is any session whose opening prompt carries a `<command-name>`, and when a local command opens a turn the CLI sends its envelope as the *first* thing in that user message — so a session begun with `/clear` rooted on `/clear`, and every token the session went on to spend was booked against it. On this device that was true of eight sessions whose real command was typed in the same breath (`/mc -t feat/command-toolkit-cli`, `/revive`, `/review`, `/fb`, `/improve`), each of which lost its own run to a `clear` row, plus three where nothing followed the `/clear` at all and the row existed only to hold somebody else's cost. `parseCommandEnvelope` now walks the envelopes in order and takes the first **non-local** one, so those eight are recorded as the command that actually ran and the three are not runs at all. Locality is decided by **adjacency** and nothing else — the caveat text has to sit directly ahead of the envelope, the order the CLI emits across all eleven caveats in the captured logs — because that same caveat survives verbatim into compaction summaries, thousands of characters from an unrelated envelope it says nothing about. Each envelope's `<command-args>` is now read from its own block rather than from the first one in the prompt, which is what had been emptying these runs' prompts: `/clear` carries empty args, so the criteria the user actually typed were being discarded along with the label. That block ends at its **own closing tag**, not at the next envelope, because criteria quote envelopes constantly — a `/task` run whose criteria named `<command-name>/clean</command-name>` and `<command-name>/pr</command-name>` would otherwise have its whole 2,660-character args block cut at the first quotation and come back empty, inflicting the very symptom this entry is about on a run that had been read correctly. Because the store is append-only and cannot forget a line, a record whose thread no longer reads as a run is retracted by writing it back **retired** — `readCommandRuns` drops retired records and re-running retracts nothing further. Only a thread whose **opening prompt was actually read** is retracted: a transcript can outlive its `.state.json`, and the proxy records no `root` at all until it has one, so a sidecar that is missing, torn, or promptless is silence rather than testimony that the run never happened. Retired records are still carried forward through reconciliation, so a thread that reads as a run again keeps the turns that, once its sidecars are pruned, only the record still remembers.

- **The code caught up with the docs it was reconciled against** — the docs pass that preceded this one corrected every doc that was genuinely stale, which left a residue of the opposite kind: code that no longer did what its now-verified doc said. Seven of those closed here. **Skeleton loading** claimed every `QueryState` call site passed a skeleton, and six did not — Commands, Command detail, Command run, Jobs, and both queries on Job detail now reserve their own shape (stat rows, the 300px run scatter, the step tree, the file tree beside its viewer), built from the pages' own classes with no pixel heights, and the doc's call-site count is corrected from 21 to 27. **`server/src/api.ts` read as a binary file** to `rg` and `grep`, because a suggestion's map key was built as `` `${bucket}\0${id}` `` and the literal NUL made every search of that file silently miss — including the search for the function two items below. The separator is now a unit separator written as an escape, which no more appears in a number or an id than a NUL did, so key semantics and collisions are unchanged and `rg buildTools server/src/api.ts` matches again. **The read routes were not method-gated**: `POST /api/withheld` and its siblings answered 200 under the wildcard CORS that is only safe while those routes stay reads, and now answer 405 with `Allow: GET, OPTIONS`. The six documented POST routes keep their origin-checked CORS exactly as it was and still own their own methods — a foreign-origin POST to `/api/chat/sessions` is refused there with 403, not 405. **`UsageMeter` collapsed two pace statuses** into one label, so `on-pace` and `aggressive` both read `Near record` despite already carrying different tones; `aggressive` now says `Passing record`, which is what projecting past the record by reset actually means. **`requestsToScan` ordered a small candidate set largest-first**, which in a session whose bodies grow toward the end means reading only the tail — the same peak-then-even-timeline-walk the general path takes now runs for a set inside the budget too, with the timeline filling whatever reads the walk's own dedupe left spare. **`bucket-tool-schema-heavy` shipped `sources: []`** while its sibling rule named its evidence; `BucketBreakdownSummary` now carries `toolsSources` — the requests the average was taken over, heaviest schemas first, capped at ten — and the rule cites them. And **`PROXY_FILTER_INVENTORY`'s `task-tools` entry** described a proxy that no longer exists; it now states what `proxy/proxy.mjs` strips today: a regex anchored on the injected note's opening and closing phrases, cut from every text block, with an emptied block dropped, a message left with no content dropped, the blank-line run collapsed, and text nothing matched forwarded byte-for-byte. Two of the fixes carry new tests — that a small candidate set is not size-ordered, and that a read route refuses a POST over a real socket rather than a handler stub.

- **The weekly usage meter counts the whole week** — the Overview's estimated windows summed only the live `logs/` directory, which retains roughly the current day, so the weekly meter reported **3% of window** on this device: a seven-day figure drawn from about five hours of logs, comfortable-looking no matter how hard the account had been running. The archive that fixes it was already half-wired — `logs/archive/<date>/` keeps full per-request sidecar triples for weeks, and `learnCeilings` has always read four weeks of it to *infer the ceiling* — but nothing ever read it for the **count** that ceiling divides. `buildUsage` now unions the live directory with the archived days the windows reach into, so both halves of the estimate come from the same history. The interesting half is what had to change first. `coverage` measured the span back to the oldest surviving request, which reads a **hole in the middle** of a window as full coverage — and since the amber `partial` marking is what the span drives, backfilling alone would have swapped a visibly wrong number for an invisibly wrong one: this device's own archive is missing two days inside the current week. So coverage now counts the **days actually retained**, via a new `retainedDays` on `buildUsageLimits`; a day counts when its own archive directory is on disk, and because a reporting day can straddle `<date>` and `<date + 1>` the seam can *understate* coverage, which is the safe direction — it marks the window `partial` rather than presenting an incomplete count as a total. Days are the unit because rotation is day-granular, so a quiet stretch inside a retained day is genuinely quiet while a missing directory is a hole; day ends resolve through a new `dayStartMs`, which applies the zone offset twice so the two DST changeover days keep their real 23 and 25 hours rather than being forced to 24. Callers that pass no `retainedDays` keep the old span, which is all a caller with no retention map can honestly claim. Two smaller guards ride along: archived days are memoised individually for the process lifetime — `/api/usage/stream` rebuilds on a 600ms debounce and would otherwise re-read thousands of sidecar files per tick — while an *absent* day is deliberately **not** cached, since the archive job may simply not have run yet and a sticky miss would pin the gap in place until restart; and live and archived reads are deduped by source filename, so an archiver that copies rather than moves cannot double every request in the seam and inflate the very number the meters exist to report.
- **A session's own captures survive an evening start** — the three scans that floor themselves at a session's start (its Request breakdown and errors page via `resolveSessionRequests`, a suggestion bucket's per-session peaks, and the live graph's session-family request scan) derived that floor by slicing the raw UTC instant — `started.slice(0, 10)` — and handed it to `readSidecars`'s `since`, which compares against *reporting* days. Eastern runs behind UTC, so a session opened after 8pm Eastern carries a `started` whose UTC day is already tomorrow, and the floor then excluded every request that session ever made: the breakdown read zero captures, the bucket lost that session's peak, and the graph fell back to drawing the whole run from transcript gists. All three now derive the floor with `reportDay`, the same clock the filter compares against, so the scan starts on the day the dashboard actually buckets the session into — which also **supersedes the day-back widening** the graph's scan took in the entry below, since a floor derived on the right clock needs no slack to cover the offset. `REPORT_TZ` is unchanged: `America/New_York` already tracks EST and EDT as the date dictates. The filename prefilter inside `readSidecars` keeps its UTC slice on purpose — it selects a superset that each sidecar's own timestamp then narrows, and a UTC filename day is never *earlier* than its reporting day, so it cannot drop a sidecar the timestamp pass would have kept.

- **The live graph actually reads the captured requests** — the graph was documented as re-reading its step text from the Request breakdown, and in practice was drawing almost entirely from transcripts, where every line is gisted to 160 characters. Two independent defects, both silent. First, the scan window: the floor for which sidecars to read came off the family's earliest transcript `started`, which is a **UTC** instant, but the sidecar reader narrows by *reporting* day in `REPORT_TZ` (`America/New_York`) — so a session opened between midnight and ~04:00 UTC reports on the day *before* its own timestamp, the floor excluded every request it ever made, and the family resolved to zero captured requests. Measured on the local `logs/`: the same query returned `files=0` at the computed floor and `files=4382` a month earlier. The floor was first backed off a day to cover the offset; the entry above replaced that slack by deriving the floor on the reporting clock itself. Second, the merge: `mergeSessionNodes` advanced its position in the derived stream only on a match, so a single step the two streams worded differently desynced them permanently and every later step stayed at its gist — equal-length 132/132 streams matched only 100, and a 45/45 pair matched 17. It now walks both sides and re-syncs on a mismatch, searching outward along growing diagonals for the nearest pairing that skips fewest steps on either side within a 24-step window; drift is counted in steps because its cause is whole turns one side holds and the other doesn't. Past the window the transcript carries the rest alone, so the graph still degrades rather than breaks. Over the real log directory the two fixes take step coverage from no thread resolving at all to **355 of 358 steps (99%)** read from the captured request.

- **The Request breakdown holds its place when you come back to it** — clicking a row deep in a request's "Messages by size" table and then going back no longer dumps you at the top of the page to scroll down and find your place again. The router had no scroll restoration at all (`createRouter({ routeTree })`), so every arrival — including a Back — started at offset 0; `scrollRestoration: true` turns on TanStack's per-history-entry snapshot, which also covers the other drill-downs and any scroller the page owns, while a forward navigation still starts at the top. That option alone is not enough for a page whose body arrives with a query: the router restores the offset the moment the route renders, which on a cache miss is the loading state, and a document that short cannot hold the offset, so the browser clamps it away. `useRestoredScroll` re-applies the remembered offset once the breakdown's query has resolved and the tables are on screen, and no-ops on a first visit, where the cache has no entry for the location.

- **The day rolls over at local midnight, not 20:00** — every day-bucketed Overview and Trend value is now bucketed in Eastern (`America/New_York`, so EST or EDT as the date dictates) instead of on the sidecar timestamp's raw UTC prefix. An evening's work used to jump to "tomorrow" as soon as UTC crossed midnight, so the Overview both counted the *previous* evening's requests and hid the current one's — on a sample day that was 676 requests wrongly included and 265 wrongly missing. Because the proxy names files in UTC, one reporting day now straddles the filenames `D` and `D+1`: the filename filter selects a superset and each sidecar's own timestamp narrows it exactly, and `readArchivedDay` merges the two UTC archive folders a reporting day spans. Busiest-hour is computed and labelled in the same zone (`17:00 EDT`, not `17:00 UTC`), and the Overview date line and the "By day" tables name the zone they're in. The Skim trend buckets in the same zone, so its days line up with the window that selects them. Digests already finalized into the archive keep the UTC buckets they were written with; raw archived sidecars take precedence over them, so this only shows on days whose sidecars have been pruned.
- **An unsent chat draft survives navigating away** — what you typed into the Sessions page composer but never sent is no longer discarded the moment you click through to a session, the graph, or anywhere else. The draft moved out of `ChatConversation`'s component state (which unmounts with the page) and into `ChatSessionProvider`, which already sits above the router so the turn log, pending prompt and Stop button outlive the page they were started on — the input now travels with them. It still clears where clearing is the point: `send` empties it on submit rather than on success, since the prompt is already on screen as a turn, and "New chat" clears it along with the session it belonged to.

- **Sessions are named, not numbered** — a transcript now headlines what it is instead of its thread id, which is what 92 of 100 local transcripts showed. Only a session Claude Code titled itself carried a name, and it only titles interactive chats: a dashboard-started run is headless (`claude --print`) and a subagent shares its parent's session id, so neither is ever titled. `deriveSessionName` condenses the opening prompt into a short sentence-case name for those, `sessionName`/`sessionDisplayName` set one fallback order (CLI title → derived name → prompt → id) that the listing, the graph, the detail page and a suggestion's sources all read, and the id stays as the mono sublink. Two title-linking bugs went with it: a title landing on the *first* thread whose opening prompt matched left a second thread with the same prompt permanently nameless (it now goes to the most recently active **untitled** match, and never displaces a title already written), and titles were only ever matched against in-memory threads, so a proxy restart dropped them — an unclaimed title now waits in a `.pending-titles.json` sidecar and a title arriving for a thread that exists only on disk is written to it directly.

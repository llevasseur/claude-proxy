## [Unreleased]

### Added

- **A row of "What it is made of" now opens the section's actual text** — the breakdown could say that one heading was 43.8% of a 111.5 KB prompt without ever showing a word of it, which leaves the only actionable question ("what is in there?") unanswered at the point it becomes worth asking. Every row of that table is now a link to `/trends/avg-system-prompt/$hash/section/$index`, a page carrying the section's size, share and depth as stat tiles above its verbatim text. **Reusing `/context/$file/message/$index` was investigated first and rejected**: `RequestBreakdown` models the system prompt as a single `systemBytes` number with no per-section array, so there is nothing in that route for a section index to address, and pointing it at one would have meant inventing a fake message. The stored outline could not answer it either — `WirePromptSection` keeps `block`, `heading`, `level` and `bytes` and **no text and no offset** — so the text has to be read back out of a request body that sent the prompt. Any of them will do, since the hash is over the prompt itself; `buildPromptSection` walks the live directory and the window's archived days for sidecars whose `request.system.hash` matches, tries the newest bodies first and stops at the first one that parses. Bodies age out at 30 days while outlines are kept forever, so a section whose every candidate has been evicted **comes back with its size and an empty `parts` rather than an error** — the same line retention already draws elsewhere. Index alignment is the load-bearing detail: `wirePromptSectionTexts` and `sectionsOfText` are now one parse (`spansOfText`), mirroring `outlineWirePrompt`'s loop and its `if (text !== "")` skip, with **byte counts from offset arithmetic and text from line ranges** so a multi-byte character cannot desync the two; a body whose span count no longer matches the outline is discarded rather than sliced. A heading repeated across blocks is **one row and one page with one part per block**, matching how `sectionShares` already sums it. The `$index` addresses the server's ranked order, so each row carries its rank and **sorting the table does not move a link** — verified in the browser by sorting alphabetically and reading the `href`s back (15, 3, 8, 11, not 0–3).

### Changed

- **The system-prompt breakdown moved from `/prompts/$hash` to `/trends/avg-system-prompt/$hash`** — the page is only ever reached by clicking a cohort in the Avg system prompt trend, and its breadcrumbs already said so (Trends › Avg system prompt › `<hash>`), but the URL claimed a top-level `/prompts` section that does not exist. Nesting it under the metric it drills into makes the address match the path through the app. The API is untouched (`/api/prompt?hash=…`); the change is the route declaration in `router.tsx`, the `useParams({ from })` it is read with, and the one `<Link to>` in `PromptMixPanel`'s `CohortLabel`. TanStack Router types all three against the registered tree, so `typecheck` is what proves they agree. The sibling `/trends/$metric` is a two-segment route and is not shadowed by its new three-segment child — verified in the browser that `/trends/avg-system-prompt` still renders the trend page and `/trends/avg-system-prompt/<hash>` still renders the breakdown. **This does not by itself make the page reachable**: `logs/system-prompts/` is empty, so every cohort comes back with `hash: null` and `CohortLabel` renders an unlinked `(est.)` span for all of them. Populating that store — by running `prompt-backfill`, or by accumulating traffic through a proxy carrying the capture code — is what lights the links up.

### Fixed

- **The route-parity harness no longer runs past its timeout once the prompt store is populated** — `/api/prompt`'s case list was one replay per distinct hash in the last archived day's 7-day mix, and each case rescans that whole window on both read backings. That was free while `logs/system-prompts/` was empty, because every cohort came back with `hash: null` and the list was empty; after `prompt-backfill` tagged 20,858 sidecars across 596 prompts, a single day carries 40–120 distinct hashes and the run blew through the 600s limit. It now replays each day's **three biggest cohorts**, which are the ones the mix page actually links to, under the same bounded-cases precedent as `PER_THREAD_CASES`. The cause was pinned to the data rather than to the code in this change: the reworked `spansOfText` was benchmarked against the pre-change parse over 793 real captured bodies and came back **140ms vs 142ms for the same 13,315 sections**, and the new `/api/prompt/section` route is deliberately not in `PARITY_ROUTES`.

- **The Avg system prompt page no longer jumps down once its data lands** — the loaded page puts `PromptMixPanel`'s two-card row *above* the chart, but `TrendDetailSkeleton` only ever reserved the chart grid, so the entire page dropped by the height of that panel the moment the trend query resolved. Two smaller shifts rode along with it: the panel returned `null` while its own `prompt-mix` query ran, so it popped in a second time after the page had already settled, and the day-over-day line sits in the `pagehead` *outside* `QueryState`, so it pushed everything below it down by one line when the comparison appeared. The skeleton now renders the same boxes the loaded page will, in the same order — a `PromptMixSkeleton` shaped like the real panel (both headings and the "click a prompt for its breakdown" note are fixed strings, so they render as **real text** rather than shimmer), the panel shows that placeholder instead of `null` while it loads, and the pagehead holds its line. **Reserving one line where the page renders three was the remaining error**: the cohort tables' first column carries a wrapping `model · size-band` label, which makes real rows 60–101px against a flat 39px placeholder, so `SkeletonColumn` gained a `lines` field and the mix tables reserve two. Measured in the browser with the API artificially delayed so the skeleton actually paints: the chart grid's offset moved **169px** before and **9px** after, with the panel itself reserving 685px against a rendered 694px. The residue is data-dependent — row counts and how far a label wraps are not knowable before the fetch — so the counts are the tables' own `TOP_COHORTS` shape rather than a match to one day's traffic.

- **The Overview skeleton no longer has the usage meters touching the stat cards** — the 22px gap between stacked grids comes from `.grid + .grid`, an *adjacent* sibling selector, and while the page loads `QueryState` renders `SkeletonStatus` between the usage grid and the skeleton it wraps. That `.sr-only` span is `position: absolute`, so it takes up no space and looks invisible in the layout, but it is still an element in the sibling chain — enough to break `+` and drop the margin to `0`, which is why the spacing was right once the data landed and wrong only while it was loading. The rule now also matches across it (`.grid + .sr-only + .grid`, and the same for `.grid + .card`), so the placeholder sits exactly where the loaded content will. Verified in the browser against the real stylesheet: with the status node in place the old selector computes `margin-top: 0px` and the new one `22px`.

### Added

- **The Overview now answers "are today's tokens costing more than usual?", and the Trends page has folded into it** — spend and volume each already had a chart, and neither could answer the question, because both move with volume alone: a day that cost more because it *did* more looks identical to a day that cost more because it bought its tokens badly. The new **Cost per token** card plots one dot per day with volume on x and spend on y, so a day's slope from the origin *is* its blended price, and the dashed line through the origin is the median $/MTok of the window's **earlier** days — today is excluded from its own baseline, so a bad day cannot quietly raise the bar it is judged against. Today is drawn larger and in a different hue, and one sentence above the plot states the whole verdict: `2026-08-03: $549.44 (so far today) · $2.27/MTok across 242,044,868 tokens −23% below the $2.96/MTok median of the 4 days before it.` The denominator is `realInput + output`, and `realInput` **already counts cache reads and writes** — the whole prompt. That is deliberate and is what makes the number mean efficiency rather than arithmetic: a cache read is an order of magnitude cheaper than fresh input but still a token in the denominator, so leaning on the cache genuinely pulls the rate down. `cost-rate` is registered in `METRICS` like any other statistic, so it also earns an Overview stat card and a `/trends/cost-rate` drill-down for free, and `UsageDigest.trend` gained `costPerMTok` for its day-over-day chip. **`/trends` itself is gone**, which is what the card was worth: the page's two bar charts were `/trends/$metric` sub-pages reachable by clicking the matching stat card, and its by-day table repeated what those pages already showed. Only **Tokens per request** had no other home, so it moved across as a full-width Overview card. The path stays as a redirect to `/` rather than 404ing a bookmark, and because every route is a flat child of the root with an explicit path, `/trends/$metric` is a *sibling* of `/trends` and not a child — removing the index route leaves every drill-down untouched. The rate arithmetic lives in `packages/core` (`rateTokens`, `costPerMTok`, `costRatePoints`, `baselineRate`, `summarizeCostRate`) under test, including that a cached day and a fresh day moving identical volume land on different rates. **Verified in the browser against real data**, which is how two defects were caught that typechecked cleanly: `--accent` resolves to the same teal as `--signal`, so the legend named a two-colour distinction the plot never drew; and recharts silently drops a `ReferenceLine` whose `segment` runs outside the axis domain, so the baseline vanished entirely the moment the priciest day out-sloped the median. Both axes are now fixed and the segment is clamped to whichever edge it reaches first.

- **A system prompt on the avg-system-prompt page is now something you can open and read section by section** — the mix panel already named which cohorts were pulling the daily mean up, but it stopped at the name and the total: "`security-monitor · 0d5df35d` is 38% of requests at 51.6 KB apiece" says *which* prompt is the problem without saying *what inside it* is. Every identified cohort in **Where the number comes from**, and every mover in **Why it changed**, is now a link to `/prompts/$hash` — a page whose left card lists that prompt's `#`-headings **sorted by largest share first**, with size, depth and an inline bar, and whose right card lists every day in the window the prompt actually ran: its request count, its share of that day's traffic, its own size, and the bytes it contributed to that day's mean. So the path from "the mean moved" to "this one heading is 47% of the prompt that did it" is two clicks. The table sorts on all four columns in both directions, client-side over the list already in hand. **Share is of the prompt's own section bytes, not of its wire bytes**, so the column sums to 100%: JSON escaping and the block envelope belong to no heading, and attributing them to one would misstate every row. A **legacy cohort stays unlinked** — it is keyed by model and size band rather than by a prompt, so there is no single outline to open, and it renders `(est.)` as before. The route is `/api/prompt?hash=&days=`, which reads the outline out of the content-addressed store at `logs/system-prompts/<hash>.json` and reuses the mix walk `buildPromptMix` already does, now extracted as `promptMixWindow` so the two cannot drift. A prompt whose outline was never stored, or a hash no request ever sent, **answers with an empty breakdown rather than an error** — pre-capture traffic is the normal case for older days, not a failure. `sectionShares` lives in `packages/core` as a pure function beside `diffWirePrompts`, and the route is registered in `PARITY_ROUTES` so both read backings are replayed against it.

- **A trend page now says in words how its latest day compares to the one before** — the chart and the by-day table both held the answer to "did this move since yesterday?", but reading it meant eyeballing the last two points or scrolling to the top two rows, which is exactly the question that sends anyone to `/trends/$metric` in the first place. Every trend page now carries one line under its description — `2026-08-03: 35,989 B  +14% up from 31,458 B on 2026-08-02` — with the delta chip tinted by the metric's own `increaseIsBad`, so a rise in cost reads red and a rise in cache-hit reads green. It is derived client-side from the last two digests already in the window rather than from a new field, so no route changed and the sentence follows the 7/14/30-day switcher. **The two days come from the digests, not the clock**: a gap in captured traffic means the newest two days need not be today and yesterday, which is why both dates are named rather than saying "today". A prior day of zero yields no percentage and says so instead of printing a meaningless `+0%`. **Avg system prompt** also gained a `trendField`, so `UsageDigest.trend` now carries `avgSystemPromptBytes` alongside `realInput`, `output`, `cost` and `requestCount` — that puts the day-over-day chip on its Overview card too, and adds it to the daily summary's trend line, which is where a system prompt quietly growing by 14% overnight had previously been invisible.

- **A concept is now something you can open, sort and read the research behind** — the Concepts page shipped as a flat list, and four things about it were wrong in use. The **Term** column now fits its own longest value and does not wrap, with **Explanation** absorbing whatever width is left and wrapping inside it — a short label reads worse broken across lines than a sentence does. **Term, Field and Saved sort** in both directions, client-side over the list already in hand, defaulting to Saved descending so an untouched page reads exactly as before; ties fall back to file position so equal values do not shuffle between renders. **`find-skills` is never listed**: it is the skill that finds skills, so its presence says the run went looking, not that the concept relates to it — `withoutMetaSkills` drops it in `buildConcepts`/`buildConcept` only, which leaves `logs/concepts.jsonl` and the `concept` table faithful to every word `/teach` wrote and keeps the parity harness comparing filtered against filtered. And **clicking a row opens `/concepts/$ord`**, a detail page served by `/api/concepts/concept?ord=N`, live on the same store watch as the list, 404 on a line the store no longer holds. The address is the **line the record sits on**, assigned from file order before the list is sorted, because a term can be taught twice and the store has no other key. The record contract gained four **optional** fields — `notes` (rendered as Markdown), `tips`, `sources`, and `surfacedSkills`, the skills a run turned up as against those it applied — carried through schema version 6 as a `notes` column plus one `concept_item(ord, kind, item_ord, item)` table for all three lists, since only `skill` was ever a real grouping question. **Absent stays absent**: `normalizeConcept` leaves an unrecorded field off the object rather than defaulting it, so the page says nothing where nothing was recorded and every record written before these fields existed still reads exactly as it did. The v6 migration deletes the `concepts.jsonl` watermark row, because adding columns does not change the file and the next pass would otherwise skip the rebuild that fills them. `/teach` itself still writes only the original five fields — it lives outside this repo, so teaching it to write the new ones, and to stop recording `find-skills` at the source, is a change there.

- **The concepts `/teach` records are now visible in the dashboard** — `logs/concepts.jsonl` had been write-only since the command shipped: `/teach` appended one JSON object per line (`term`, `sentence`, `field`, `skills`, `savedAt`) and nothing in the repo ever read the file back, so the only way to see what had been taught was to open it. There is now a **Concepts** page listing every saved term with its one-sentence explanation, field, skills and date, newest first, served by `/api/concepts` and following `logs/concepts.jsonl` live through `/api/concepts/stream` — `/teach` appends from outside the server, so the page watches the file rather than polling. Behind it, `server/src/db/ingest-concepts.ts` indexes the store into a new `concept` table (plus `concept_skill` for the array facet) at schema version 5, following the `command_run` precedent exactly: a single `file_watermark` row on `bytes` + `modified`, an unchanged store skipped without being opened, and a changed one **re-parsed whole with every row replaced in one transaction**. That wholesale rebuild is the point — it is what keeps `rm logs/claude-proxy.db && pnpm --filter server ingest` a total recovery rather than a resync, and the JSONL the sole source of truth. The table's primary key is the line's position, because the store has no natural key and nothing retracts a line: a term taught twice is two rows, which is itself worth seeing. The read goes through the `SidecarSource` seam so both backings answer identically, and the DB side re-checks its watermark against `stat` and falls back to the file whenever a record landed between two ingest passes. No new dependency, and nothing under `proxy/` was modified.

- **This repo now owns its own log lifecycle, and evicts bodies at 30 days** — slice 6 of the [SQLite migration](docs/wayfinder/map-sqlite-substrate.md), and the last one. Until now nothing here had ever archived or deleted a log; both jobs belonged to an out-of-repo script that had silently stopped archiving, and whose pruner deleted **whole `archive/<date>/` directories** — audit sidecars included — once a day aged past the window. `pnpm --filter server maintain` replaces it: it archives past-day logs into `logs/archive/<date>/`, evicts `.md` and `.request.txt` older than `RETENTION_DAYS` (default 30) **per file inside an archived day**, and prints the digest through the existing `buildSummary` path — no model call, no network. It is a **dry run by default** and only touches disk with `--apply`, reporting counts and bytes reclaimed either way. Every `.audit.json` is kept forever and no day directory is ever removed; nothing without a date-prefixed filename is ever a candidate, which is what keeps `logs/sessions/`, `logs/commands/`, `logs/.chat/` and `logs/suggestion-status.json` untouched. The planner in `server/src/retention.ts` is a pure function from a listing to a plan, so it is tested over a fixture corpus and no test can delete a real log. The launchd agent is under version control at `scripts/com.llevasseur.claude-proxy.maintain.plist`. **The measurement behind it**: across 16,581 captured request triples the bodies are ~96% of the bytes and the sidecars ~1%, and every field path in a sidecar maps to a column — so evicting bodies while keeping sidecars buys 98.6% of the disk win while preserving `rm logs/claude-proxy.db && pnpm --filter server ingest` as total recovery. That is also why the cutover this slice was originally sketched as — the proxy writing rows, content-addressed blobs, authored state moving in, `/revive` reading the DB — was **considered and rejected**; see [ADR 0004](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md). The database stays a disposable view permanently, not as a staging state, and nothing under `proxy/` was modified.

### Changed

- **`AGENTS.md` now names the command shapes the classifier refuses, and the two discovery loops that keep regressing** — a follow-on to #105 over 39 buckets of recorded sessions, and both halves are written into sections that already existed rather than beside them. **The refusals were never about permission.** Five refused tool results across two sessions all had the same property: the agent had already decided to take the step, so the refusal cost a turn and a retry and prevented no work — and each one succeeded when reissued as the smallest bare command. So `Classifier-sensitive Git calls` is now `Classifier-sensitive calls`, since none of the three recorded shapes is git-specific: a read-only probe captured into a command substitution (`BASE=$(git merge-base origin/main HEAD)`, `d=$(ls logs/archive | sort | tail -1)` — run it bare and read the value off the output), an inspection glued to a mutation in one call (`ls -la logs/claude-proxy.db*; mv …` — two calls, which is the branch-lifecycle rule generalized), and a long process launched with a trailing `&` plus `sleep` (the Bash tool's own `run_in_background` and a bounded wait on the log is the supported form, and re-sending fails again because a foreground `sleep` is separately blocked). **The discovery rules were not restated, because restating them is what did not work**: `serial-discovery` and `redundant-reads` were resolved by #105 and tripped again across thirteen and twelve buckets respectively, so the trip-wire and the no-re-read rule are instead sharpened against the two shapes actually observed violating them. The **per-file loop** — one `Read` per changed file, or one `git diff origin/main:<path> HEAD:<path>` per path, recorded at runs of twelve in review workflows — is called out as the clearest case the trip-wire governs, because the file list arrived in a single call and every read in the loop was therefore known before the first went out; `git diff origin/main...HEAD -- <path> <path> …` asks once. And **re-reading to locate a different symbol** is named as a re-read rather than a new lookup, since it is what puts `server/src/api.ts` and the `apps/admin/src/` route files at four and five reads: `rg -n 'foo|bar' <file>` finds both at once and a numeric `offset`/`limit` slice fetches only the range still missing. The section is no longer than it was — a fan-out bullet that duplicated the one four bullets above it was removed to pay for the new text. The `unfinished-tasks` suggestion, the largest by bucket count, was **deliberately not acted on**: its fix belongs to the slash-command definitions in the separate `my-command` repo, not here.

- **`AGENTS.md` now names the exact failures this repo's own analyzer keeps measuring** — the sections covering worktree ownership, shell forms and discovery were already there and the behaviours regressed across ten consecutive buckets of sessions anyway, because the rules were advice rather than something checkable mid-turn. Each is rewritten in place against measured evidence rather than added alongside: the worktree-ownership section now quotes the `This session is not the owner of the worktree at …` error verbatim, names the tool that emits it, states that the second call returns the identical error, gives the `git worktree list --porcelain` → `my-command-tools worktree end` replacement, and tells a compacted session to re-derive provenance instead of assuming ownership. Bash — the source of roughly two thirds of all failed tool calls — gets a working form per observed shape: `pnpm --filter <pkg>` instead of a relative `cd server`, absolute paths instead of `cat components/…`, `LC_ALL=C` for `sed` over the non-UTF-8 bytes in `logs/`, an explicit timeout instead of a retry into the same 2m ceiling, and `pr --title … --body -`. Serial discovery gets a countable trip-wire (four consecutive read-only calls with no decision between them) and re-reading gets a flat rule reconciled with the read-before-write precondition, so the two no longer read as contradicting each other. The repository map now covers `apps/admin`'s hand-registered route table, `packages/core`, `proxy/` and where tests live, so a session stops re-deriving the layout. One claim in the source suggestions was **checked and dropped**: `ERR_MODULE_NOT_FOUND` in a fresh worktree is not a missing `@claude-proxy/core` build, because there is no build — its `exports` map points at `./src/index.ts` and `packages/core/dist` never exists — so the rule says bootstrap instead.

- **An evicted request body is now a typed state, not a missing file** — reading a body that retention removed used to throw `request file not found`, which is indistinguishable from a bug. `/api/context/detail`, `/api/context/message` and `/api/context/tool` now return a discriminated union: either the body, or `{ evicted: true, day, retentionDays, retained }` carrying the audit sidecar's metrics, and the dashboard renders **"Body evicted after 30 days — metrics retained"** with the retained token counts, byte totals and tool table. A body that was never captured at all still 404s, so real bugs stay visible. `/api/skim` gained `meta.bodiesEvicted`, counting requests whose sidecar is present but whose body is gone; both read backings derive it from the same disk observation rather than from the substrate's `blob_evicted` column, which is only as fresh as the last ingest — so the parity harness stays byte-identical. Drill-downs also now resolve bodies inside `archive/<date>/` rather than only the live directory, which archiving again would otherwise have made unreachable for every past day.

- **Reads now come from SQLite, and the way back is one flag** — slice 5 of the [SQLite migration](docs/wayfinder/map-sqlite-substrate.md) graduates the substrate from a shadow to the thing actually answering. Slices 1–4 built the tables and proved, route by route, that the database returns byte-identical JSON to the directory scan; this slice flips the default. Every API route now reads through `readSource()` in `server/src/db/runtime.ts`, which hands back the substrate unless `DB_READS=0` is set, in which case every route goes back to the file scan it used through slice 4. That is the entire rollback: no migration to undo, no data to move back, because the log files were never touched and the scan still answers everything. The resolver is also the only place that chooses, so no endpoint can quietly end up on a different backing than the one beside it, and it falls back on its own if the database could not be opened at all — a failure to open is a slow read, not an outage. The startup banner says which side is serving. **The invariants are unchanged**: `logs/` is still the sole source of truth and the database is still a disposable materialized view, still rebuilt from scratch by `rm logs/claude-proxy.db && pnpm --filter server ingest`; authored state (`logs/suggestion-status.json`, device settings) is still a JSON file and still read as one from both sides; `logs/sessions/*.md` are still written exactly as before, which is what keeps `/revive` working off disk with no API and no database; nothing under `proxy/` was modified; and there is still **no new dependency** — `node:sqlite`, raw SQL, `PRAGMA user_version`, schema still at version 3.
- **Shadow mode is now whichever side did *not* serve** — it was built to check the substrate against the files while the files answered, which after the flip would have been checking the answer against itself. `shadowSource()` returns the opposite of whatever `readSource()` picked: the files verify the substrate by default, the substrate verifies the files under `DB_READS=0`, and neither happens when the substrate never opened, because then there is no second opinion to be had. `shadowCheck` takes which side served so a reported difference still labels the file answer `files` and the database's `db` whichever way round it ran. It is still off unless `SHADOW_DB` is set, still runs in a `queueMicrotask` after the response is out, and still cannot affect what was served.
- **`/api/sessions/session` re-reads the transcript when the row is behind it** — this was a known blocker, recorded by slice 2 and deliberately left for the slice that flipped reads. `dbSource.readSession` returned the row's `meta`, `bytes` and `modified` alongside a freshly-read `content`, so a transcript appended to since the last ingest produced an object that disagreed with itself: `bytes` counting a shorter transcript than `content` held, `meta` describing a header the content had moved past. File-backed reads made it harmless, and the parity harness could not catch it by construction — it snapshots the corpus precisely to freeze the appends that cause it. It now reads the content and `stat`s the file in the same breath and lets the file's own size and mtime be the authority, using the row's metadata only when its watermark matches exactly, which is the same equality `ingest` uses to decide a transcript is unchanged. When the row is behind — or missing entirely, for a transcript the substrate has not reached yet — it re-parses the content, which is exactly what the file reader would have answered. The trade-off is named rather than hidden: this route stops being a detector of a transcript the substrate missed, so `/api/sessions` — replayed whole, and length-sensitive — is what catches that now, with shadow mode as the second net. There is a test that does the append the harness exists to prevent.
- **`/api/commands` reads back the store it just reconciled** — the same staleness the transcript fix settled, in the one place the server writes before it reads. `withCommandReconcile` appends to `logs/commands/runs.jsonl` and then answers from the substrate, which only picks the append up after the ingest watcher's 500ms debounce; a just-detected run, or a just-retired one, would have been missing from the very response the reconcile ran to produce. `dbSource.readCommandRuns` now `stat`s the store and compares it against the `file_watermark` row `ingestCommandRuns` keeps — the same `bytes`/`modified` equality used everywhere else — and re-reads the file whenever the mark is missing or does not match exactly. The rows answer only when they are provably current. The parity harness could not catch this either: it reconciles once and ingests before replaying, so its rows are never behind. There is a test that appends to the store between two ingests.
- **The suggestion-status write goes through the seam too** — slice 4's review flagged that `applySuggestionStatus` had grown a source parameter with no caller that ever passed anything but the default. Rather than delete it or leave it unexercised, the POST handler now passes `readSource()`. The flags themselves are authored state and stay in `logs/suggestion-status.json`; what goes through the seam is the derived half the response echoes back — the bucket/suggestion join — so the POST cannot describe a different corpus than the GET beside it. It stays out of the parity harness on purpose, because it is a write and replaying it against the real-corpus snapshot would write through a hardlinked status file; it is covered instead by a both-backings agreement test on the synthetic corpus. The CLI keeps the file default, since it runs with no substrate open.

### Added

- **A System prompt page, and it edits the file rather than just showing it** — `~/.claude/CLAUDE.md` is the device-wide instruction file every Claude Code session on this machine loads into its system prompt, and it was the one piece of device config the dashboard could measure but never show: the proxy [deliberately never records the system prompt](docs/features/session-transcripts.md), so the Context-size page could tell you the prompt averaged N bytes of every request while the text itself was only readable in an editor. `/system-prompt` reads the file, renders it, and writes it back. The read half is shaped in core (`outlineSystemPrompt` for the heading outline, `summarizeSystemPrompt` for size, an `estTokens` figure and the section spans) so the page can show the same numbers for the draft in the textarea as for the file on disk — the size tile carries "N on disk" whenever they differ, because what is being edited is the per-request cost of every session that follows. The write half is the fourth entry on the server's write allowlist, so it answers under the origin-checked CORS the chat routes use rather than the open `*` reads get, and it is the only one of the four that rewrites authored state in place. Three things guard that: the text is normalized before it is written (CRLF to LF, trailing blank lines collapsed to a single closing newline) so editing through a browser textarea cannot produce a diff nobody made; the previous contents are copied to `<path>.bak` first, so a bad save is recoverable outside the app; and the new contents land via a temp file plus `rename`, so a crash mid-write cannot leave a half-written system prompt for every later session to load. The response is a fresh read of the file rather than an echo of the request, which means the page cannot show a save that did not land. Clearing the prompt entirely is allowed but takes a second click, the way the job delete does. The route reads `~/.claude`, so — like `/api/projects`, `/api/jobs` and `/api/hooks-plugins` before it — it stays out of the parity harness on purpose: it is outside the `logs/` scope [ADR 0004](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md) gives the substrate, and indexing authored state into a disposable view is the boundary those three already sit behind. `CLAUDE_SYSTEM_PROMPT` overrides the path for tests and non-standard homes.
- **`/clean` and `/pr` are runs of their own, not just steps inside `/task`** — the Commands page promised a nested command would count both as a segment of its parent and toward its own command's numbers, but only the first half was true: `reconcileCommandRuns` parsed the `<command-name>` envelope solely against a session's opening prompt, and a nested command is never the opening prompt. All 170 records in the store were commands typed to start a session; zero `clean`, zero `pr`. The obvious fix — parse the envelope on every user turn — cannot work, and the sidecars say why: the CLI expands a nested command **client-side**, injecting the command file's body as an ordinary user turn with `$ARGUMENTS` already substituted and the envelope tags stripped, so there is no envelope on a nested turn to find. What survives is the `Skill(skill=<name>)` tool node the transcript already records, and that is what a child run is now anchored on, restricted to names present in the installed command catalogue so a plain skill like `grilling` is not mistaken for a command. A child run is a **slice** of its host's transcript rather than a separate session: it carries a `nodeRange` running from its own `Skill` node to wherever the next nested invocation begins (or the end of the transcript), and its turns, tool calls, subagents and tokens are the host's, filtered to that span. That is what makes the two readings agree by construction — the parent's totals already contain the child's, because the child is part of the parent, so nothing is double-counted and no hole is left where the child ran. Subagents follow the same rule: a child claims only the ones spawned inside its own span, while the parent keeps all of them. Records are keyed on a new `runId` — a thread id for a top-level run, `<threadId>~<node>` for a nested one — which is deliberately the *same* value as before for every record already written, so the schema bump to `2` upserts the existing store rather than duplicating it, and a link to `/commands/task/<threadId>` still resolves. The reconcile pass stays idempotent and incremental: nested targets share their host's sessions, so the sidecar sweep still opens each `.request.txt` body at most once, ever. The run detail links a child back to the run that invoked it, and the run list shows `nested in /task` where a child has no prompt of its own to show — `/clean` and `/pr` declare no `## Step N` headings, so their records have a single unattributed bucket, but the duration, token cost, tool calls and outcome are real and their own.

- **The command runs are indexed, and the three routes over them are proved byte-identical from SQL** — slice 3 of the [SQLite migration](docs/wayfinder/map-sqlite-substrate.md) extends the substrate from transcripts to `logs/commands/runs.jsonl`, the append-only store `reconcileCommandRuns` distils out of the sessions and the captured requests before they age out. Six tables land: `command_run` (one row per record, carrying the envelope, the model and the run window, the outcome / interruption / `reachedEnd` triple, and the nine `runTotals` figures flattened into columns), `command_run_flag` and `command_run_thread` (the leading `--flags` and the run's whole agent family, the latter joining back to slice 2's `session` rows), `command_run_turn` (the per-turn context series), `command_run_step` (the per-step tokens, cost and the five waste counters), and `command_run_pattern`. Everything slices 1 and 2 settled still holds and is not revisited: `logs/` remains the sole source of truth with the database a **disposable view** — `rm logs/claude-proxy.db && pnpm --filter server ingest` still rebuilds all of it — nothing authored goes in, `proxy/` is untouched, reads are still file-backed, and the whole thing is still `node:sqlite` with raw prepared statements and **no new dependency**. Two things about command runs forced departures from the previous slices' shape, and both are why runs are their own slice. First, **a run is stored, not re-derived**: unlike a sidecar or a transcript, nothing re-reads a run's source on every read, and `readCommandRuns` deliberately hands back records it does not fully understand — `isCommandRun` checks three identity fields, so a record written by a newer or older writer is kept and rendered from whatever it has, which is also why half the record's fields are optional (`retired?`, `CommandStep.artifacts?`, and every field `runTotals` and `toListItem` default). Rebuilding such a record from columns cannot reproduce "this key was absent" versus "this key held the default", and it would silently drop a future writer's fields the moment slice 5 flips reads to DB-backed. So `command_run` carries a `document` column holding the record itself: **the tables exist to be queried, the document is what is served**, and the DB-backed `readCommandRuns` re-parses documents and re-applies the store reader's own sort and `retired` filter rather than reassembling anything. Second, **the store is a single mutable file**, so it gets a third watermark shape — a `file_watermark` row keyed on the path, holding `bytes` + `modified` — and a store whose `stat` still matches is never opened; when it has moved, the whole file is re-parsed and every row replaced inside one transaction, which is bounded because the table holds one row per run rather than one per appended line. `logs/commands/` also gets its own `fs.watch`, since the watch on `logs/` is not recursive. The parity harness gains `/api/commands`, `/api/commands/command` (including one flag facet per command, so the filter is exercised and not just the aggregate) and `/api/commands/run`, all enumerated from the **file** side so the substrate is asked about every command and every run the store knows rather than only the ones it managed to index; the `/stream` variants are absent because SSE re-serves the same builder. The installed catalogue under `~/.claude/commands` is deliberately **not** indexed — it lives outside `logs/`, so it is not the substrate's to mirror and both backings read it identically — but the harness pins it on `ParityContext.commandsDir` so a `/sync` landing mid-run cannot move it between the two replays, and the real-corpus test **copies** both it and `runs.jsonl` into its snapshot, because a hardlink freezes which files exist and not their contents. Shadow mode covers the three new routes behind `SHADOW_DB`, computing the DB answer after the response is already written and never affecting it. `NORMALIZATIONS` is still empty.

- **The session transcripts are indexed too, and the ten routes over them are proved byte-identical from SQL** — slice 2 of the [SQLite migration](docs/wayfinder/map-sqlite-substrate.md) extends the substrate from audit sidecars to `logs/sessions/`: `session` (one row per transcript, carrying the header metadata `parseSessionTranscript` derives, the listing's `bytes` / `modified`, and the untruncated opening prompt off the `.state.json` sidecar), `session_node` (the appended step stream in transcript line order), and `session_node_text` (the `.nodes.jsonl` sidecar). Everything slice 1 settled still holds and is not revisited: `logs/` remains the sole source of truth with the database a **disposable view** — `rm logs/claude-proxy.db && pnpm --filter server ingest` rebuilds all of it — nothing authored goes in, `proxy/` is untouched, and the whole thing is still `node:sqlite` with raw prepared statements and **no new dependency**. The transcript **body** stays on disk exactly as before: `md_path` is a pointer, `readSession` still reads the file for its `content`, and the DB backing never stops those files being written, because [`/revive`](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md) reads them straight off disk with no API and no database. Two things about transcripts forced departures from slice 1's shape, and both are the point of doing sessions as their own slice. First, **a transcript is mutable** — the proxy appends to it for the life of a run — so "seen this filename stem already" is not a sufficient watermark the way it is for an immutable audit sidecar. The session watermark is therefore **per file** (`bytes` + `modified`): an append always moves the size, so one `stat` per transcript detects change without re-reading it, and ingest stays idempotent — a second pass over an unchanged directory parses nothing. The same mutability meant the `fs.watch` had to be widened, since the proxy appends inside `logs/sessions/` without touching `logs/` itself, and a non-recursive watcher on the parent would have let the tables trail the files for a whole run. Second, **`session_node_text` is deliberately not a column on `session_node`** and carries no foreign key to it: the sidecar is sparse, it outlives edits, and it can name a node index the transcript no longer has — the file reader hands such an entry back rather than dropping it, so the substrate has to be able to as well. Eviction, by contrast, is *not* a state here: unlike a `request` row, whose `.md` body can be retained away underneath it, a transcript **is** its row's source, so a body that disappears takes the row with it (and its nodes, by cascade) on the next pass. Ten more routes register with the **parity harness** — `/api/sessions`, `/api/sessions/graph`, `/api/sessions/session`, `/api/sessions/node-text`, `/api/sessions/breakdown`, `/api/sessions/errors`, `/api/sessions/graph/nodes`, `/api/sessions/suggestions`, `/api/sessions/suggestions/bucket` and `/api/context` — replayed both ways with the **full JSON** compared, key order included, and the `NORMALIZATIONS` list still **empty**: the agent tree is rebuilt on the DB side by the same `linkAgentSessions` the file reader uses, which sorts each family internally and so does not care what order SQL hands rows over in, and the listing sort is reproduced rather than compensated for. `/api/context/detail`, `/api/context/message` and `/api/context/tool` are the named exceptions and stay unregistered: they read a `.request.txt` body straight off disk and touch no indexed column, so there is no DB path for them to disagree on. Per-thread cases replay the newest twenty transcripts rather than all of them — not a weakened comparison, since `/api/sessions` and `/api/sessions/graph` are replayed whole and carry *every* transcript's metadata and node stream, so a row the substrate got wrong fails there regardless; the cap only bounds the routes that re-read request bodies per thread. The real-corpus test's snapshot was widened to take `sessions/` too — the transcripts being the most volatile thing in the log directory, they are precisely the race that snapshot exists to close — and it **copies** them rather than hardlinking, unlike the write-once audit sidecars: a hardlink shares the inode, so it freezes which files exist but not their contents, and the proxy's appends to a live transcript would otherwise land inside the snapshot mid-replay and read as a substrate mismatch. The session suffix list is kept separate from the sidecar one because `.md` means two different things in this tree and taking the request bodies would have changed which requests read as blob-evicted. **Shadow mode** covers all ten new routes on the same terms as before: served from the files, computed from SQL alongside, mismatch logged, off unless `SHADOW_DB` is set, and strictly unable to affect the response. **Nothing flips to DB-backed reads** — that is slice 5.

- **A SQLite query substrate over the logs, built as a disposable view and proved byte-identical before anything depends on it** — `logs/` is doc-shaped, so every read path in the server is a full `readdir` + `readFile` scan rebuilt per request; the questions the dashboard now asks ("which tools burn the most tokens across every session", "how does this move across thirty archived days") are joins and aggregations, and a directory listing cannot serve them without re-reading everything each time. So the audit sidecars are now indexed into **`logs/claude-proxy.db`** — SQLite in WAL mode via **`node:sqlite`**, which is built into Node and therefore adds **no dependency**, leaving the project's zero-dependency stance intact; the one real platform change is the engines floor moving from `>=18` to `>=22`, Node 18 having gone EOL in April 2025 and Node 20 in April 2026. Raw SQL with prepared statements, schema version in `PRAGMA user_version`, no ORM and no query builder. What the database is allowed to *be* is the load-bearing decision: it is a **disposable materialized view**, `logs/` stays the sole source of truth, every table is reconstructible by re-ingesting, and the supported total-recovery path is therefore just `rm logs/claude-proxy.db && pnpm --filter server ingest`. That invariant decides the rest. Nothing **authored** goes in — `logs/suggestion-status.json` and device settings stay JSON files, because a view that can be deleted may not hold the only copy of something no re-ingest could rebuild. The `.md` and `.request.txt` bodies (~1.2 GB/day, ~99% of the bytes) stay on disk untouched, with the DB holding nullable pointers plus an explicit `blob_evicted` flag, so "retention deleted the body, we kept the metrics" is a queryable fact rather than a dangling path. And **`proxy/` is not touched at all**: the proxy is load-bearing — if it breaks, Claude Code itself stops working — so the server does all ingest, which is a blast-radius decision rather than a dependency-purity one. Ingest runs on server start plus an `fs.watch` on the log directory, keyed on the sidecar filename stem, so running twice or dying halfway are both harmless; it reconciles each directory against its live listing, so a day the summary job archives moves its rows rather than duplicating them and a file retention deletes takes its rows with it. The schema is audit rows only in this slice — `request`, a normalized `request_tool` (the headline unlock: "which tools burn the most tokens" becomes a `GROUP BY`), `request_rate_limit`, and `ingest_watermark` — plus two tables the spec did not ask for and losslessness did: `request_skipped`, because the file readers count an unparseable file under `parseErrors` and a structurally invalid one under the digest's `skipped`, and a view that quietly dropped them could not reproduce those numbers; and explicit `*_present` flags, because a legacy sidecar with no `session` object and a current one whose every session field is null are different facts on disk. **Nothing reads from the database yet**, and the reason is the artifact this slice really exists to build. The file-backed and DB-backed readers sit behind one `SidecarSource` interface, and a **parity harness** replays every wired route (`/api/summary`, `/api/tools`, `/api/trends`, `/api/usage`) against the whole of `logs/archive` **both ways**, asserting the **full JSON is identical** — including object key order, which `JSON.stringify` preserves and the digest's model map inherits from read order — never a row count and never a summary. Legitimate diffs are permitted only as **named** normalizations that state the mechanism making them benign, and the list is **empty**: rather than sorting differently and compensating, the DB reader reproduces the file reader's filename-stem iteration order exactly, which is what makes tie-breaking in the tool table and the busiest-hour scan land the same way on both sides. A harness that cannot fail proves nothing, so one test corrupts a row on purpose and asserts the harness catches it. Against a hardlinked snapshot of this machine's real archive — 14 days, ~14,800 requests, ~506,000 tool rows — all four routes are byte-identical on every day with zero normalizations; the snapshot is what makes that reproducible, since replaying against the live directory races the proxy still writing to it. Alongside it, **shadow mode** (`SHADOW_DB=1`, off by default) serves from the files exactly as today and computes the DB answer in parallel, logging any disagreement; it is a strict observer, running after the response has gone out and swallowing every failure inside it, because a broken substrate must not be able to break a page. Routes flip per route, only once parity is green, and the log files keep being written throughout — recorded in [ADR 0004](docs/adrs/0004-adopt-sqlite-as-the-query-substrate.md) together with the hard constraint that `/revive` reads `logs/sessions/*.md` straight off disk with no API and no database, so a later stage must not stop writing those files until `/revive` has been taught the DB, on pain of the migration disabling its own recovery mechanism. The remaining five slices, and a resume runbook written for a cold agent, are in the [migration map](docs/wayfinder/map-sqlite-substrate.md).

- **A suggestion's `done` is read as a dated claim, so a fix that held stops looking like one that didn't.**
  - Buckets are frozen windows, so a rule that tripped on old sessions trips on them forever — "still tripping" was never evidence a fix failed.
  - Each flag's `updated` is compared against the window's session span, giving every row a `recurrence`: `historical` (the window predates the claim), `regressed` (the window was recorded entirely after it and tripped anyway), `mixed`, `none`.
  - The claim is rule-wide rather than per bucket: one `done` carries to every later window instead of needing one mark per bucket. Only `done` counts — `skipped` and undated flags never produce a regression.
  - `suggestions list` hides `historical` by default and prints the hidden count, so the suppression is visible rather than silent; `--recurrence <states>` and `?recurrence=` narrow explicitly.
  - The dashboard badges recurrence, counts `N regressed` in both headers, keeps regressed rows undimmed with a coral border, and folds `historical` into "hide resolved".

- **A Commands page that measures what each slash command costs to run** — a new **Commands** station studies the efficiency of the commands installed in `~/.claude/commands`: how many tokens each declared `## Step N` burns, what prompt drove the run, and where runs die. Capture is **passive** — every real invocation whose prompt envelope carries a `<command-name>` is a run, so there is nothing to tag and no harness to start — and a run is the top-level session rolled up with its whole subagent tree via the existing `linkAgentSessions`, with a nested command counting both as a segment of its parent and toward its own command's numbers. The feature exists in three levels: `/commands` lists installed commands with invocations, a cost sparkline, completion rate and last run; `/commands/:command` leads with a **run scatter over time** (x = when, y = total tokens, colour = outcome, size = turns) carrying vertical markers where the command file itself changed, above a stacked tokens-by-step bar that swaps to a single run on hover, a pattern-frequency table and the run list; `/commands/:command/:threadId` draws a **token-weighted step tree** with the declared steps as the spine, every turn, tool call and subagent hanging off its attributed step at a width proportional to its tokens, and a per-turn delta inspector that reuses `/api/context/message` to show the actual bytes a turn sent. Flags are a **facet** rather than a variant — `/task --sub` and `/task` are the same command, filtered — because splitting them would fragment a small sample into a smaller one. What makes any of this possible is a store: transcripts and captured request bodies live for roughly a day and only sidecars are archived, so an append-only, schema-versioned `logs/commands/runs.jsonl` distils each run while its raw material is still on disk, and the page reads only from there. One idempotent reconcile pass keyed by thread id upserts records, fired debounced on log-directory change so the page moves mid-run and again from the daily-summary job as a backstop — the same code path both times, safe to re-run. Because the store is the only source, **data accrues only going forward**: there is no backfill, and a fresh checkout shows installed commands with no runs, which is the honest state rather than an error. The design's real constraint is that **step attribution is a heuristic** — turns are placed by the agent's own narration and by nested sub-command boundaries, not by any marker the model emits — and the feature refuses to pretend otherwise. Each placement carries a confidence, the run detail states plainly how much is guessed ("53 of 64 transcript nodes were placed against a step, 3 of them anchored on something the run actually did"), and turns nothing could place go into a dashed, clearly-labelled **unattributed** gutter that the UI shows rather than hides. The attribution rules are isolated and unit-tested precisely so an explicit `STEP n/N` marker can replace them later without touching anything else. Nothing is normalised — no dividing by files touched or diff lines — because a size proxy would launder the raw distributions this page exists to show. The pattern catalogue is a small deterministic rule set firing on specific graph nodes and badged there, joined across runs for frequency ("seen in 13 of 18 `/task` runs"), not sequence mining; waste and rework are step-attributable counters in the run record (errored tool calls, duplicate reads, cache misses, no-op turns), and the existing per-session suggestions engine is **linked** on the run detail rather than rebuilt. Degradation is stated wherever it happens: a run whose transcripts have aged out says so instead of rendering zeros as fact, a command with no `## Step N` headings reads "none declared", a step never reached is labelled as such, and a schema bump leaves older records readable rather than crashing the page.

- **Usage meters that read Anthropic's own numbers** — the meters were live but wrong: the Overview showed a weekly window at ~142% while Claude Code's own `/usage` panel said 7%. Two independent causes, both fixed here. The first is the denominator. Anthropic returns `anthropic-ratelimit-*` headers on API-key traffic but not on subscription OAuth traffic — measured on this device, **0 of 12,929** captured sidecars carried a `rateLimit` field — so the "authoritative" header path never once fired, and every window fell through to a ceiling *learned* from history, which is only a lower bound on the allowance. Dividing by a floor reads far too high. So the proxy now polls `GET https://api.anthropic.com/api/oauth/usage`, the same endpoint that panel reads, and a window sourced from it is exact: Anthropic's percentage, Anthropic's reset instant, no ceiling guessed at and no coverage caveat. That call needs the user's OAuth token, which decided where it lives — **in the proxy**, where the token is already in memory to be forwarded, so only the resulting numbers ever reach disk and the credential is never written, logged, or put in a sidecar; `x-api-key` requests are ignored outright, the endpoint being OAuth-only. It polls on a fixed 60-second timer rather than per request or per SSE tick, because a busy session would otherwise hammer it hundreds of times a minute, and it writes `logs/usage-live.json`, which wakes the existing log-directory watcher so the Overview stays live over SSE with no new plumbing. Every failure mode degrades rather than breaks: a failed poll leaves the last good file alone, a reading older than five minutes stops being used as a percentage, an unrecognised `kind` is skipped rather than guessed onto the wrong meter, and with no token seen yet — a freshly-started proxy, before its first request — the whole thing simply falls back to the estimate. The second cause is the *numerator*, and it would have survived the first fix. Anthropic's weekly allowance is a **fixed** window resetting at a published instant, not a trailing seven days, so estimating over a trailing week sweeps up everything since last Friday and charges it to an allowance that reset on Saturday: on this device, 83.0M weighted units counted where 14.9M actually belonged, a **5.6× overcount**. The estimate now anchors to the real reset instant, and the anchor deliberately **outlives the reading it came with** — allowances reset on a fixed cadence, so an instant that has already passed is rolled forward by whole windows and a week-old poll still marks where the current window opened. Coverage for an anchored window is measured against the part that has *elapsed* rather than the nominal span, since a weekly window seven hours old with all seven hours on disk is completely covered, and judging it against 168 hours would read 4% and stamp `partial` on a complete count. With no anchor ever seen the window still falls back to trailing — wrong in a known direction rather than unknowably.

- **Deleting a job from the Jobs page, for real** — each row on **Jobs** gains a `Delete` that removes that job's whole directory from `~/.claude/jobs`: its state, its timeline and everything under its `tmp/`. Listing husks without a way to clear them was half a feature — they accumulate, nothing else reaps them, and the page that knows about them is the obvious place to act. It is an actual `rm -r` with no trash behind it, so the control is awkward in proportion: the first click *arms* the row (`Delete 4.2 MB?` / `Yes, delete` / `cancel`), only one row is armed at a time, and what was removed is stated afterwards — name, file count, bytes freed, path — above the table it just changed. A **running** job is refused: its daemon is still writing there, so the button is disabled up front rather than failing after the click, and the API answers 409 if something asks anyway. Backed by `POST /api/jobs/delete`, the one destructive route in the API and the one on the jobs surface that isn't a GET: it goes through the origin-checked write CORS the chat routes use rather than the read routes' `*`, since a wildcard origin on a delete would let any page open in the browser wipe the device's job history. Before removing anything it re-establishes the target from scratch — the same id validation and direct-child test, an `lstat` that refuses a symlinked job directory outright (removing the link would leave the target, following it would delete outside the root), and a realpath check that the directory is still a direct child of the realpath'd jobs root. The reply carries the refreshed listing as well as the removal, so the page never re-renders a row that is already gone.

- **A device-wide browser for `~/.claude/jobs`** — a new **Jobs** station lists every background job directory on the machine, whichever project it ran in: state, working directory, file count, size and last activity, newest first, with **Jobs / Running / Husks / On disk** tiles above it. A state word is badged by *tone* rather than matched exactly, so a vocabulary Claude Code extends degrades to `unknown` instead of being forced into a known bucket, and a directory with no readable `state.json` is listed as a **husk** rather than hidden — its job is gone, its scratch space is still on your disk. Selecting any file opens it with a **Pretty / Raw** toggle — pretty re-indents and colours JSON, renders `timeline.jsonl` as badged state changes, strips terminal escapes and collapses carriage-return progress redraws out of a build log, numbers and colours source, and inlines a screenshot; raw is the bytes on disk, for the moment you suspect the pretty view of hiding something. Reading is confined to the job: the id and every path segment are validated, then the resolved path is `realpath`'d and re-checked against the job root, so a symlink an agent left in its own `tmp/` cannot become a way to read the filesystem; text is capped at 512 KB and a file whose bytes contain a NUL is reported as binary rather than shown as mojibake. Backed by `GET /api/jobs`, `GET /api/jobs/job?id=` and `GET /api/jobs/file?id=&file=` (`CLAUDE_JOBS` overrides the directory), with the shaping and the viewer transforms pure and unit-tested in `packages/core`.
- **Usage meters that configure themselves** — the meters previously needed `USAGE_LIMIT_5H` / `USAGE_LIMIT_WEEK` set per device, so a checkout without them showed only the note telling you to set them. They now fall back to a ceiling **learned from history**: the busiest *completed* window on record. The distinction matters twice over. Only completed windows count, because the one in progress is still filling and would peg every meter at 100%; and only windows the retained logs fully span count, because a window starting before the oldest retained request is a fragment, and admitting it would drag the peak down to whatever survived rotation. That history has to come from `logs/archive/<date>/`, which keeps full per-request sidecar triples — the live `logs/` directory holds roughly a day and cannot span even one completed week. The new `server/src/usage-history.ts` reads 28 days of live plus archived sidecars (four weeks leaves room for three completed weekly windows) and memoises the result for an hour, since thousands of sidecars is too much to re-read per request and the answer can only change when a window completes. What the feature refuses to do is the interesting half. A learned ceiling is a **lower bound on the allowance, never the allowance** — Anthropic never stated the limit, so the most that can be said is "at least this much was possible" — and the error runs in one direction only: dividing by a ceiling that is too low makes utilization read too *high*, so the meter overstates how close the account is and cannot invent headroom. The UI carries that rather than burying it: the window is marked `inferred` with the reasoning on hover, the status chip drops limit language for record language (`Below record`, `Near record`, `New record`), and the blurb calls passing the bar *new territory* instead of exhaustion — only the header path ever claims requests will be refused. A configured ceiling still wins outright, being a statement about the allowance where the learned figure is a guess at its floor, and `USAGE_LIMIT_ENV_SUFFIX` in core is now the single source of truth for those variable names so a blurb cannot suggest one the server doesn't read. Nothing is invented where nothing is known: a window with under one completed window of history is omitted as before, and a window kind with no traffic at all learns nothing rather than a ceiling of zero, which is how the Fable meter stays absent on plans that never touch it. Two documentation errors went with it — the archive keeps raw sidecars, not per-day digests as the feature doc claimed, and a proxy restart does **not** always produce `rateLimit` headers: Anthropic returns `anthropic-ratelimit-*` on API-key traffic but not on subscription OAuth traffic, so on such an account the header path never fires at all, which is exactly the gap the learned ceiling fills.

- **The Overview tracks the usage limits, live** — a meter per metered allowance (rolling **5-hour**, **weekly**, and **weekly Fable** where it applies), each with a sentence saying whether the current rate is comfortable, close to the ceiling, or on track to run out early. The meters and the day's digest now both arrive over SSE — `/api/usage/stream` and a new `/api/summary/stream`, both watching the log directory through the existing `serveSse` helper — so the page moves as the proxy captures requests instead of at the last reload. The bar's colour tracks the **pace**, not the fill level: a nearly-full bar late in a window is fine while a modest one early on may not be, so the tone comes from where the rate is heading, and a faint extension of the bar marks the utilization the rate projects to by reset. The projection is `utilization / elapsed` — the sustainable rate being to spend the whole allowance over the whole window — with `elapsed` derived from the reset instant, so a window resetting in 1h of 5h is 80% gone. Two sources feed it, in order. First, **Anthropic's own accounting**: the proxy already had `up.headers` in hand and now records every `anthropic-ratelimit-*` / `x-ratelimit-*` response header into the sidecar's new `rateLimit` field, which carries the real allowance and the real reset and so needs no configuration. Names are matched by *shape* rather than against a fixed list — one segment names the span (`5h`, `7d`/`week`), an optional one narrows it to a model family, the last names the field — so a renamed or newly-added window reaches the dashboard without a proxy change; resets are accepted as an ISO instant, epoch seconds, epoch milliseconds, or seconds-from-now; and only the newest request's headers are read, since an older reading understates everything since. Second, an **estimate** from logged tokens in weighted units (`input + output + cacheCreation + cacheRead × 0.1` — cache reads bill at about a tenth of fresh input, and `realInput` is avoided because it already sums the other three), measured against a ceiling from `USAGE_LIMIT_5H` / `USAGE_LIMIT_WEEK` / `USAGE_LIMIT_WEEK_FABLE` (`_`/`,` separators and `k`/`m` suffixes accepted). There is deliberately **no default ceiling**: Anthropic doesn't publish quotas as token counts, so a window with neither headers nor a configured limit is omitted rather than drawn against an invented denominator — and setting the Fable ceiling is what opts that meter in, which is how "optional based on plan" is expressed. The honesty of the estimate is the subtle part. `logs/` retains roughly the current day and the archive keeps per-day *digests* rather than raw sidecars, so an estimated **weekly** window routinely cannot see its own span — measured at 15% coverage on this device. Each estimated window therefore reports `coverage`, and below 0.95 the meter is labelled `partial` in amber with the blurb stating the real figure is higher, so a reassuring number never stands unqualified on incomplete data. Two more states refuse to read as reassuring zeroes: no requests captured at all emits no estimated window (0% would say "well within limits" when the truth is "nothing was observed"), and a trailing estimate gets its own vocabulary throughout — exceeding a ceiling the operator chose says so, and only the header path claims requests will be refused. The pace logic is pure and takes an injected `now`, so every threshold is covered by tests.

### Fixed

- **The parity harness's staleness test queried a column that no longer exists** — the assertion that `/api/commands` re-reads a store the rows are behind looked the run up by `thread_id`, but `command_run` has been keyed on `run_id` since nested runs became records of their own (a nested run *shares* its host's thread, so the thread id was never a key). The test failed with `no such column: thread_id` rather than on the behaviour it guards. It now looks the row up by `runKey(run)`, which is what the table stores.

- **`/clear` is no longer a command run, and no longer charged for the work that followed it** — the Commands index listed `clear` with eleven invocations, one of them at **$17.05 over 60 turns**, for a command that executes entirely in the CLI and never reaches the model. Nothing was miscounted: a run is any session whose opening prompt carries a `<command-name>`, and when a local command opens a turn the CLI sends its envelope as the *first* thing in that user message — so a session begun with `/clear` rooted on `/clear`, and every token the session went on to spend was booked against it. On this device that was true of eight sessions whose real command was typed in the same breath (`/mc -t feat/command-toolkit-cli`, `/revive`, `/review`, `/fb`, `/improve`), each of which lost its own run to a `clear` row, plus three where nothing followed the `/clear` at all and the row existed only to hold somebody else's cost. `parseCommandEnvelope` now walks the envelopes in order and takes the first **non-local** one, so those eight are recorded as the command that actually ran and the three are not runs at all. Locality is decided by **adjacency** and nothing else — the caveat text has to sit directly ahead of the envelope, the order the CLI emits across all eleven caveats in the captured logs — because that same caveat survives verbatim into compaction summaries, thousands of characters from an unrelated envelope it says nothing about. Each envelope's `<command-args>` is now read from its own block rather than from the first one in the prompt, which is what had been emptying these runs' prompts: `/clear` carries empty args, so the criteria the user actually typed were being discarded along with the label. That block ends at its **own closing tag**, not at the next envelope, because criteria quote envelopes constantly — a `/task` run whose criteria named `<command-name>/clean</command-name>` and `<command-name>/pr</command-name>` would otherwise have its whole 2,660-character args block cut at the first quotation and come back empty, inflicting the very symptom this entry is about on a run that had been read correctly. Because the store is append-only and cannot forget a line, a record whose thread no longer reads as a run is retracted by writing it back **retired** — `readCommandRuns` drops retired records and re-running retracts nothing further. Only a thread whose **opening prompt was actually read** is retracted: a transcript can outlive its `.state.json`, and the proxy records no `root` at all until it has one, so a sidecar that is missing, torn, or promptless is silence rather than testimony that the run never happened. Retired records are still carried forward through reconciliation, so a thread that reads as a run again keeps the turns that, once its sidecars are pruned, only the record still remembers.

Seven of those closed here. **Skeleton loading** claimed every `QueryState` call site passed a skeleton, and six did not — Commands, Command detail, Command run, Jobs, and both queries on Job detail now reserve their own shape (stat rows, the 300px run scatter, the step tree, the file tree beside its viewer), built from the pages' own classes with no pixel heights, and the doc's call-site count is corrected from 21 to 27. **`server/src/api.ts` read as a binary file** to `rg` and `grep`, because a suggestion's map key was built as `` `${bucket}\0${id}` `` and the literal NUL made every search of that file silently miss — including the search for the function two items below. The separator is now a unit separator written as an escape, which no more appears in a number or an id than a NUL did, so key semantics and collisions are unchanged and `rg buildTools server/src/api.ts` matches again. **The read routes were not method-gated**: `POST /api/withheld` and its siblings answered 200 under the wildcard CORS that is only safe while those routes stay reads, and now answer 405 with `Allow: GET, OPTIONS`. The six documented POST routes keep their origin-checked CORS exactly as it was and still own their own methods — a foreign-origin POST to `/api/chat/sessions` is refused there with 403, not 405. **`UsageMeter` collapsed two pace statuses** into one label, so `on-pace` and `aggressive` both read `Near record` despite already carrying different tones; `aggressive` now says `Passing record`, which is what projecting past the record by reset actually means. **`requestsToScan` ordered a small candidate set largest-first**, which in a session whose bodies grow toward the end means reading only the tail — the same peak-then-even-timeline-walk the general path takes now runs for a set inside the budget too, with the timeline filling whatever reads the walk's own dedupe left spare. **`bucket-tool-schema-heavy` shipped `sources: []`** while its sibling rule named its evidence; `BucketBreakdownSummary` now carries `toolsSources` — the requests the average was taken over, heaviest schemas first, capped at ten — and the rule cites them. And **`PROXY_FILTER_INVENTORY`'s `task-tools` entry** described a proxy that no longer exists; it now states what `proxy/proxy.mjs` strips today: a regex anchored on the injected note's opening and closing phrases, cut from every text block, with an emptied block dropped, a message left with no content dropped, the blank-line run collapsed, and text nothing matched forwarded byte-for-byte. Two of the fixes carry new tests — that a small candidate set is not size-ordered, and that a read route refuses a POST over a real socket rather than a handler stub.

- **The weekly usage meter counts the whole week** — the Overview's estimated windows summed only the live `logs/` directory, which retains roughly the current day, so the weekly meter reported **3% of window** on this device: a seven-day figure drawn from about five hours of logs, comfortable-looking no matter how hard the account had been running. The archive that fixes it was already half-wired — `logs/archive/<date>/` keeps full per-request sidecar triples for weeks, and `learnCeilings` has always read four weeks of it to *infer the ceiling* — but nothing ever read it for the **count** that ceiling divides. `buildUsage` now unions the live directory with the archived days the windows reach into, so both halves of the estimate come from the same history. The interesting half is what had to change first. `coverage` measured the span back to the oldest surviving request, which reads a **hole in the middle** of a window as full coverage — and since the amber `partial` marking is what the span drives, backfilling alone would have swapped a visibly wrong number for an invisibly wrong one: this device's own archive is missing two days inside the current week. So coverage now counts the **days actually retained**, via a new `retainedDays` on `buildUsageLimits`; a day counts when its own archive directory is on disk, and because a reporting day can straddle `<date>` and `<date + 1>` the seam can *understate* coverage, which is the safe direction — it marks the window `partial` rather than presenting an incomplete count as a total. Days are the unit because rotation is day-granular, so a quiet stretch inside a retained day is genuinely quiet while a missing directory is a hole; day ends resolve through a new `dayStartMs`, which applies the zone offset twice so the two DST changeover days keep their real 23 and 25 hours rather than being forced to 24. Callers that pass no `retainedDays` keep the old span, which is all a caller with no retention map can honestly claim. Two smaller guards ride along: archived days are memoised individually for the process lifetime — `/api/usage/stream` rebuilds on a 600ms debounce and would otherwise re-read thousands of sidecar files per tick — while an *absent* day is deliberately **not** cached, since the archive job may simply not have run yet and a sticky miss would pin the gap in place until restart; and live and archived reads are deduped by source filename, so an archiver that copies rather than moves cannot double every request in the seam and inflate the very number the meters exist to report.
- **A session's own captures survive an evening start** — the three scans that floor themselves at a session's start (its Request breakdown and errors page via `resolveSessionRequests`, a suggestion bucket's per-session peaks, and the live graph's session-family request scan) derived that floor by slicing the raw UTC instant — `started.slice(0, 10)` — and handed it to `readSidecars`'s `since`, which compares against *reporting* days. Eastern runs behind UTC, so a session opened after 8pm Eastern carries a `started` whose UTC day is already tomorrow, and the floor then excluded every request that session ever made: the breakdown read zero captures, the bucket lost that session's peak, and the graph fell back to drawing the whole run from transcript gists. All three now derive the floor with `reportDay`, the same clock the filter compares against, so the scan starts on the day the dashboard actually buckets the session into — which also **supersedes the day-back widening** the graph's scan took in the entry below, since a floor derived on the right clock needs no slack to cover the offset. `REPORT_TZ` is unchanged: `America/New_York` already tracks EST and EDT as the date dictates. The filename prefilter inside `readSidecars` keeps its UTC slice on purpose — it selects a superset that each sidecar's own timestamp then narrows, and a UTC filename day is never *earlier* than its reporting day, so it cannot drop a sidecar the timestamp pass would have kept.

- **The live graph actually reads the captured requests** — the graph was documented as re-reading its step text from the Request breakdown, and in practice was drawing almost entirely from transcripts, where every line is gisted to 160 characters. Two independent defects, both silent. First, the scan window: the floor for which sidecars to read came off the family's earliest transcript `started`, which is a **UTC** instant, but the sidecar reader narrows by *reporting* day in `REPORT_TZ` (`America/New_York`) — so a session opened between midnight and ~04:00 UTC reports on the day *before* its own timestamp, the floor excluded every request it ever made, and the family resolved to zero captured requests. Measured on the local `logs/`: the same query returned `files=0` at the computed floor and `files=4382` a month earlier. The floor was first backed off a day to cover the offset; the entry above replaced that slack by deriving the floor on the reporting clock itself. Second, the merge: `mergeSessionNodes` advanced its position in the derived stream only on a match, so a single step the two streams worded differently desynced them permanently and every later step stayed at its gist — equal-length 132/132 streams matched only 100, and a 45/45 pair matched 17. It now walks both sides and re-syncs on a mismatch, searching outward along growing diagonals for the nearest pairing that skips fewest steps on either side within a 24-step window; drift is counted in steps because its cause is whole turns one side holds and the other doesn't. Past the window the transcript carries the rest alone, so the graph still degrades rather than breaks. Over the real log directory the two fixes take step coverage from no thread resolving at all to **355 of 358 steps (99%)** read from the captured request.

- **The Request breakdown holds its place when you come back to it** — clicking a row deep in a request's "Messages by size" table and then going back no longer dumps you at the top of the page to scroll down and find your place again. The router had no scroll restoration at all (`createRouter({ routeTree })`), so every arrival — including a Back — started at offset 0; `scrollRestoration: true` turns on TanStack's per-history-entry snapshot, which also covers the other drill-downs and any scroller the page owns, while a forward navigation still starts at the top. That option alone is not enough for a page whose body arrives with a query: the router restores the offset the moment the route renders, which on a cache miss is the loading state, and a document that short cannot hold the offset, so the browser clamps it away. `useRestoredScroll` re-applies the remembered offset once the breakdown's query has resolved and the tables are on screen, and no-ops on a first visit, where the cache has no entry for the location.

- **The day rolls over at local midnight, not 20:00** — every day-bucketed Overview and Trend value is now bucketed in Eastern (`America/New_York`, so EST or EDT as the date dictates) instead of on the sidecar timestamp's raw UTC prefix. An evening's work used to jump to "tomorrow" as soon as UTC crossed midnight, so the Overview both counted the *previous* evening's requests and hid the current one's — on a sample day that was 676 requests wrongly included and 265 wrongly missing. Because the proxy names files in UTC, one reporting day now straddles the filenames `D` and `D+1`: the filename filter selects a superset and each sidecar's own timestamp narrows it exactly, and `readArchivedDay` merges the two UTC archive folders a reporting day spans. Busiest-hour is computed and labelled in the same zone (`17:00 EDT`, not `17:00 UTC`), and the Overview date line and the "By day" tables name the zone they're in. The Skim trend buckets in the same zone, so its days line up with the window that selects them. Digests already finalized into the archive keep the UTC buckets they were written with; raw archived sidecars take precedence over them, so this only shows on days whose sidecars have been pruned.
- **An unsent chat draft survives navigating away** — what you typed into the Sessions page composer but never sent is no longer discarded the moment you click through to a session, the graph, or anywhere else. The draft moved out of `ChatConversation`'s component state (which unmounts with the page) and into `ChatSessionProvider`, which already sits above the router so the turn log, pending prompt and Stop button outlive the page they were started on — the input now travels with them. It still clears where clearing is the point: `send` empties it on submit rather than on success, since the prompt is already on screen as a turn, and "New chat" clears it along with the session it belonged to.

- **Sessions are named, not numbered** — a transcript now headlines what it is instead of its thread id, which is what 92 of 100 local transcripts showed. Only a session Claude Code titled itself carried a name, and it only titles interactive chats: a dashboard-started run is headless (`claude --print`) and a subagent shares its parent's session id, so neither is ever titled. `deriveSessionName` condenses the opening prompt into a short sentence-case name for those, `sessionName`/`sessionDisplayName` set one fallback order (CLI title → derived name → prompt → id) that the listing, the graph, the detail page and a suggestion's sources all read, and the id stays as the mono sublink. Two title-linking bugs went with it: a title landing on the *first* thread whose opening prompt matched left a second thread with the same prompt permanently nameless (it now goes to the most recently active **untitled** match, and never displaces a title already written), and titles were only ever matched against in-memory threads, so a proxy restart dropped them — an unclaimed title now waits in a `.pending-titles.json` sidecar and a title arriving for a thread that exists only on disk is written to it directly.
